# src/features.rs
## Summary
The feature layer — where CodeOwl looks past declarations and imports into call expressions and JSX to build the cross-cutting edges a feature spec needs (M5, extended by M10's `.from("table")` and M11's rendered-component expansion). It holds three narrow extractors (`fetch("/api/...")` literals, `.from("table")` calls, `<Component/>` tags) and their resolvers, plus the participant-set assembly. Deliberately not general call-graph analysis — that stays deferred past Phase 1. This is the most framework-coupled part of the codebase: the `/api/` convention and the Next.js App Router path join are specific to one stack. M13 split it so `assemble_participants` is a stack-generic graph walk over flow edges and one-hop imports, while every Next-specific judgment — `is_page`, the route slug, the `is_colocated || file_does_data_work` admission rule — lives behind `trait FeatureModel`, implemented once here by `TypeScriptNextFeatureModel`. A stack with no runtime entry surface returns `None` from `StackPack::feature_model` and has no feature layer at all; the `extract_*` / `resolve_*` free functions stay `pub` as shims for `TypeScriptNextStack` and the tests.

## `RouteLiteral`
`pub struct RouteLiteral`
### Summary
A resolved `fetch("/api/...")` call site — the file it appears in and the static request path — used to build the client→route edge a feature spec needs. Cached on `Graph` alongside `ResolvedImport` so task assembly never re-parses a file's syntax tree.
### Behavior
Plain data. `static_path` is already normalised by the time a `RouteLiteral` exists: the query string is stripped and the value is guaranteed to start with `/api/` (the extractor discards anything else — a fully dynamic URL, an external host). Call sites are found anywhere in the file, not just at top level, because these calls almost always sit inside an event handler or an effect.
### Depends on
- (none)

## `extract_route_literals`
`pub fn extract_route_literals(source: &str, rel_path: &str) -> Vec<RouteLiteral>`
### Summary
The per-file pass that finds every `fetch("/api/...")` string-literal call in a TypeScript source, producing the `RouteLiteral`s that become client→API-route flow edges.
### Behavior
Parses the file with `ts_parser` (returning an empty vec on a parse failure), then hands the whole tree to `walk_for_fetch` for a full recursive descent — deliberately not the shallow top-level walk `extract.rs` uses, since a `fetch` call is almost always buried inside a handler or effect. Only `fetch(<string literal>)` forms are matched; a `fetch(url)` with a computed argument produces nothing. Runs once per file at index time; the results are cached on `Graph`.
### Depends on
- `src/lang.rs::ts_parser` — crate::lang

## `walk_for_fetch`
`fn walk_for_fetch(node: Node, source: &str, rel_path: &str, out: &mut Vec<RouteLiteral>)`
### Summary
The recursive tree-sitter visitor behind `extract_route_literals` — checks whether a node is a `fetch(<literal>)` call and recurses into every child.
### Behavior
At each node: if it's a `call_expression` whose `function` field is the bare identifier `fetch` and whose first argument yields a static path via `static_path_from_literal`, a `RouteLiteral` is pushed. The identifier check is literal — `window.fetch(...)` or an aliased `f(...)` is not matched. Then it descends into all children unconditionally, so nesting depth doesn't matter and a file can contribute many literals. Only the *first* argument is inspected; a second `RequestInit` argument is ignored.
### Depends on
- externals: tree_sitter

## `static_path_from_literal`
`fn static_path_from_literal(node: Node, source: &str) -> Option<String>`
### Summary
Extracts a fully-static `/api/...` path from the first argument of a `fetch` call — a plain string, or a template string whose path portion has no interpolation. Returns `None` rather than guess at a partially-dynamic path.
### Behavior
For a `string` node it reads the inner content and defers to `path_from_raw` with `path_complete = true`. For a `template_string` it takes named children only (skipping the backtick tokens); if the first isn't a `string_fragment` it bails. It then decides whether the path is complete: it is if there's no `${...}` substitution at all, *or* if the static fragment already contains a `?` — meaning any later interpolation lands in the query string, which is stripped anyway, not in the path. That completeness flag is passed to `path_from_raw`, which is what actually enforces the `/api/` prefix and drops the query string. Any other node kind → `None`.
### Depends on
- externals: tree_sitter

## `path_from_raw`
`fn path_from_raw(raw: &str, path_complete: bool) -> Option<String>`
### Summary
The final filter turning a raw literal string into an accepted route path: drops the query string, keeps it only if it begins with `/api/`.
### Behavior
Bails immediately (`None`) when `path_complete` is false — the caller has decided an interpolation makes the path unreliable. Otherwise it takes everything before the first `?` and returns `Some(that)` iff it starts with `/api/`. So `/api/submit?x=1` → `Some("/api/submit")`, `/other/thing` → `None`, `https://…` → `None`. The `/api/` gate is what scopes route-literal resolution to Next.js App Router API routes specifically.
### Depends on
- (none)

## `text`
`fn text<'a>(node: Node, source: &'a str) -> &'a str`
### Summary
A local helper: the source substring a tree-sitter node spans, as a borrowed `&str`.
### Behavior
Calls `node.utf8_text` against the source bytes and returns `""` on the (practically impossible, for a tree parsed from valid UTF-8 `&str`) error case rather than propagating it. The same convenience wrapper several other modules define privately; kept per-file to avoid a shared tree-sitter utility crate surface.
### Depends on
- externals: tree_sitter

## `resolve_route_literal`
`pub fn resolve_route_literal(graph: &Graph, static_path: &str) -> Option<SymbolId>`
### Summary
Turns a `/api/...` path from a `fetch` call into the `SymbolId` of the `app/api/.../route.ts` file that serves it, using Next.js's directory-to-URL convention — a deterministic segment match, not a search.
### Behavior
Splits the path (after stripping `/api/`) into non-empty segments, then scans `graph.files()` for one whose `api_route_segments` produce a list of the *same length* where each segment either matches literally or is a dynamic placeholder (`[id]`, `[...slug]`) that matches anything. Segment count must be exact — there is no prefix matching, which is safe only because `static_path_from_literal` already refused any path that wasn't fully static. Returns the first matching file's id, or `None` if nothing matches (an external URL that slipped through, a route that doesn't exist, a typo).
### Depends on
- `src/graph.rs::Graph` — crate::graph
- `src/symbol.rs::SymbolId` — crate::graph

## `api_route_segments`
`fn api_route_segments(file_id: &str) -> Option<Vec<&str>>`
### Summary
Given a repo-relative file path, returns its API-route path segments if it *is* a Next.js App Router API route file — `app/api/<segments>/route.ts` — or `None` otherwise.
### Behavior
Requires both the `app/api/` prefix and the `/route.ts` suffix; either missing → `None`. The middle is split on `/` into borrowed segments, dynamic markers (`[id]`) included verbatim. Only `route.ts` is recognised, not `route.tsx` or `route.js` — a Phase-1 narrowing. This is the candidate-side half of `resolve_route_literal`'s match.
### Depends on
- (none)

## `is_dynamic_segment`
`fn is_dynamic_segment(seg: &str) -> bool`
### Summary
Whether a route path segment is a Next.js dynamic placeholder — `[id]`, `[slug]`, `[...rest]` — which matches any literal segment during route resolution.
### Behavior
A bracket check: `true` iff the segment starts with `[` and ends with `]`. It doesn't distinguish single (`[id]`) from catch-all (`[...slug]`) forms — both are treated as "matches one literal segment", which is why `resolve_route_literal` also enforces an exact segment count and a true catch-all route wouldn't resolve a multi-segment path. Adequate for the routes in the pilot repo.
### Depends on
- (none)

## `TableRef`
`pub struct TableRef`
### Summary
One `.from("<table>")` call site — the file and the table name it queries — the Supabase/PostgREST convention for "this code touches that table" (M10). Cached on `Graph` and resolved against the `Schema` nodes `schema.rs` extracts.
### Behavior
Plain data, same shape and lifecycle as `RouteLiteral`: found by a full-tree walk at index time, persisted so task assembly doesn't re-parse. `table` is the raw string argument, unqualified — resolution against a `schema-file::<table>` node happens later, in `graph.rs`.
### Depends on
- (none)

## `extract_table_refs`
`pub fn extract_table_refs(source: &str, rel_path: &str) -> Vec<TableRef>`
### Summary
The per-file pass that finds every `.from("<table>")` member call in a TypeScript source, producing the `TableRef`s that become code→table flow edges (M10).
### Behavior
Parses with `ts_parser` (empty vec on parse failure), then `walk_for_from` descends the whole tree. Deliberately narrow: the argument must be a single plain string literal shaped like a table name (`[a-z_][a-z0-9_]*`), which is what rules out `Array.from(...)` / `Buffer.from(...)` and any `.from(tableVar)`. An ORM-aware matcher (`db.payments`, `Payment.findMany`) is out of scope for Phase 1.
### Depends on

## `walk_for_from`
`fn walk_for_from(node: Node, source: &str, rel_path: &str, out: &mut Vec<TableRef>)`
### Summary
The recursive tree-sitter visitor behind `extract_table_refs` — recognises a `<receiver>.from("table")` call and recurses into every child.
### Behavior
A node contributes a `TableRef` only if all of: it's a `call_expression`; its function is a `member_expression` whose property is `from`; the receiver is not a known builtin (`is_builtin_from_receiver` filters `Array`/`Object`/`Buffer`); there is exactly one argument (`named_child(1)` is `None`); that argument is a `string` literal; and its content passes `is_table_name`. The single-argument rule is deliberate — `Array.from(x, fn)` and RxJS `from(a, b)` are excluded even if they somehow slipped past the receiver check. Then it descends into all children.
### Depends on
- externals: tree_sitter

## `is_table_name`
`fn is_table_name(s: &str) -> bool`
### Summary
Whether a string looks like a SQL table identifier — `[a-z_][a-z0-9_]*` — the shape check that keeps `.from("...")` extraction from picking up arbitrary string arguments.
### Behavior
Non-empty, first character an ASCII lowercase letter or underscore, every character lowercase / digit / underscore. Rejects uppercase (`.from("SomeClass")`), paths (`.from("./x")`), URLs, and anything with a dot or dash. Intentionally strict — a schema that uses mixed-case or quoted identifiers would be missed, which is acceptable for the Supabase/Postgres convention this targets.
### Depends on
- (none)

## `is_builtin_from_receiver`
`fn is_builtin_from_receiver(member: Node, source: &str) -> bool`
### Summary
Heuristic that rejects a `.from(...)` whose receiver is a global constructor (`Array.from`, `Buffer.from`, `Object.fromEntries`-adjacent) rather than a query builder.
### Behavior
Returns `true` only when the member expression's `object` is a bare `identifier` whose first character is ASCII uppercase. The reasoning: a Supabase/query-builder receiver is always a lowercase-initial variable (`supabase`, `db`) or a call expression (`createClient().from(...)`), so an uppercase-initial identifier is a reliable tell for a builtin. A receiver that's a member access or call is *not* flagged here — it's assumed to be a real query builder.
### Depends on
- externals: tree_sitter

## `resolve_table_ref`
`pub fn resolve_table_ref(graph: &Graph, table: &str) -> Option<SymbolId>`
### Summary
Resolves a `.from("<table>")` name to its `Schema` node — an exact-name match against the `CREATE TABLE` symbols `schema.rs` extracted.
### Behavior
Scans `graph.symbols()` for the first `SymbolKind::Schema` symbol whose table name (the part after `<schema-file>::`, via `table_name_of`) equals `table`, then returns its `SymbolId`. `None` when there's no matching `CREATE TABLE` — a database view, an RPC name, or a typo. As M10's validation frames it, this is a "resolves to a plausible candidate" bar, not a correctness guarantee; a schema with two same-named tables in different schemas would match whichever comes first.

## `walk_for_jsx`
`fn walk_for_jsx(node: Node, source: &str, out: &mut BTreeSet<String>)`
### Summary
The recursive tree-sitter visitor behind `extract_rendered_components` — collects the name of every uppercase-initial JSX element tag into a set.
### Behavior
At a `jsx_opening_element` or `jsx_self_closing_element`, it takes the first child of kind `identifier` as the tag name and inserts it if the first character is ASCII uppercase. ## `is_colocated`
`fn is_colocated(component_file: &str, entry_file: &str) -> bool`
### Summary
Whether a component file lives in the entry point's own directory subtree — the other way (besides doing data work) a rendered component joins a feature's `core`.
### Behavior
Takes the entry file's directory (everything before its last `/`) and returns `true` iff `component_file` starts with that directory plus a trailing slash. So `app/submit/artwork-uploader.tsx` is co-located with `app/submit/page.tsx`; `components/ui/button.tsx` is not. ## `EntryPoint`
`pub struct EntryPoint`
### Summary
One framework-enumerated feature entry point — the thing a feature spec is written about. `kind` names the framework convention it came from, `id` is the unique slug for `docs/specs/_features/<id>.md`, `file` is the source file, `title` is the human label rendered in the document.

## `FeatureModel`
`pub trait FeatureModel: Send + Sync`
### Summary
The pack-owned answer to "what is a feature" for a stack that has runtime entry points. A stack with none (a CLI, a library) returns `None` from `StackPack::feature_model` and never constructs this — its corpus is symbol / file / rollup / system specs only.
### Behavior
Two methods, deliberately minimal (design decision 8 — a second impl doesn't arrive until M17). `enumerate_entry_points` lists every entry point the framework's file or annotation conventions expose in the graph. `admits_to_core` decides, for a `candidate_file` reached from an entry by a resolved flow edge, whether it belongs *inside* the feature (tracked by `source_hash`, so a body change is a feature change) or stays a one-hop dependency (`interface_hash`). These are the only two judgments the otherwise-generic `assemble_participants` walk can't make itself — where an edge points is `StackPack::resolve_flow_edge`, everything else is mechanical. `Send + Sync` because a feature model is a stateless ZST shared across the server.

- `src/graph.rs::Graph` — crate::graph

## `impl FeatureModel for TypeScriptNextFeatureModel`
`impl FeatureModel for TypeScriptNextFeatureModel`
### Summary
The Next.js implementation of the two `FeatureModel` judgments — enumerating page and orphan-API-route entry points, and deciding which reached files join a feature's `core`.
### Behavior
`enumerate_entry_points` first collects the set of API-route files that some `route-literal` flow edge resolves to (the "targeted" set). It then emits an `EntryPoint { kind: "page" }` for every `is_page` file, followed by an `EntryPoint { kind: "api-route" }` for every `is_api_route` file *not* in the targeted set — a route with no page calling it (a webhook, a cron target) is a feature in its own right; one that a page fetches is folded into that page's feature instead. Slugs come from `feature_slug`, titles from `entry_route_path`.

`admits_to_core` is called by the generic walk for every resolved file edge. It admits the candidate if it's an API route (`route-literal` targets are always `app/api/**/route.ts`, so this reproduces M11's "route targets join unconditionally"), or it's co-located with the entry point's directory, or it does data work. Component targets (`.tsx`) therefore fall through to exactly the co-location / data-work test M11 defined.

## `Participants`
`pub struct Participants`
### Summary
A feature's participant set, split into three tiers: `core` (the feature's own code — entry point plus what it reaches through flow edges the pack admits), `dependencies` (the symbols that core code imports directly), and `data` (the SQL tables the core code queries via a resolved `.from("table")`).
### Behavior
Plain vecs of string ids. The tiers differ in how staleness is tracked: `core` and `data` key on `source_hash` (a body change, or a schema change to a touched table, is a real change to the feature), while `dependencies` key on `interface_hash` (only a public-surface change matters, same as any reference edge). `dependencies` and `data` are one hop only — never expanded further — mirroring the containment-only recursion invariant for reference edges. Produced by `assemble_participants`; consumed by `next_feature_task` (to build the generation context) and `current_participant_hashes` (to detect staleness).
### Depends on
- (none)

## `assemble_participants`
`pub fn assemble_participants(
    graph: &Graph,
    fm: &dyn FeatureModel,
    entry: &EntryPoint,
) -> Participants`
### Summary
Walks the feature rooted at an entry point and produces its `Participants` (`core` / `dependencies` / `data`). Stack-generic: it follows `flow_edges` and one-hop imports off the graph and never names a framework convention — the `FeatureModel` makes the two judgments it can't.
### Behavior
`core` is built by BFS from `entry.file`: dequeue a file, add it to `core`, then for each of its flow edges that resolves to a *file* node, enqueue that file iff `fm.admits_to_core` says yes (a `seen` set prevents cycles and rework). An edge that resolves to a *symbol* rather than a file is skipped here — that's the `data` tier. After `core` is closed: `dependencies` is every resolved import target of a `core` file that isn't itself in `core`, deduped, in discovery order. `data` is every flow edge from a `core` file resolving to a symbol (for the TS+SQL pack, a `.from("table")` landing on a `SymbolKind::Schema` node), deduped and sorted for a deterministic hash. The walk stays one hop past `core` for both `dependencies` and `data` — it never recurses into the rest of the graph.
### Depends on
- `src/graph.rs::FlowTarget` — crate::graph
- `src/graph.rs::Graph` — crate::graph
- externals: std, tree_sitter
