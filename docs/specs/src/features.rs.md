# src/features.rs
> Generated by [CodeOwl](https://github.com/siddswork/codeowl)
## Summary
This file is the generic half of the feature layer: it knows what a feature is in the abstract and how to assemble one, but nothing about any particular framework. A feature is a framework entry point plus what it reaches. `EntryPoint` names one (its kind, a unique id that becomes the spec filename, a title, and the file it starts in). `FeatureModel` is the interface a language pack implements to say what its framework's entry points are and which reached files belong inside a feature; the Next.js model lives in the TypeScript pack, and the Quarkus and FastAPI models in the Java and Python packs. `feature_model_for` recovers the model of the stack that built a graph (none for a stack with no runtime entry surface such as a command-line tool, so it has no feature specs at all), and `enumerate_entry_points` wraps it, giving an empty list when there is no model. `assemble_participants` is the framework-neutral walk: from the entry file it follows resolved flow edges and imports breadth first, asks the model whether each reached file belongs in the feature's own code, and sorts everything else into one-hop dependencies or data tables, so the result is three tiers (`core`, `dependencies`, `data`) in a `Participants` value. Core files are tracked by their whole source hash, dependencies by their public shape, and data by its source hash, so a body change to a core file changes the feature while only a public-surface change to a dependency does. A file that declares tables never also becomes core, and only resolved edges are followed, so an unresolved call adds nothing. `feature_slug` turns a route path into a filename-safe slug (`app/submit/page.tsx` becomes `submit`, the root page becomes `home`, folders join with hyphens); it is written for the Next.js layout even though it sits in the generic layer. A test-only `fixture` helper builds a real graph from a few files in a temp directory for this file's tests and the packs' feature tests. The layer is deliberately narrow and is not general call-graph analysis, which stays deferred.

## `EntryPoint`
`pub struct EntryPoint`
### Summary
One entry point a framework's own conventions expose — a page, an API route, an HTTP resource, a scheduled job, whatever a given stack's `FeatureModel` knows how to recognize. This is the thing a feature spec gets generated for.
### Behavior
`kind` names the framework convention this entry point came from (`"page"` / `"api-route"` for Next.js; other stacks add their own kinds like `"http"` or `"kafka"`), letting `enumerate_entry_points` return a mixed list spanning several conventions at once. `id` is the unique slug that names the resulting spec file (`docs/specs/_features/<id>.md`) — it must not collide across different `kind`s from the same stack; where a stack's entry-point path spaces overlap, its `FeatureModel` prefixes `id` with `kind` to keep them distinct. `title` is the human-facing label rendered inside the generated document. `file` is the entry point's own source file.

## `FeatureModel`
`pub trait FeatureModel: Send + Sync`
### Summary
The interface a language or framework supplies to say what a "feature" is in its codebase, such as a page or an API route in Next.js, or an HTTP endpoint in a Java service. A stack with nothing like that, such as a command-line tool or a library, simply provides none.
### Behavior
Two methods are required, and the trait must be safe to share across threads. `enumerate_entry_points(graph)` returns every feature entry point the framework's file or annotation conventions expose in the graph. `admits_to_core(graph, entry, candidate_file)` is asked about a file reached from an entry point by a resolved flow edge into a file node, and answers whether that file belongs inside the feature's core (tracked by its whole `source_hash`, so any edit to it changes the feature) or is merely a one-hop dependency (tracked by its public shape, the `interface_hash`). Those two judgments are the only ones the generic walk in `assemble_participants` cannot make itself; where a flow edge points is decided separately by the pack's flow-edge resolution. A stack without such a model returns none from its pack, and its documents are symbol, file, folder and system specs only. The trait is deliberately kept to these two methods.

## `feature_model_for`
`pub fn feature_model_for(graph: &Graph) -> Option<&'static dyn FeatureModel>`
### Summary
Returns the feature model for the language stack a repo was indexed with, or nothing if that stack has no concept of features, as is the case for a command-line tool or a library.
### Behavior
Recovers the pack from the graph through `stack::for_graph` and returns whatever that pack's `feature_model()` gives: a shared reference valid for the whole program, or `None`. Doing the lookup from the graph means read-only callers such as the spec code do not need the pack passed down to them. A graph with an empty pack name (one built by a test helper, or an old cache) gets the TypeScript pack, so it gets the Next.js feature model; a non-empty name that is not a registered pack is not tolerated, and `for_graph` panics on it rather than guessing. Only the Rust pack returns `None`; Java and Python always return a model, which for a plain Java library simply finds zero entry points, so a `Some` result does not mean any feature exists. Callers treat `None` as "this repo has no feature layer" and skip feature work entirely.

## `Participants`
`pub struct Participants`
### Summary
Everything a feature spec is written from, split into three tiers by how directly each piece belongs to the feature and how its own staleness gets tracked.
### Behavior
`core` is the feature's own code: the entry point plus everything it reaches through the feature's own edges (a rendered component, a route literal it calls). Core files are tracked by `source_hash` — any real edit to their body is treated as a real change to the feature, since this is the code the feature spec is actually describing.

`dependencies` are the symbols that core code imports directly — tracked by `interface_hash` instead, the same as any other reference edge elsewhere in CodeOwl, since only a change to a dependency's public surface (not its internal implementation) should make the feature spec stale.

`data` are the SQL tables the core code queries via a resolved `.from("table")` call — tracked by `source_hash`, so a schema change to a table this feature touches (a column added or removed) makes the feature spec stale too.

`dependencies` and `data` are deliberately one hop only, never expanded further: a feature spec consumes what it directly depends on, it doesn't recursively pull in the rest of the graph behind those dependencies. This mirrors the same one-hop discipline CodeOwl's recursive spec generation applies to containment edges, just applied here to reference edges instead.

## `assemble_participants`
`pub fn assemble_participants(
    graph: &Graph,
    fm: &dyn FeatureModel,
    entry: &EntryPoint,
) -> Participants`
### Summary
Works out everything that belongs to one feature: the files that make up its own code, the pieces of other code it leans on, and the database tables it touches. It is what lets a feature description cover more than the single page or route file where the feature starts.
### Behavior
The walk is generic and never names a framework. It asks the feature model (`fm`) for the one judgment it cannot make itself, namely whether a reached file belongs inside the feature.

First it groups the graph's flow edges and resolved imports by the file they start from, once, so the passes below don't rescan the full lists. It also collects, once, every file that declares at least one table symbol.

Core: a breadth-first walk starts at the entry file. Each file taken joins `core` (a file already seen is skipped, which also ends cycles). From it the walk follows every resolved flow edge and every resolved import, flow targets first. A target that is a file node is used as is, and a target that is a symbol is replaced by the file containing it, so writing the same dependency as a module import or as one named import ends up classified the same way. A candidate file is skipped if it is already seen or if it declares any table (those files belong in `data`, and must not also become `core`, which would hide their tables, for example a models file that holds both a table class and plain request classes). Otherwise `fm.admits_to_core` decides, and a file that passes is queued. That answer is cached per candidate, because several core files often reach the same file and the model's check can be a full graph scan.

Dependencies and data: after the walk, every import and then every flow edge from a `core` file that resolves to a symbol is classified. A symbol whose file is already in `core` is skipped, since that code is fully tracked already. A table symbol goes to `data`, anything else to `dependencies`, each de-duplicated. Imports and flow edges that resolve to a whole file are skipped here, since such a file either joined `core` or was judged not part of the feature, so a rejected file leaves no trace in the participants (it still shows in `get_callers`). Unresolved targets are ignored throughout.

The result is `Participants`: `core` in walk order with the entry file first, `dependencies` in discovery order, and `data` sorted. It cannot fail, and the walk terminates because each file is visited once. The limit to know: only edges that resolved are followed, so a call through an unresolved import or an unresolvable route string adds nothing to the feature.
