# src/features.rs
## Summary
This file implements the "feature" layer, the part of CodeOwl that groups code around the things a person actually uses (a page, an API route) instead of just around folders. It looks past plain declarations and import statements into a few narrow patterns: a `fetch("/api/...")` call that names an API route by its literal path, a `.from("table")` call that names a database table, and a `<Component/>` tag matched back to the import that brought it in. Resolving those to the real files and tables is what lets a feature's description include code that following imports alone would never reach. Most of the file is generic. `assemble_participants` walks the graph's flow edges and one-hop imports to build a feature's full set of core files, supporting symbols and tables, the same way for any framework. The framework-specific part is behind the `FeatureModel` interface, implemented here once by `TypeScriptNextFeatureModel`, which says what a feature is in a Next.js project (a page, or an API route no page calls) and which reached files belong inside it. A stack with no features, such as a command-line tool, supplies no model, so `feature_model_for` and `enumerate_entry_points` give nothing for it.

## `RouteLiteral`
`pub struct RouteLiteral`
### Summary
One `fetch("/api/...")` call found anywhere in a file's client code — the raw evidence CodeOwl uses to connect a page to the API route it actually calls, since that connection is a string match, not an `import`.
### Behavior
`from_file` is the file the call was found in. `static_path` is the matched path, already stripped of any query string and guaranteed to start with `/api/`. The search isn't limited to top-level code — these calls are almost always inside an event handler or a `useEffect`, so the whole file is scanned regardless of nesting. `RouteLiteral`s are persisted on the `Graph` itself (the same way a `ResolvedImport` is) so that `get_next_spec_task` doesn't have to re-walk every file's syntax tree (the structure `tree-sitter` produces from the source text) on every call — they're computed once and read back out.
### Depends on
- (none)

## `extract_route_literals`
`pub fn extract_route_literals(source: &str, rel_path: &str) -> Vec<RouteLiteral>`
### Summary
The per-file pass that finds every `fetch("/api/...")` string-literal call in a TypeScript source, producing the `RouteLiteral`s that become client→API-route flow edges.
### Behavior
Parses the file with `ts_parser` (returning an empty vec on a parse failure), then hands the whole tree to `walk_for_fetch` for a full recursive descent — deliberately not the shallow top-level walk `extract.rs` uses, since a `fetch` call is almost always buried inside a handler or effect. Only `fetch(<string literal>)` forms are matched; a `fetch(url)` with a computed argument produces nothing. Runs once per file at index time; the results are cached on `Graph`.
### Depends on
- `src/lang.rs::ts_parser` — crate::lang

## `walk_for_fetch`
`fn walk_for_fetch(node: Node, source: &str, rel_path: &str, out: &mut Vec<RouteLiteral>)`
### Summary
The recursive tree-sitter visitor behind `extract_route_literals` — checks whether a node is a `fetch(<literal>)` call and recurses into every child.
### Behavior
At each node: if it's a `call_expression` whose `function` field is the bare identifier `fetch` and whose first argument yields a static path via `static_path_from_literal`, a `RouteLiteral` is pushed. The identifier check is literal — `window.fetch(...)` or an aliased `f(...)` is not matched. Then it descends into all children unconditionally, so nesting depth doesn't matter and a file can contribute many literals. Only the *first* argument is inspected; a second `RequestInit` argument is ignored.
### Depends on
- externals: tree_sitter

## `static_path_from_literal`
`fn static_path_from_literal(node: Node, source: &str) -> Option<String>`
### Summary
Extracts a fully-static `/api/...` path from the first argument of a `fetch` call — a plain string, or a template string whose path portion has no interpolation. Returns `None` rather than guess at a partially-dynamic path.
### Behavior
For a `string` node it reads the inner content and defers to `path_from_raw` with `path_complete = true`. For a `template_string` it takes named children only (skipping the backtick tokens); if the first isn't a `string_fragment` it bails. It then decides whether the path is complete: it is if there's no `${...}` substitution at all, *or* if the static fragment already contains a `?` — meaning any later interpolation lands in the query string, which is stripped anyway, not in the path. That completeness flag is passed to `path_from_raw`, which is what actually enforces the `/api/` prefix and drops the query string. Any other node kind → `None`.
### Depends on
- externals: tree_sitter

## `path_from_raw`
`fn path_from_raw(raw: &str, path_complete: bool) -> Option<String>`
### Summary
The final filter turning a raw literal string into an accepted route path: drops the query string, keeps it only if it begins with `/api/`.
### Behavior
Bails immediately (`None`) when `path_complete` is false — the caller has decided an interpolation makes the path unreliable. Otherwise it takes everything before the first `?` and returns `Some(that)` iff it starts with `/api/`. So `/api/submit?x=1` → `Some("/api/submit")`, `/other/thing` → `None`, `https://…` → `None`. The `/api/` gate is what scopes route-literal resolution to Next.js App Router API routes specifically.
### Depends on
- (none)

## `text`
`fn text<'a>(node: Node, source: &'a str) -> &'a str`
### Summary
A local helper: the source substring a tree-sitter node spans, as a borrowed `&str`.
### Behavior
Calls `node.utf8_text` against the source bytes and returns `""` on the (practically impossible, for a tree parsed from valid UTF-8 `&str`) error case rather than propagating it. The same convenience wrapper several other modules define privately; kept per-file to avoid a shared tree-sitter utility crate surface.
### Depends on
- externals: tree_sitter

## `resolve_route_literal`
`pub fn resolve_route_literal(graph: &Graph, static_path: &str) -> Option<SymbolId>`
### Summary
Turns an API path written in code, such as `/api/users/42`, into the route file that handles it, by following the Next.js folder naming convention. It is how a page's `fetch("/api/...")` call is connected to the server code behind it.
### Behavior
Strips a leading `/api/` from the path and splits the rest on `/`, dropping empty pieces. It then looks through the repo's files for one whose own route path (from `api_route_segments`, which only recognises `app/api/.../route.ts`-style files) has the same number of pieces and where each piece either is a dynamic segment (`[id]`, `[...slug]`, which matches any value) or equals the corresponding piece exactly. The first such file is returned as its arena id. There is no prefix or fuzzy matching: the counts must be equal, so an incomplete path never matches, and a guard elsewhere (`static_path_from_literal`) keeps incomplete paths from reaching here. If no file matches it returns `None`. Pure read.
### Depends on
- `src/graph.rs::Graph` — crate::graph
- `src/symbol.rs::SymbolId` — crate::graph

## `api_route_segments`
`fn api_route_segments(file_id: &str) -> Option<Vec<&str>>`
### Summary
Given a repo-relative file path, returns its API-route path segments if it *is* a Next.js App Router API route file — `app/api/<segments>/route.ts` — or `None` otherwise.
### Behavior
Requires both the `app/api/` prefix and the `/route.ts` suffix; either missing → `None`. The middle is split on `/` into borrowed segments, dynamic markers (`[id]`) included verbatim. Only `route.ts` is recognised, not `route.tsx` or `route.js` — a Phase-1 narrowing. This is the candidate-side half of `resolve_route_literal`'s match.
### Depends on
- (none)

## `is_dynamic_segment`
`fn is_dynamic_segment(seg: &str) -> bool`
### Summary
Whether a route path segment is a Next.js dynamic placeholder — `[id]`, `[slug]`, `[...rest]` — which matches any literal segment during route resolution.
### Behavior
A bracket check: `true` iff the segment starts with `[` and ends with `]`. It doesn't distinguish single (`[id]`) from catch-all (`[...slug]`) forms — both are treated as "matches one literal segment", which is why `resolve_route_literal` also enforces an exact segment count and a true catch-all route wouldn't resolve a multi-segment path. Adequate for the routes in the pilot repo.
### Depends on
- (none)

## `TableRef`
`pub struct TableRef`
### Summary
One `.from("<table>")` call found in application code — the Supabase/PostgREST convention for naming which database table a query runs against, since that's also a string reference rather than anything an `import` can resolve.
### Behavior
`from_file` is the file the call was found in; `table` is the table name matched inside the `.from(...)` call. Like `RouteLiteral`, these are stored on the `Graph` rather than re-derived per lookup, and get resolved against the schema nodes `schema.rs` extracts from `CREATE TABLE` statements — a `TableRef` whose `table` matches an extracted schema node becomes the flow edge that lets `get_callers` on a table answer "what app code actually touches this."
### Depends on
- (none)

## `extract_table_refs`
`pub fn extract_table_refs(source: &str, rel_path: &str) -> Vec<TableRef>`
### Summary
The per-file pass that finds every `.from("<table>")` member call in a TypeScript source, producing the `TableRef`s that become code→table flow edges (M10).
### Behavior
Parses with `ts_parser` (empty vec on parse failure), then `walk_for_from` descends the whole tree. Deliberately narrow: the argument must be a single plain string literal shaped like a table name (`[a-z_][a-z0-9_]*`), which is what rules out `Array.from(...)` / `Buffer.from(...)` and any `.from(tableVar)`. An ORM-aware matcher (`db.payments`, `Payment.findMany`) is out of scope for Phase 1.
### Depends on
- `src/lang.rs::ts_parser` — crate::lang

## `walk_for_from`
`fn walk_for_from(node: Node, source: &str, rel_path: &str, out: &mut Vec<TableRef>)`
### Summary
The recursive tree-sitter visitor behind `extract_table_refs` — recognises a `<receiver>.from("table")` call and recurses into every child.
### Behavior
A node contributes a `TableRef` only if all of: it's a `call_expression`; its function is a `member_expression` whose property is `from`; the receiver is not a known builtin (`is_builtin_from_receiver` filters `Array`/`Object`/`Buffer`); there is exactly one argument (`named_child(1)` is `None`); that argument is a `string` literal; and its content passes `is_table_name`. The single-argument rule is deliberate — `Array.from(x, fn)` and RxJS `from(a, b)` are excluded even if they somehow slipped past the receiver check. Then it descends into all children.
### Depends on
- externals: tree_sitter

## `is_table_name`
`fn is_table_name(s: &str) -> bool`
### Summary
Whether a string looks like a SQL table identifier — `[a-z_][a-z0-9_]*` — the shape check that keeps `.from("...")` extraction from picking up arbitrary string arguments.
### Behavior
Non-empty, first character an ASCII lowercase letter or underscore, every character lowercase / digit / underscore. Rejects uppercase (`.from("SomeClass")`), paths (`.from("./x")`), URLs, and anything with a dot or dash. Intentionally strict — a schema that uses mixed-case or quoted identifiers would be missed, which is acceptable for the Supabase/Postgres convention this targets.
### Depends on
- (none)

## `is_builtin_from_receiver`
`fn is_builtin_from_receiver(member: Node, source: &str) -> bool`
### Summary
Heuristic that rejects a `.from(...)` whose receiver is a global constructor (`Array.from`, `Buffer.from`, `Object.fromEntries`-adjacent) rather than a query builder.
### Behavior
Returns `true` only when the member expression's `object` is a bare `identifier` whose first character is ASCII uppercase. The reasoning: a Supabase/query-builder receiver is always a lowercase-initial variable (`supabase`, `db`) or a call expression (`createClient().from(...)`), so an uppercase-initial identifier is a reliable tell for a builtin. A receiver that's a member access or call is *not* flagged here — it's assumed to be a real query builder.
### Depends on
- externals: tree_sitter

## `resolve_table_ref`
`pub fn resolve_table_ref(graph: &Graph, table: &str) -> Option<SymbolId>`
### Summary
Finds the database table definition that a table name written in code refers to, so a `.from("payments")` query can be linked to the `CREATE TABLE` it targets.
### Behavior
Searches every symbol in the graph for one of kind `Schema` (a table produced by schema extraction) whose table name, taken from the end of its id with `table_name_of`, equals the given name exactly, and returns its arena id. The first match wins. If nothing matches it returns `None`, which happens for a database view, a typo, or a table created outside the indexed schema files. The match is by name only, so a name that happens to be defined in two schema files resolves to whichever comes first. It only reports a plausible candidate, not a guarantee that the query really targets it.

- `src/graph.rs::Graph` — crate::graph
- `src/symbol.rs::SymbolId` — crate::graph

## `walk_for_jsx`
`fn walk_for_jsx(node: Node, source: &str, out: &mut BTreeSet<String>)`

## `is_colocated`
`fn is_colocated(component_file: &str, entry_file: &str) -> bool`
### Summary
Whether a component file lives in the entry point's own directory subtree — the other way (besides doing data work) a rendered component joins a feature's `core`.
### Behavior
Takes the entry file's directory (everything before its last `/`) and returns `true` iff `component_file` starts with that directory plus a trailing slash. So `app/submit/artwork-uploader.tsx` is co-located with `app/submit/page.tsx`; `components/ui/button.tsx` is not. ## `EntryPoint`
`pub struct EntryPoint`
### Summary
One entry point a framework's own conventions expose — a page, an API route, an HTTP resource, a scheduled job, whatever a given stack's `FeatureModel` knows how to recognize. This is the thing a feature spec gets generated for.
### Behavior
`kind` names the framework convention this entry point came from (`"page"` / `"api-route"` for Next.js; other stacks add their own kinds like `"http"` or `"kafka"`), letting `enumerate_entry_points` return a mixed list spanning several conventions at once. `id` is the unique slug that names the resulting spec file (`docs/specs/_features/<id>.md`) — it must not collide across different `kind`s from the same stack; where a stack's entry-point path spaces overlap, its `FeatureModel` prefixes `id` with `kind` to keep them distinct. `title` is the human-facing label rendered inside the generated document. `file` is the entry point's own source file.
### Depends on
- (none)

## `FeatureModel`
`pub trait FeatureModel: Send + Sync`
### Summary
The interface a language or framework supplies to say what a "feature" is in its codebase, such as a page or an API route in Next.js, or an HTTP endpoint in a Java service. A stack with nothing like that, such as a command-line tool or a library, simply provides none.
### Behavior
Two methods are required, and the trait must be safe to share across threads. `enumerate_entry_points(graph)` returns every feature entry point the framework's file or annotation conventions expose in the graph. `admits_to_core(graph, entry, candidate_file)` is asked about a file reached from an entry point by a resolved flow edge, and answers whether that file belongs inside the feature's core (tracked by its whole `source_hash`, so any edit to it changes the feature) or is merely a one-hop dependency (tracked by its public shape only). Those two judgments are the only ones the generic walk in `assemble_participants` cannot make itself; where a flow edge points is decided separately by the pack. A stack without such a model returns no feature model, and its documents are file, folder and system specs only. The trait is deliberately kept to these two methods.
### Depends on
- `src/graph.rs::Graph` — crate::graph

## `TypeScriptNextFeatureModel`
`pub struct TypeScriptNextFeatureModel`
### Summary
Defines what counts as a "feature" in a Next.js project using the App Router: each page, plus any API route that no page refers to, becomes a feature, and the components and API routes a page uses are pulled into it.
### Behavior
`enumerate_entry_points` builds the list in two parts. First, it collects the files that are the target of a resolved `route-literal` flow edge, meaning an API route that some code calls. Then, every file that `is_page` becomes an entry of kind `page`. Every file that `is_api_route` and is not in that targeted set is added as kind `api-route`, so an API route that a page already calls is not a feature of its own but part of that page's feature. Each entry gets its slug from `feature_slug`, its title from the route path (`entry_route_path`), and its file.

`admits_to_core` is asked about each file reached from an entry through a resolved edge. It returns true if the file is an API route, or sits next to the entry file (`is_colocated`), or does data work (`file_does_data_work`: it calls an API route or queries a table). Otherwise the file is only a one-hop dependency. An API route is always admitted, which reproduces the older rule that route-literal targets join the feature unconditionally. Rendered components, which are `.tsx` files, fall through to the co-location and data-work tests. The struct has no fields.
### Depends on
- `src/graph.rs::FlowTarget` — crate::graph
- `src/graph.rs::Graph` — crate::graph
- externals: std, tree_sitter

## `Participants`
`pub struct Participants`
### Summary
Everything a feature spec is written from, split into three tiers by how directly each piece belongs to the feature and how its own staleness gets tracked.
### Behavior
`core` is the feature's own code: the entry point plus everything it reaches through the feature's own edges (a rendered component, a route literal it calls). Core files are tracked by `source_hash` — any real edit to their body is treated as a real change to the feature, since this is the code the feature spec is actually describing.

`dependencies` are the symbols that core code imports directly — tracked by `interface_hash` instead, the same as any other reference edge elsewhere in CodeOwl, since only a change to a dependency's public surface (not its internal implementation) should make the feature spec stale.

`data` are the SQL tables the core code queries via a resolved `.from("table")` call — tracked by `source_hash`, so a schema change to a table this feature touches (a column added or removed) makes the feature spec stale too.

`dependencies` and `data` are deliberately one hop only, never expanded further: a feature spec consumes what it directly depends on, it doesn't recursively pull in the rest of the graph behind those dependencies. This mirrors the same one-hop discipline CodeOwl's recursive spec generation applies to containment edges, just applied here to reference edges instead.
### Depends on
- (none)

## `assemble_participants`
`pub fn assemble_participants(
    graph: &Graph,
    fm: &dyn FeatureModel,
    entry: &EntryPoint,
) -> Participants`
### Summary
Works out everything that belongs to one feature: the files that make up its own code, the pieces of other code it leans on, and the database tables it touches. It is what lets a feature description cover more than the single page or route file where the feature starts.
### Behavior
The walk is generic and never names a framework. It asks the feature model (`fm`) for the one judgment it cannot make itself, namely whether a reached file belongs inside the feature.

First it groups the graph's flow edges and resolved imports by the file they start from, once, so the passes below don't rescan the full lists.

Core: a breadth-first walk starts at the entry file. Each file taken joins `core`. From it the walk follows every resolved flow edge and every resolved import. A target that is a file node is used as is, and a target that is a symbol is replaced by the file containing it, so writing the same dependency as a module import or as one named import ends up classified the same way. A candidate file is skipped if it is already seen or if it declares any table (those files belong in `data`, and must not also become `core`, which would hide their tables). Otherwise `fm.admits_to_core` decides, and a file that passes is queued. That answer is cached per candidate, because several core files often reach the same file and the model's check can be expensive.

Dependencies and data: after the walk, every import and every flow edge from a `core` file that resolves to a symbol is classified. A symbol whose file is already in `core` is skipped, since that code is fully tracked already. A table symbol goes to `data`, anything else to `dependencies`, each de-duplicated. Imports that resolve to a whole file are skipped here, since such a file either joined `core` or does no data work. Unresolved targets are ignored throughout.

The result is `Participants`: `core` in walk order, `dependencies` in discovery order, and `data` sorted. It cannot fail, and the walk terminates because each file is visited once.
### Depends on
- `src/graph.rs::FlowEdge` — crate::graph
- `src/graph.rs::FlowTarget` — crate::graph
- `src/graph.rs::Graph` — crate::graph
- `src/symbol.rs::SymbolId` — crate::graph
- `src/resolve.rs::ResolvedImport` — crate::resolve
- externals: std, tree_sitter
