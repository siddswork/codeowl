# src/imports.rs
## Summary
The TypeScript import reader: it parses one file and lists where its code comes from, which is the raw input for linking files to one another. It runs as its own tree-sitter pass, separate from the declaration extractor, so each stays single-purpose, and parsing a small file twice costs next to nothing. The result for a file is a `FileImports` with four lists: named imports (`import { a } from './x'`), re-exports (names a file forwards, such as `export { a } from './x'`, or a local `export { a }` of something it imported), default imports (`import Foo from './x'`), and qualified references, which the TypeScript pass never fills but the Rust and Java packs do. Named forms resolve to a specific symbol later, default imports only to a file, and the file-level reason for tracking those is to trace a rendered `<Component/>` back to its source. Namespace imports (`import * as ns`) and wildcard re-exports (`export * from`) are deliberately not tracked, since neither names one declaration. Small helpers read names out of export clauses and import lists, and are shared with the declaration extractor so both read an `export { ... }` line the same way. Everything here is specific to TypeScript; other languages have their own import readers.

## `ImportRef`
`pub struct ImportRef`
### Summary
One named `import` statement as extracted from a file's source, before it's been resolved to an actual target — the raw shape of `import { <imported_name> } from '<specifier>'`.
### Behavior
`specifier` is the module string as written (`'./graph'`, `'@/lib/utils'`). `imported_name` is the name being imported. A local alias (`import { Foo as Bar }`) is deliberately not tracked here: renaming on import is purely local to the importing file and has no bearing on what the import actually resolves to, so keeping it would add a field nothing downstream needs.

## `ReExport`
`pub struct ReExport`
### Summary
One named re-export — how a barrel file (a file whose only job is to gather and forward names from other files, without declaring anything itself) passes along a name it doesn't own: `export { <source_name> as <exported_as> } from '<specifier>'`.
### Behavior
`specifier` is the module the name is being forwarded from. `source_name` is that name as declared in the source module; `exported_as` is the name this file re-exports it under (identical to `source_name` when there's no `as` rename). Resolving an import against a barrel means following its `ReExport`s through to wherever `source_name` is actually declared, rather than stopping at the barrel file itself.

- (none)

## `DefaultImport`
`pub struct DefaultImport`
### Summary
One default import: `import <local_name> from '<specifier>'` (or the default half of `import <local_name>, { ... } from '<specifier>'`). Tracked specifically so a rendered `<Component/>` tag can be resolved to the file it came from — React components are almost always default-exported, so the named-import list alone can't answer "what file defines this component."
### Behavior
`local_name` is the name this file calls the import by; `specifier` is the module string it came from. Resolution here is deliberately file-level only — it answers "which file does this default import point at," not "which specific symbol in that file," since a default export doesn't have a name of its own to match against the way a named import does. See `resolve::resolve_default_imports` for how this gets turned into an actual file target.

## `FileImports`
`pub struct FileImports`
### Summary
Everything a single file says about where it gets code from: its named imports, the names it forwards from other files, its default imports, and any fully-spelled-out references that need no import line at all.
### Behavior
Four lists. `imports` holds named imports. `re_exports` holds names the file forwards from elsewhere, which is how a barrel file (one that only re-exports) passes a name along. `default_imports` holds `import Name from './x'` forms. `qualified_refs` holds references written with their full path and no `use` or `import` statement, such as Rust's `crate::a::b::Item` or a Java fully-qualified class name. These are kept apart from `imports` on purpose: Java's same-package scan treats an explicit import of a simple name as hiding a same-package guess for that name, and a fully-qualified reference to a different type of the same name, as with two distinct `Fight` classes, must not trigger that hiding. TypeScript and Python never fill `qualified_refs`, because their module systems have no way to reach another module without naming it. `default_imports` and `qualified_refs` default to empty when absent from older cached data. Plain data, no logic.

- (none)

## `extract_imports`
`pub fn extract_imports(source: &str, rel_path: &str) -> FileImports`
### Summary
Reads a TypeScript or JavaScript file and lists what it imports and what it forwards from other files. It is the first step in connecting files to one another.
### Behavior
Parses the source with tree-sitter, using the grammar for the file's extension. If parsing produces no tree it returns an empty `FileImports`. Only the file's top-level statements are examined. An `import` statement goes to `visit_import`, which records named and default imports. An `export` statement goes to `visit_maybe_reexport`, which records `export { x } from './y'` forms. After that, `visit_bare_reexports` handles the other kind of re-export, a local `export { X }` clause that names something the file imported earlier. Anything nested deeper, such as a dynamic `import()` call, is not looked at. It cannot fail.
### Depends on
- `src/lang.rs::ts_parser` — crate::lang

## `ExportSpec`
`pub(crate) struct ExportSpec<'a>`
### Summary
One name listed inside an `export { ... }` clause, with the different public name it is published under if it is renamed.
### Behavior
`name` is the name as written first, such as `a` in `export { a as b }`, and `alias` is the published name (`b`) when there is one. An alias identical to the name, as in `export { a as a }`, is not a rename, so `alias` is `None` for it. Both fields borrow text from the source being parsed, so the struct only lives as long as that text and is used within a single parse. It is visible within the crate only and produced by `export_specs`.

## `export_specs`
`pub(crate) fn export_specs<'a>(clause: Node, source: &'a str) -> Vec<ExportSpec<'a>>`
### Summary
Reads the list of names inside one `export { ... }` clause and returns them in the order written. It is the single place that knows how such a clause is laid out, so the import code and the symbol extractor read it the same way.
### Behavior
Walks the direct children of the clause node and keeps only those of kind `export_specifier`. For each, it reads the `name` field and the `alias` field as text. A specifier with no readable name is skipped. The alias is dropped to `None` when it equals the name, so `export { a as a }` is not seen as a rename. Each result is an `ExportSpec` borrowing from the source. The order matches the source. A clause with no specifiers gives an empty list. It cannot fail.
### Depends on
- externals: tree_sitter

## `bare_export_clause`
`pub(crate) fn bare_export_clause<'t>(stmt: Node<'t>) -> Option<Node<'t>>`
### Summary
Picks out the braces part of a local export line such as `export { X, Y as Z }`, where there is no `from` and so the names refer to things defined or imported in this same file.
### Behavior
Returns `None` unless the statement is an `export_statement` with no `source` field, meaning no `from '...'`. That excludes `export { X } from './y'`, which re-exports another module's name and says nothing about a local one, and also excludes `export function f() {}`, which has no clause. Otherwise it returns the statement's `export_clause` child, or `None` if it has none. It is the shared test used both when collecting re-exports of earlier imports and when marking local declarations as exported. The returned node is tied to the parse tree it came from, so it must be used before that tree is dropped. It cannot fail.
### Depends on
- externals: tree_sitter

## `named_import_specs`
`fn named_import_specs<'a>(named: Node, source: &'a str) -> Vec<(&'a str, &'a str)>`
### Summary
Reads the `{ ... }` part of an import line and returns, for each name, what it is called in the other file and what it is called here. For `import { a as b, c } from './m'` that gives `(a, b)` and `(c, c)`.
### Behavior
Walks the direct children of the named-imports node and keeps those of kind `import_specifier`. For each, the source-module name is the `name` field, and the local name is the `alias` field if present, otherwise the same as the name. A specifier whose name cannot be read is skipped. The pairs come back in source order, borrowed from the source text. An empty braces list gives an empty vector. It is shared by `visit_import` and by `visit_bare_reexports`, which needs the same local-to-source name mapping to resolve re-exports of imported names. It cannot fail.
### Depends on
- externals: tree_sitter

## `visit_import`
`fn visit_import(node: Node, source: &str, out: &mut FileImports)`
### Summary
Records what one `import` statement brings in: a default import, named imports, or both. A statement that imports nothing by name is ignored.
### Behavior
Gets the module specifier from the statement's `source` string (quotes removed) and returns if there is none. If there is no import clause, as in a side-effect-only `import './polyfill'`, it returns without recording anything. If the clause has a plain identifier directly under it, that is the default binding: it covers `import Foo from ...` and the `Foo` in `import Foo, { Bar } from ...`, and is pushed as a `DefaultImport` with its local name and specifier. A namespace import (`import * as ns`) is a different child kind and is deliberately skipped. If there is a named-imports part, each name goes through `named_import_specs` and a `ImportRef` with the specifier and the name as it appears in the other module is pushed. The local alias is not stored, because resolution is by the original name. It cannot fail.
### Depends on
- externals: tree_sitter

## `visit_bare_reexports`
`fn visit_bare_reexports(root: Node, source: &str, out: &mut FileImports)`
### Summary
Catches the case where a file imports a name and then passes it on with a local `export { X }` line, such as `import { X } from './a'; export { X };`. Without it, a file importing `X` from this one would not be traced through to where `X` is really defined.
### Behavior
First it collects the file's bare export clauses (`export { ... }` with no `from`), and returns at once if there are none, which is the common case, so most files never get the extra work. Otherwise it reads the file's imports in a pass of its own, because imports are hoisted and `export { X }` may legally appear before `import { X }`. That pass builds a map from each local name to the module specifier and the name as it is in that module, using `named_import_specs`. Only named imports are tracked, so a default or namespace import that is re-exported is not followed.

Then for each name in each clause, if it matches an imported local name, a `ReExport` is recorded: the published name is the alias if there is one, otherwise the name; the specifier and source name come from the map. This is the same form as `export { original as Y } from '...'`, which resolution already follows. A name the file declares itself is not a re-export, so it is left out and handled by the symbol extractor. Names that are not imported are skipped silently.
### Depends on
- externals: std, tree_sitter

## `visit_maybe_reexport`
`fn visit_maybe_reexport(node: Node, source: &str, out: &mut FileImports)`
### Summary
Records the names a file forwards straight from another module, as in `export { a, b as c } from './m'`. This is how a barrel file (one that only gathers other files' exports) passes names along.
### Behavior
Called on every top-level `export` statement. It returns without recording anything when the statement has no `source` string, because that is an ordinary `export function`, `export class` or `export const`, not a forward. It also returns when there is a source but no export clause, which is the wildcard `export * from '...'`; wildcards are deliberately not followed because they name no single declaration. Otherwise it records one `ReExport` per name in the clause: the published name is the alias if the name is renamed, otherwise the name; the specifier is the module path; and the source name is the original name in that module. The names are read with `export_specs`, so a self-alias `a as a` is treated as no rename. It cannot fail.
### Depends on
- externals: tree_sitter
