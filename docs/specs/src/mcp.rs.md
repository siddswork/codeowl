# src/mcp.rs
## Summary
CodeOwl's MCP interface — every tool a coding agent can call. It has two halves: pure reads (`get_symbol`, `get_callers`, `get_callees`, `get_spec`, `get_spec_coverage`, `search_code`), which never write anything and never call an LLM, and the generation pair (`get_next_spec_task`, `submit_spec`), which hand the client's own LLM a unit of work and store the prose it writes back. `CodeOwlServer` is the server object holding the live graph and repo root; the rest of the file is the request and response shapes each tool takes and returns, plus the `rmcp` wiring that registers them. CodeOwl holds no API credentials and calls no model — a hard rule kept true by every write path here doing nothing but persist text the caller supplied.

## `IdRequest`
`pub struct IdRequest`
### Summary
The request shape for every single-id MCP tool — `get_symbol`, `get_callers`, `get_callees`, `get_spec`. Just a stable symbol/file id string.
### Behavior
One field, `id`. Its doc comment becomes the parameter description in the generated MCP tool schema (via `JsonSchema`), so it's written for the calling agent: `"A symbol's stable id, e.g. \"lib/utils.ts::cn\""`. Also accepts a file path, `feature:<slug>`, `rollup:<dir>`, or `system` where the target tool does.
### Depends on
- (none)

## `SearchRequest`
`pub struct SearchRequest`
### Summary
The request shape for the `search_code` tool — one regex `query` string.
### Behavior
One field. The doc comment is the schema parameter description. The pattern is passed straight to `search::search_code`, which compiles it as a `RegexMatcher` — an invalid regex comes back as a tool error, not a panic.

## `CoverageRequest`
`pub struct CoverageRequest`
### Summary
The request shape for `get_spec_coverage` — an optional `scope` directory prefix.
### Behavior
`scope: None` reports the whole repo. `scope: Some("lib")` narrows the **file and rollup** portion to paths under that prefix; features and the system spec stay repo-wide regardless (they have no directory to scope to). Passed through to `spec::coverage`.

## `CoverageItemResponse`
`pub struct CoverageItemResponse`
### Summary
One entry in `get_spec_coverage`'s `pending` list — a document still needing attention, with its `id` (ready to pass to `get_next_spec_task`), `kind`, `status`, `fan_in`, `smells`, and `generations` cost.
### Behavior
A `CoverageItem` projected for the wire. `status` is only ever `"missing"` / `"stale"` here, or `"current"` when `smells` is non-empty (a hash-current doc a quality check still distrusts). `fan_in` is 0 for non-file kinds. `generations` is this document's share of `--budget=N` — for a file, its uncovered/stale/smelly symbols plus 1 for the file summary; for a rollup/feature/system, 1. `smells` and `generations` are additive fields (M15) that `structural_sweep.py` normalizes away.
### Depends on
- (none)

## `CoverageResponse`
`pub struct CoverageResponse`
### Summary
The full `get_spec_coverage` result: the current / stale / missing / smelly document counts, `generations_remaining` (the real `--budget=N` for a complete pass over the scope), and the priority-ordered `pending` list.
### Behavior
`current` + `stale` + `missing` count *documents* against the granularity-rule inventory (a file with 20 uncovered symbols is still 1 missing document). `generations_remaining` is the sum of every pending item's `generations` — the number that actually sizes a full run. `smelly` counts documents with a quality smell of *any* status, so it isn't exclusive with `current`. `pending` is ordered the way a budgeted `--all` run should spend: high-fan-in files, then features, then the long tail, then rollups, then the system spec.
### Depends on
- (none)

`pub struct CallerInfo`

One entry in a `get_callers` result — a file that references the queried symbol, and the name it imports it under.

Plain data. For a code symbol, `from_file` imports `imported_name` via a resolved `import`/`use` edge. For a SQL table, `from_file` has a `.from("<table>")` call and `imported_name` is the table name. Not a call graph — see `get_callers`.

## `SpecResponse`
`pub struct SpecResponse`
### Summary
The `get_spec` result — the spec's `id`, `status`, deterministic `signature`/`docstring`, the LLM `content`, and the `changed` / `smells` diagnostics.
### Behavior
`status` is `"missing"` / `"current"` / `"stale"`. `content` is `Some` for both `current` and `stale` — the last-known-good text is always served (the read/write split: `get_spec` never triggers generation), `None` only for `missing`, where `signature` + `docstring` still come back as a stub. `changed` names which inputs moved (`"source"`, `"changed:<id>"`, `"added:<id>"`) and is empty unless `stale`. `smells` is the deterministic prose-quality check — non-empty even when `current`, empty when `missing`.
### Depends on
- (none)

## `GenerateTaskRequest`
`pub struct GenerateTaskRequest`
### Summary
The request shape for `get_next_spec_task` — one `target` string.
### Behavior
`target` accepts a file id, a feature entry-point path, a `feature:<slug>` / `rollup:<dir>` id, a directory path with ≥2 spec-bearing files, or `"system"` / `"."` for the whole repo. The handler is stateless — calling it repeatedly with the same target walks that target's bottom-up ladder until `{"kind":"done"}`.

## `DependencyContext`
`pub struct DependencyContext`
### Summary
One reference-edge dependency in a generation task — its id and a one-paragraph `summary`, so the agent can describe how the unit uses it without re-reading its source.
### Behavior
`summary` is the dependency's own `## Summary` if it has a current spec, otherwise a deterministic stub (signature + docstring). Assembling this never triggers the dependency's generation — that's the containment-only recursion rule. Early in a corpus most of these are stubs; they upgrade to real summaries for free as coverage grows.

## `SpecTaskResponse`
`pub enum SpecTaskResponse`
### Summary
The `get_next_spec_task` result — a tagged enum of the six task shapes the generation loop can be handed: `Symbol`, `File`, `Feature`, `Rollup`, `System`, and `Done`.
### Behavior
`Symbol` and `File` are the bottom-up chase — one per uncovered symbol, then the file — each carrying pre-assembled `source` and `dependencies`, plus `prior_*` prose when this is a reconciliation regeneration (M8 case 4). `Feature` / `Rollup` / `System` are one-shot: a single document with a single `spec_hash`, composed from already-generated summaries (never raw source), and only ever offered once everything they compose from is current. Their `id` (`"feature:<slug>"`, `"rollup:<dir>"`, `"system"`) is passed straight back to `submit_spec` and is never a real file/symbol id. `Done` serialises as `{"kind":"done"}` — a real object, not a bare `null` some MCP clients reject — and is the loop's stop signal.
### Depends on
- (none)

## `CodeOwlServer`
`pub struct CodeOwlServer`
### Summary
The MCP server — the object a coding agent talks to. It holds one snapshot of the code graph plus the repo root, and exposes CodeOwl's tools: look up a symbol, list what imports it or what it imports, read or write a spec, report spec coverage, and grep the source.
### Behavior
The graph is stored behind an atomic pointer (`ArcSwap`) so the background file-watcher can swap in a freshly rebuilt one mid-session without any request blocking. Every handler grabs one consistent snapshot up front (`self.graph.load_full()`) and works against that for the whole call — an internal symbol id is only valid for the graph that produced it, so a handler must never straddle a swap.

Read tools:
- `get_symbol` — one symbol's full record by id, or an error for an unknown id.
- `get_callers` — every file that imports this symbol (for a database table: every file that queries it).
- `get_callees` — everything the *file* this symbol lives in imports, with the resolved target where known. File-level, not per-symbol.
- `search` — a plain regex sweep of the source, via `search_code`.
- `get_spec` — the stored prose spec for a symbol / file / `feature:<slug>` / `rollup:<dir>` / `system`, tagged `missing`, `current`, or `stale` (with a `changed` list naming what moved) plus any quality `smells`.
- `get_spec_coverage` — how much of the repo's spec inventory is current vs stale vs missing vs smelly, and a prioritised `pending` list of what to generate next.

Writes all go through `submit_spec`, which dispatches on the id prefix (`system`, `rollup:`, `feature:`, or a plain symbol/file id) to the matching `spec::submit_*` function and returns the new content hashes.

`get_next_spec_task` / `resolve_next_task` walk the generation ladder for a target — a file's uncovered symbols, then the file, then the feature if it's an entry point; a directory's rollup; for `system`, every module and feature then the top-level spec — and return the next unit of work with everything needed to write it (source text, dependency summaries, any prior human edit to reconcile against), or `Done` when the target is fully covered.

`new` constructs the server; `graph_store` hands out the shared graph cell for the watcher to publish into; `root` (test-only) exposes the repo root.
### Depends on
- `src/graph.rs::Graph` — crate::graph
- `src/graph.rs::SymbolView` — crate::graph
- `src/symbol.rs::SymbolKind` — crate::symbol
- externals: arc_swap, rmcp, std

## `impl ServerHandler for CodeOwlServer`
`impl ServerHandler for CodeOwlServer`
### Summary
The `rmcp::ServerHandler` impl — supplies the server's `ServerInfo` (protocol version, capabilities, and the instructions block clients show to the agent). Tool dispatch itself is generated by the `#[tool_router]` / `#[tool_handler]` macros, not written here.
### Behavior
`get_info` builds `ServerInfo` from `Default` and sets its public fields individually (the struct is `#[non_exhaustive]`): `protocol_version` to `LATEST`, `capabilities` to tools-only, and `instructions` to the long prose block that tells a consuming session what each tool is for and that spec *writing* only happens via `/codeowl-generate`. That instructions string is the same text surfaced in this session's system context.
### Depends on
- externals: rmcp
