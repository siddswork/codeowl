# src/rust.rs
## Summary
This file is CodeOwl's Rust language support, the counterpart to the TypeScript extractor. It does two jobs. First, it reads one `.rs` file with tree-sitter (a library that turns source text into a syntax tree) and records its declarations: top-level items, plus one level inside `impl` blocks, traits, inline modules and structs. Functions and macros are callables. Structs, enums, unions, traits, `impl` blocks and modules are containers, and a struct's named fields, constants, statics and type aliases are values. Function bodies, enum variants and a tuple struct's positional fields are deliberately not recorded. Rust splits a type's data (`struct Foo`) from its methods (separate `impl Foo` blocks), but a reader wants one `Foo`, so after the walk every inherent `impl` block is folded back into its type, its methods reparented onto it and its fingerprints combined with the type's. A trait implementation (`impl Trait for Foo`) stays its own symbol, except in one narrow case: a type with no fields, no inherent methods and exactly one trait impl in the file is folded, since otherwise nothing would mark it stale when that impl changes. Each container carries a whole-content fingerprint and a public-surface fingerprint, so a body edit does not mark dependents stale but a changed public signature does. Second, it reads `use` statements, `pub use` re-exports and fully-written `crate::` paths, and resolves them to declarations using Rust's own mapping from module paths to files, including `crate::`, `self::`, `super::`, library crates in the same repo, and one step of re-export. It also adds a link from a trait implementation to its type when both sit in the same file, where no `use` exists to create one.

## `extract_file`
`pub fn extract_file(source: &str, rel_path: &str) -> Vec<ExtractedSymbol>`
### Summary
Reads one Rust file and returns the declarations in it: its top-level items, plus the members one level inside each `impl` block, trait and module. Each type's separate `impl` blocks are folded back into the type so a type reads as one thing.
### Behavior
Creates a tree-sitter parser (a library that turns source text into a syntax tree) with the bundled Rust grammar, and if the text cannot be parsed at all it returns an empty list. It walks the file's top-level items in order, calling `visit_item` for each with no parent. It then finds the top-level types whose fields were not extracted, which the folding step needs to know about, and passes the collected symbols through `merge_inherent_impls`. That step moves the methods from each plain `impl Foo { ... }` block into the symbol for `Foo`, while a trait implementation such as `impl Trait for Foo` stays as its own symbol. The merged list is what it returns. Nothing from the syntax tree escapes the function. Function bodies, and a struct's fields beyond what is recorded as members, are not extracted as separate declarations.

- `src/symbol.rs::ExtractedSymbol` — crate::symbol
- externals: tree_sitter

## `top_level_types_with_unextracted_fields`
`fn top_level_types_with_unextracted_fields(
    root: Node,
    source: &str,
    file: &str,
) -> std::collections::HashSet<String>`
### Summary
Finds the top-level Rust structs that do have fields which CodeOwl does not record as members, namely tuple structs such as `struct UserId(u64);`. It lets the code that merges `impl` blocks tell a struct that truly has no fields from one whose fields were simply not captured.
### Behavior
Looks only at the file's direct top-level items. For each `struct` whose body is an ordered field list, the positional fields of a tuple struct, and which has at least one field and a readable name, it adds the id `<file>::<Name>` to a set. Structs with named fields, and unit structs with no body at all, are not added. The set is returned. It exists because the merge step decides a type has "zero fields" by checking that its children list is empty, and that check cannot otherwise distinguish a genuine marker type from `struct UserId(u64);`, whose one real field is deliberately not extracted as a member yet. It scans top-level items only because the merge step only considers top-level types. It cannot fail.
### Depends on
- externals: std, tree_sitter

## `short_id`
`fn short_id(id: &str) -> &str`
### Summary
Pulls the last piece off a symbol's stable id string (the parts separated by `::`) — the plain name a human would recognize, like turning `a.rs::Counter` into `Counter`.
### Behavior
Splits the id from the right on `::` and returns the final segment, falling back to the whole string if there's no separator at all. Only ever called on the specific id shapes `merge_inherent_impls` deals with — a top-level type's own id, or a method's id from an *inherent* `impl` block (one with no trait, just `impl Counter { ... }`) — where this simple last-segment split always gives the right short name. It is never used on a trait-impl id like `a.rs::impl Debug for S`, where the same naive split would produce a wrong or misleading result.</content>

## `merge_inherent_impls`
`fn merge_inherent_impls(
    syms: Vec<ExtractedSymbol>,
    opaque_types: &std::collections::HashSet<String>,

### Summary
Rust splits a type's data (`struct Foo`) from its behavior (separate `impl Foo { ... }` blocks, sometimes several). This function folds those blocks back into the type, so `Foo` is documented as one thing with its methods and its fingerprints cover them. A trait implementation is folded only in one narrow case.
### Behavior
Works over one file's symbols. It maps type names to the top-level struct, enum or union symbols the file defines, then decides which `impl` blocks fold into which type:
- Every plain inherent `impl Foo { ... }` on a type the file defines folds into it, unconditionally. Impls on a type the file does not define are left alone.
- A trait impl (`impl Trait for Foo`) folds only in a degenerate shape: the type has no fields of its own (and was not flagged as having unextracted tuple fields), no inherent-impl methods, and this is the only trait impl targeting it in the file. Then a standalone document for the type would have nothing to say beyond a guess at what the trait impl already states, and nothing links the two, so no one would mark the bare type stale when the impl's behavior changed. In every other shape each trait impl keeps its own section.

If nothing qualifies it returns the symbols unchanged. Otherwise, for each folded block: its methods (the run of symbols right after it that are its children) are reparented onto the type and their ids rewritten from `<file>::impl Foo::m` to `<file>::Foo::m`. If a method would share an id with a field or with a method already folded in, such as a `validate` field next to `fn validate`, the later method gets a `#2`, `#3` suffix so it cannot overwrite the field in the graph's id map. It also records each block's hash, markers (attributes), the full line range of the block, and which method signatures count as public.

The block symbols are then dropped and each type is rebuilt: its whole-content hash folds in each block's hash; its public-surface hash, if it has one, folds in the public signatures, meaning `pub` methods of an inherent impl or every method of a folded trait impl (they carry no `pub`, since they are public because the trait is), so they are included because they are part of the type's public shape; attribute markers are merged without duplicates; the methods are added as children; and the block line ranges are kept as extra spans, so the `impl Trait for Type {` header, the only line naming the trait, stays in the dependency scan and in the source shown. A type with no public-surface hash keeps none.

Known limitation: whether a trait impl is the only one is judged within this file only, so a second trait impl for the type in another file is invisible and the type still folds. Closing that would need a whole-repo second pass, which was deliberately not built ahead of a real repo hitting it.

## `visit_item`
`fn visit_item(
    node: Node,
    parent_id: Option<&str>,
    source: &str,
    file: &str,
    out: &mut Vec<ExtractedSymbol>,
)`
### Summary
Looks at one Rust item and records the right kind of symbol for it: functions and macros as callables, structs, traits, `impl` blocks and modules as containers, and constants, statics, type aliases and fields as values.
### Behavior
`parent_id` is the enclosing `impl`, trait or module, or `None` at the top of a file. It dispatches on the syntax node's kind:
- A function becomes a callable with raw kind `fn`, or `method` when it has a parent. A function signature with no body, a trait method with no default, is a method too, because it is still part of the trait's surface. A `macro_rules` definition is a callable.
- A struct goes to `visit_container` with its name, so its named fields become value members. Only named fields are extracted; a tuple struct's positional fields are deliberately skipped and fall through to the catch-all, rather than being guessed at ahead of a real repo needing them.
- An enum and a union are recorded as single containers with no member symbols, so an enum's variants are not separate declarations.
- `const`, `static` and `type` items are values.
- A trait goes to `visit_container` as a trait, and an `impl` block goes to `visit_container` named from its header (`impl Foo` or `impl Trait for Foo`).
- A `mod` is recorded as a container only if it has an inline body and is not a `#[cfg(test)]` module; a module declared only by `mod name;` and a test module are skipped.

Every other item kind is silently ignored. It appends to `out` and returns nothing.

## `visit_container`
`fn visit_container(
    node: Node,
    raw: &str,
    name: String,
    parent_id: Option<&str>,
    source: &str,
    file: &str,
    out: &mut Vec<ExtractedSymbol>,
)`
### Summary
Records one Rust struct, trait, `impl` block or inline module as a container, walks its members, and computes the two fingerprints that decide when its specs and dependents go stale: one over everything in it, and one over only its public surface.
### Behavior
The id is `<file>::<name>` at file level, or `<parent id>::<name>` when nested. It walks the container's body, calling `visit_item` for each member with this container as parent, so members are appended first. It then takes only the direct children (filtering by parent id, so a grandchild of a nested container is not mistaken for a direct member).

Whole-container fingerprint (`source_hash`): the signature (the header before the body) plus each direct member's `source_hash`, one per line, hashed, so an edit to any member is an edit to the container.

Public-surface fingerprint (`interface_hash`), built only if the container is `pub` and otherwise `None`: it starts from the signature and adds:
- Each public value member's signature, with any assigned value stripped, so `pub const X: u32 = 1` contributes its name and type but not the number. Type aliases are the exception: the `= Target` is the alias's whole meaning, so it is kept. A private member contributes nothing.
- For a trait, every method signature, since a trait's methods are its entire contract and carry no `pub` of their own. This covers only the trait's own methods. The methods of an inherent `impl` are folded in later, by `merge_inherent_impls`, because at this point they still belong to a separate impl block.

Finally the container is inserted before its members, keeping parent-then-children order, with its line range, preceding doc comment, attributes as markers, parent id and member ids. It appends to `out` and returns nothing.

Rust's rules for turning a module path into a file are structural, so this follows the folder layout and does not run a general module resolver.
### Behavior
First it loads the crate map, which records each library crate in the repo and where each file's `crate::` root is (`CrateMap::load` reads the `Cargo.toml` files). Then, visiting files in sorted order so the saved list is stable, for each file it resolves two groups.

Imports and re-exports: each `use` entry and each `pub use` entry, using the source name for a re-export, goes through `resolve_one`. It maps a module path to a file by convention, `crate::a::b` to `<src>/a/b.rs` or `<src>/a/b/mod.rs`, and not by reading `mod` declarations, then looks the item up as a top-level symbol in that file, following one hop of `pub use`. Every entry is kept, with the target set or empty, and the targets that were found are remembered for the file.

Qualified references: each `crate::a::b::Item` written with no `use` is resolved the same way, but it only becomes an edge if it resolves to a real target that is new. An unresolved one is noise, not a declared intent, so it is dropped. A target in the same file is dropped, since it was never a blind spot. A target already reached by an explicit `use` is dropped, because the callees tool does no de-duplication of its own and would otherwise show it twice.

Finally it adds the same-file trait-impl links from `same_file_trait_impl_edges`, which connect a trait implemented in the same file as its type when no import exists to do it. Returns the full list; it cannot fail, and problems show up as entries with no target.

## `same_file_trait_impl_edges`
`fn same_file_trait_impl_edges(file: &str, graph: &Graph) -> Vec<ResolvedImport>`
### Summary
Adds the missing link between a trait implementation and its type when both are in the same file. Rust needs no `use` for that, so without this link a change to the type's fields would never mark the implementation's spec stale, even though the implementation reads those fields.
### Behavior
Looks up the file's node and returns an empty list if there is none. Then for each top-level symbol of the file that is an `impl` block, it works out the target type name from the header with `trait_impl_target`, which gives nothing for a plain inherent impl, and looks for a symbol `<file>::<Type>` in the graph. If both exist it produces one edge from the file, with the type as the target and the specifier set to the literal text `same file`. The specifier is given plainly because leaving it empty would render a malformed line with nothing after the dash wherever a dependency is displayed, in the Depends-on section and in the callees tool.

It creates exactly the edge a real `use` would have, one edge per trait impl running from the implementation to its type, and none between two sibling impls of the same type, since neither's description says anything about the other's behavior. The cross-file case is already handled once a real `use` names the type, so this fills only the gap a `use` cannot reach. The dependency scan later excludes a symbol's own self-edge, so a type does not appear to depend on itself. It cannot fail.
### Depends on
- `src/graph.rs::Graph` — crate::graph
- `src/resolve.rs::ResolvedImport` — crate::resolve

## `resolve_one`
`fn resolve_one(
    crates: &CrateMap,
    from_file: &str,
    specifier: &str,
    name: &str,
    file_imports: &HashMap<String, FileImports>,
    graph: &Graph,
) -> Option<SymbolId>`
### Summary
Resolves one Rust import, a module path and an item name, to the declaration it names, following at most one `pub use` re-export when the module only forwards the name from elsewhere.
### Behavior
Turns the module path into a file with `module_path_to_file`, which handles `crate::`, `self::`, `super::` and library crate names, and returns `None` if it points outside the repo or no file matches. It then looks for a symbol `<file>::<name>` in the graph and returns it if found. If not, the module may be a barrel that forwards the name, so it looks in that file for a `pub use` published under that name. The hop is resolved from the target file's own crate, which may differ from the importing file's crate, and the symbol is looked up as the re-export's original name in the file it names. If there is no matching re-export, the hop does not resolve, or the symbol is missing, it returns `None`. Only a single hop is followed, so a chain of re-exports through several modules is not resolved, and nested-brace re-exports are not handled. It cannot fail.

## `module_dir_of`
`fn module_dir_of(file: &str) -> String`
### Summary
Given a file path, returns the directory that represents the Rust module *this file itself is* — needed to resolve a relative `self::x` import, which refers to a submodule sitting in that same module's directory.
### Behavior
For a `mod.rs`, `lib.rs`, or `main.rs` file (the files that represent a directory's own module, per Rust's filesystem convention), the module directory is that file's containing directory — so `src/graph/mod.rs` is the module directory `src/graph`, and a crate root like `lib.rs` or `main.rs` with no directory prefix is the repo root itself (empty string). For an ordinary file like `src/graph.rs`, which *is* the module `crate::graph` directly (rather than representing a directory), the module directory is the file path with its `.rs` extension stripped — so `src/graph.rs`'s module directory is `src/graph`, meaning a `self::x` written inside it resolves to `src/graph/x.rs`.</content>
### Depends on
- (none)

## `module_path_to_file`
`fn module_path_to_file(
    crates: &CrateMap,
    from_file: &str,
    specifier: &str,
    file_imports: &HashMap<String, FileImports>,
) -> Option<String>`
### Summary
Turns a Rust module path such as `crate::stats`, `super::util` or `codeowl::index` into the file in the repo where that module's items live, or into nothing when it points at an outside crate or at no file that was indexed.
### Behavior
Splits the path on `::` and decides the starting folder from the first word:
- `crate` means the root of the importing file's own crate, as found by the crate map, not one root for the whole repo.
- `self` means the importing file's module folder.
- `super` goes up one folder for each leading `super`, and the remaining words continue from there.
- Any other first word is looked up as a library crate in this repo: a workspace sibling, or the package's own library seen from a binary, test or example. If found, it resolves like `crate::` inside that crate. If not, it is treated as a 2018-style bare module under the file's crate root, and if no such file was indexed it is external and unresolved, as for `anyhow`, `std` or `tree_sitter`.

The remaining words are joined onto that folder with `/`, taking care not to add a leading slash when the folder is empty. It then tries, in order, `<path>.rs`, `<path>/mod.rs`, `<path>/lib.rs` and `<path>/main.rs`, and returns the first that exists among the indexed files. The lib and main fallbacks let a path to a crate root resolve to its root file. It is purely a file-name convention: `mod` declarations are not read, so it can be wrong for modules renamed with `#[path]`. It returns `None` for an empty path and cannot fail.
### Depends on
- `src/imports.rs::FileImports` — crate::imports
- `src/rust_crates.rs::CrateMap` — crate::rust_crates
- externals: std
