# src/rust.rs
## Summary
This file is CodeOwl's Rust language stack — the same role `lang.rs`/`extract.rs` play for TypeScript, adapted to Rust's own syntax and module system. It walks a single `.rs` file's top-level declarations (functions, structs, enums, traits, `impl` blocks, modules, constants, macros) with tree-sitter, deliberately going only one level deep into a container's body — a function's own internals, a struct's fields, an enum's variants aren't turned into separate symbols, since those are implementation detail rather than declarations worth documenting. A notable Rust-specific wrinkle it handles: Rust splits a type's data (`struct Foo`) from its behavior (a separate `impl Foo { ... }` block, possibly several of them), but a spec reader wants to think of `Foo` as one thing — so after extraction, every *inherent* impl block (one with no trait, just a type's own methods) gets folded back into its type's own symbol, while a trait implementation (`impl Trait for Foo`) is deliberately left as its own separate symbol, since "how Foo satisfies Trait" is a distinct concern. The second half of the file handles Rust's `use` statements: parsing them into imports and `pub use` re-exports, then resolving each one to the actual symbol it names by following Rust's filesystem convention for mapping a module path (`crate::a::b`, `self::x`, `super::y`) to a file — rather than a general-purpose module resolver, since Rust's own compiler defines this mapping structurally.</content>

## `extract_file`
`pub fn extract_file(source: &str, rel_path: &str) -> Vec<ExtractedSymbol>`
### Summary
Parses one Rust file's source text and pulls out its declarations — top-level items like functions and structs, plus one level of members inside an `impl`/`trait`/`mod` block. This is the Rust stack's entry point for turning a file's text into structured data, the same role `lang::extract_symbols` plays for TypeScript.
### Behavior
Loads a fresh tree-sitter parser (the parser library CodeOwl uses to build a syntax tree from source text) with the Rust grammar and parses the source; an unparseable file (e.g. one with a syntax error tree-sitter can't recover from) returns an empty list rather than erroring. It then walks only the root node's direct children — top-level items — dispatching each to `visit_item`, which recurses one level deeper into `impl`/`trait`/`mod` bodies but no further, so a function nested inside a closure or a block isn't picked up as its own symbol. The parsed tree itself is never returned or stored past this function, since its `Node` values only live as long as the tree that produced them (see `CLAUDE.md`'s Rust conventions). Before returning, `merge_inherent_impls` folds a standalone inherent `impl Foo { ... }` block's methods into the `Foo` struct/enum symbol itself, so a type's methods appear as part of its own symbol rather than as a separate, disconnected `impl` entry.</content>
### Depends on
- `src/symbol.rs::ExtractedSymbol` — crate::symbol
- externals: tree_sitter

## `short_id`
`fn short_id(id: &str) -> &str`
### Summary
Pulls the last piece off a symbol's stable id string (the parts separated by `::`) — the plain name a human would recognize, like turning `a.rs::Counter` into `Counter`.
### Behavior
Splits the id from the right on `::` and returns the final segment, falling back to the whole string if there's no separator at all. Only ever called on the specific id shapes `merge_inherent_impls` deals with — a top-level type's own id, or a method's id from an *inherent* `impl` block (one with no trait, just `impl Counter { ... }`) — where this simple last-segment split always gives the right short name. It is never used on a trait-impl id like `a.rs::impl Debug for S`, where the same naive split would produce a wrong or misleading result.</content>

- (none)

## `merge_inherent_impls`
`fn merge_inherent_impls(syms: Vec<ExtractedSymbol>) -> Vec<ExtractedSymbol>`
### Summary
Folds each standalone `impl Foo { ... }` block (an "inherent" impl — one with no trait, just a type's own methods) into the `struct`/`enum`/`union` symbol it belongs to, so a type's methods show up as part of that type's own symbol instead of dangling off a separate, easy-to-miss `impl` entry. This is the last step of Rust extraction, run once per file after every top-level item has already been turned into a symbol.
### Behavior
First builds a lookup from each top-level type's short name (its plain name, without the file prefix) to its position in the symbol list, then finds every top-level `impl` block whose signature names one of those types *and* isn't a trait implementation (`impl Trait for Foo` is recognized and skipped by `inherent_impl_target`, which only matches the bare `impl Foo` shape) — an impl on a type this file doesn't itself define is also left alone.

For each matching impl block, its methods — found as the contiguous run of symbols right after it whose `parent` points at the block — are reparented onto the target type: each method's id is rewritten from `<file>::impl Foo::method` to `<file>::Foo::method`, and its `parent` is repointed at the type's own id. If a type has more than one inherent impl block (a common Rust pattern for splitting a large type's methods across several blocks), all of them fold in, in source order. The type's `source_hash` — a fingerprint of its source text, used to detect changes — is recomputed as a hash over its own hash plus every merged block's hash (a "Merkle fold": combining several hashes into one so a change anywhere inside is detectable from the combined value alone — see `GLOSSARY.md`), so editing a method inside any of the type's impl blocks correctly marks the type itself as changed. Each block's attribute `markers` (things like `#[derive(...)]`) are unioned into the type's own markers, without duplicates. The original standalone `impl` block symbols are dropped entirely from the output; everything else in the file passes through unchanged.</content>

## `visit_item`
`fn visit_item(
    node: Node,
    parent_id: Option<&str>,
    source: &str,
    file: &str,
    out: &mut Vec<ExtractedSymbol>,
)`
### Summary
Looks at one syntax-tree node from a parsed Rust file and, if it's a kind of item CodeOwl extracts, turns it into a symbol (or, for a container, recurses into its members). This is the dispatcher `extract_file` calls once per top-level item, and that containers call again one level deeper for their own members.
### Behavior
Matches on the tree-sitter node's kind and handles each Rust item shape: `function_item` becomes a `Callable` symbol, tagged `"method"` if it's nested inside a container (`parent_id` is `Some`) or plain `"fn"` at file top level; `function_signature_item` (a trait method declared but not given a body, e.g. `fn foo(&self);` inside a trait) is also a `"method"` `Callable`, since it's still part of the trait's public surface even without an implementation. `struct_item`/`enum_item`/`union_item` become `Container`-kind symbols. `const_item`/`static_item`/`type_item` become `Value`-kind symbols (`const`, `static`, `type` respectively). `macro_definition` (a `macro_rules!` block) becomes a `Callable`. `trait_item` and `impl_item` recurse via `visit_container`, treating the trait or impl block itself as a container and its body's items as one level of nested members — `impl_item`'s container name comes from `impl_header`, which renders the impl's target type (and trait, for a trait impl). `mod_item` also recurses as a container, but only if it has an inline body (not `mod foo;`, which just points at another file) and is not gated behind `#[cfg(test)]` — test modules are skipped so a file's test code never pollutes its extracted symbol list. Any other node kind (an attribute, a use statement, a doc comment, etc.) is silently ignored.</content>

## `is_cfg_test`
`fn is_cfg_test(node: Node, source: &str) -> bool`
### Summary
Checks whether a module item is gated behind `#[cfg(test)]` — Rust's convention for unit tests written inline in the same file as the code they test, most commonly `#[cfg(test)] mod tests { ... }`.
### Behavior
Collects the node's attributes (via `attributes`) and checks whether any of them, once spaces are stripped, contains the literal text `cfg(test)`. When `true`, `visit_item` skips the whole module subtree rather than extracting its contents as symbols — the same treatment a dedicated `tests/` file gets from `classify`, so inline test code doesn't pad out a domain file's symbol list with test helpers and test functions that aren't part of its real, spec-worthy surface.</content>

- externals: tree_sitter

## `visit_container`
`fn visit_container(
    node: Node,
    raw: &str,
    name: String,
    source: &str,
    file: &str,
    out: &mut Vec<ExtractedSymbol>,
)`
### Summary
Extracts a Rust item that has a body of its own members — a `trait`, an `impl` block, or a `mod` — as a `Container` symbol, recursing into its body to extract its members first, then building the container's own symbol around them.
### Behavior
Builds the container's id from the file and the given name, then walks the item's body (if it has one) calling `visit_item` on each child with this container's id as their `parent_id` — this is the one level of nesting the Rust extractor supports (a container's members, but not members-of-members). After recursion, it collects the ids of every member symbol just appended to `out`. It computes a Merkle-folded `source_hash` (a hash combining several hashes into one so any change underneath is reflected in the combined value — see `GLOSSARY.md`) starting from the container's own signature text and appending each member's `source_hash` — so editing any member inside the container also counts as editing the container itself, mirroring how the TypeScript extractor treats a class. `is_exported` comes from whether the item's text includes `pub`; if exported, `interface_hash` is a separate hash of just the signature (used to detect only public-surface changes, not internal body edits). `docstring` comes from any doc comment immediately preceding the item, and `markers` from its attributes (like `#[derive(...)]`). The finished container symbol is inserted into `out` *before* its members (not appended after), so the output stays ordered parent-then-children the same way the TypeScript extractor's output does.</content>

- `src/hash.rs::hash_text` — crate::hash
- `src/symbol.rs::ExtractedSymbol` — crate::symbol
- `src/symbol.rs::SymbolKind` — crate::symbol
- externals: tree_sitter

Builds an `ExtractedSymbol` for a Rust item that has no members of its own — a plain function, struct, const, and the like — and appends it to the output list. The shared helper every leaf-item case in `visit_item` calls.

## `impl_header`
`fn impl_header(node: Node, source: &str) -> String`
### Summary
Produces the name used for an `impl` block's own symbol — its full header text (everything before the `{`), like `impl Graph` or `impl Display for Graph`, with whitespace normalized to single spaces.
### Behavior
Takes the text `signature_before_body` returns for the impl node and collapses any run of whitespace (including newlines from a multi-line generic bound) down to single spaces. Keeping the `impl ` prefix in the name — rather than trimming it down to just the type — is deliberate: it's what keeps an `impl Foo`'s symbol id from colliding with `Foo`'s own struct/enum symbol id, since both would otherwise share the same short name.</content>

## `inherent_impl_target`
`fn inherent_impl_target(header: &str) -> Option<String>`
### Summary
Given an `impl` block's header text, figures out which type it's adding methods to directly (an "inherent" impl, like `impl Graph { ... }`) — or returns nothing if the header is actually a trait implementation (`impl Trait for Type`) or doesn't parse as a recognizable impl header at all. This is what `merge_inherent_impls` uses to decide which types get their impl blocks folded in.
### Behavior
Normalizes whitespace, then requires the header to start with the literal word `impl` (guarding against a false match like an identifier that merely starts with the letters "impl"). If the text before any `where` clause contains the standalone word `for`, it's a trait impl (`impl Debug for S`) and this returns `None` — trait impls are deliberately left alone, out of scope for this merge. Otherwise it strips any leading generic parameter list (`<T>`), takes the type path up to the next whitespace or `<` (so `impl<T> Wrapper<T>` yields `Wrapper`, and a lifetime-qualified header like `impl ResolveCtx<'_>` also yields just `ResolveCtx`), and returns only the last segment of that path if it's namespaced (`impl foo::Bar` yields `Bar`, not `foo::Bar`) — matching how a top-level type's own short name is derived elsewhere. Returns `None` if the resulting name would be empty.</content>

## `leading_doc`
`fn leading_doc(node: Node, source: &str) -> Option<String>`
### Summary
Collects an item's doc comment (`///` lines, `//!` lines, or a `/** */` block) from directly above it in the source, so it can be stored as the extracted symbol's `docstring`.
### Behavior
Walks backward through the node's preceding siblings line by line, stopping as soon as there's any gap — a blank line, or a sibling that doesn't end exactly where the tracked line begins — since a comment paragraph separated by whitespace from the item belongs to something else, not this item. ## `extract_imports`
`pub fn extract_imports(source: &str, _rel_path: &str) -> FileImports`
### Summary
Parses a Rust file's `use` declarations into imports and re-exports, so cross-file references can later be resolved against them. A `pub use` is treated as a re-export (Rust's "barrel" pattern, where a `lib.rs`/`mod.rs` re-publishes items from its submodules), and a plain `use` as an ordinary import.
### Behavior
Parses the file fresh with the Rust grammar (returning an empty result if the file fails to parse) and walks only its top-level `use_declaration` nodes — imports nested inside a function body or a conditional block aren't tracked. For each one, it checks for a `pub`/visibility modifier to decide import vs. re-export, then finds the actual import target (skipping the `use` keyword, the visibility modifier, and the trailing `;`) and calls `use_targets` on it to get the individual `(specifier, name)` pairs a single `use` statement can name. Each pair becomes either an `ImportRef` or a `ReExport` (using the imported name as both the exported alias and source name for a re-export, since `use_targets` doesn't currently track an `as` rename separately here). Three shapes are deliberately not handled: a glob import (`use x::*`, which names no single item to track), the `self` in `use x::{self, other}` (imports the module `x` itself alongside its members), and a nested brace list (`use a::{b::C}`) — all considered rare enough in practice to defer rather than add complexity for now.</content>

## `use_targets`
`fn use_targets(arg: Node, source: &str) -> Vec<(String, String)>`
### Summary
Given one `use` statement's argument (the part after the `use` keyword), extracts every `(module-path, item-name)` pair it actually names — handling the three shapes a `use` argument can take.
### Behavior
Dispatches on the argument node's kind. A plain `scoped_identifier` (`use a::b::Item;`) is split via `split_last` into its module-path prefix and final item name, giving one pair. A `use_as_clause` (`use a::b::Item as Alias;`) reads the original path — before the rename — the same way, so the tracked import records the item's real source name rather than its local alias (matching how the TypeScript importer handles an `as` rename). A `scoped_use_list` (`use a::b::{X, Y, Z};`) reads the shared prefix once, then pairs it with every plain identifier listed inside the braces, producing one pair per listed item. Any other shape — a glob (`use a::*`) or a bare single identifier with no path — returns an empty list, since those either name no single item or aren't a form this extractor tracks.</content>

## `resolve_imports`
`pub fn resolve_imports(
    root: &Path,
    file_imports: &HashMap<String, FileImports>,
    graph: &Graph,
) -> Vec<ResolvedImport>`
### Summary
Resolves every file's tracked `use` imports and `pub use` re-exports across the whole repo to the actual symbol (or file) they point at — Rust's counterpart to the TypeScript stack's import resolver, but built around Rust's module-path-to-filesystem convention rather than a general-purpose module resolver library.
### Behavior
First figures out the crate's source root directory (`crate_src_dir`) from the set of files it was given. Then, walking files in a deterministic (sorted by path) order for reproducible output, it goes through each file's imports and re-exports together — treating a re-export's original source name the same way as an ordinary import's name — and calls `resolve_one` for each `(specifier, name)` pair to find its target symbol, building a `ResolvedImport` regardless of whether resolution succeeded (an unresolved import still gets an entry, with `target: None`). Note that resolution is driven entirely by the already-collected `file_imports` map, not by walking the filesystem again — the `root` parameter is accepted but unused for that reason, since the set of files to consider was already determined by the earlier repo walk.</content>

## `resolve_one`
`fn resolve_one(

## `module_dir_of`
`fn module_dir_of(file: &str) -> String`
### Summary
Given a file path, returns the directory that represents the Rust module *this file itself is* — needed to resolve a relative `self::x` import, which refers to a submodule sitting in that same module's directory.
### Behavior
For a `mod.rs`, `lib.rs`, or `main.rs` file (the files that represent a directory's own module, per Rust's filesystem convention), the module directory is that file's containing directory — so `src/graph/mod.rs` is the module directory `src/graph`, and a crate root like `lib.rs` or `main.rs` with no directory prefix is the repo root itself (empty string). ## `module_path_to_file`
`fn module_path_to_file(
    src: &str,
    from_file: &str,
    specifier: &str,
    file_imports: &HashMap<String, FileImports>,
) -> Option<String>`
### Summary
Converts a Rust module path — `crate::a::b`, `self::x`, `super::y`, or a bare external-looking name — into the repo-relative file that module's items actually live in, by Rust's filesystem convention, or `None` if it can't be resolved to a file that was actually walked (most commonly, an external crate like `anyhow` or `std`).
### Behavior
Splits the specifier on `::` and branches on its first segment. `crate::...` resolves relative to the crate's source directory (from `crate_src_dir`). `self::...` resolves relative to the current file's own module directory (`module_dir_of`). `super::...` walks up one directory per leading `super` segment (supporting `super::super::...` chains) before resolving the rest relative to that ancestor directory. Anything else — a name that doesn't start with `crate`/`self`/`super` — is tried as a 2018-edition-style bare top-level module path under the source directory; if no matching file was actually walked, it's assumed to be an external crate and left unresolved.

Once a base directory and the remaining path segments are joined into a candidate module path, it tries four possible file names in order: `<path>.rs` (an ordinary single-file module), or `<path>/mod.rs`, `<path>/lib.rs`, `<path>/main.rs` (a module represented by a directory) — returning the first one that actually exists among the files CodeOwl walked. If none of the four candidates were walked, returns `None`.</content>
### Depends on
- `src/imports.rs::FileImports` — crate::imports
- externals: std
