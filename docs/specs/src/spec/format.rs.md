This file is the per-file spec document: the types that hold one file's spec in memory, the hand-written render and parse of its markdown-with-frontmatter form, and the read and write that put it on disk. The types are `HashPair` (the five fields recorded per entry: source hash, the file-only fingerprint, dependency hash, prose hash, and the per-dependency breakdown), `SymbolProse` (the summary and behavior text), and `FileSpec` (the file's hashes, one entry per top-level symbol in declaration order, the file summary, and the per-symbol prose). `render` writes the frontmatter, then a title with the one-line "Generated by CodeOwl" attribution, the file summary, and one section per symbol; the signature and the "Depends on" list in each section are recomputed from the graph on every render, never stored, and a section is written only for an id that has a hash record. `parse` is its inverse and is tolerant only of what `render` produces: it reads the symbols and `dep_targets:` blocks, skips the attribution line and any unknown frontmatter key, and picks up a symbol's prose by locating its heading, so a symbol whose heading is missing is skipped rather than failing the document. Small helpers cover the rest: `extract_section` pulls the text under a heading up to the next marker, `read_file_spec` is the public read (a missing document is `None`, a malformed one is an error), and `write` saves a document. ## `HashPair`
`pub struct HashPair`
### Summary
The record stored with each written spec, holding the fingerprints and the breakdown later used to tell whether the spec still matches the code. It has five fields, and one such record exists for the file as a whole and one for each symbol in it.
### Behavior
`source_hash` fingerprints the item's own code at the time the spec was written. `fingerprint` is a file's own entry only (empty for a symbol): the language pack's hash of what a file summary could quote, and a file spec is current while it equals the graph's current fingerprint for that file. A spec written before fingerprints existed has it empty, so it reads as changed until it is migrated or regenerated. `deps_hash` fingerprints the public shape (the `interface_hash`, see `GLOSSARY.md`) of everything the item depends on, as observed at that moment; it catches the case where the item's own text is unchanged but something it imports changed shape. `dep_targets` is the list of `(target id, shortened hash)` pairs that `deps_hash` was made from, kept so a later check can name which dependency moved. It is empty for a spec written before it existed (the cause then reads "unknown") and when there are no resolved dependencies, and it is never compared against `deps_hash`, which stays the single staleness key. `spec_hash` fingerprints the prose the agent wrote, so a hand edit can be detected; staleness never uses it for invalidation. The struct is plain data with public fields and no logic.

## `FileSpec`
`pub struct FileSpec`
### Summary
The in-memory form of one file's spec document: the file's own fingerprints, a fingerprint per function or type, and all the prose. It is kept separate from the markdown text so the code that saves and merges specs never has to re-read what it just wrote.
### Behavior
Fields: `source_path` (the file's repo-relative path), `file` (a `HashPair` for the whole file), `symbols` (an id plus `HashPair` for each top-level function or type, in declaration order), `file_summary` (the prose under the file's `## Summary`), and `sections` (an id plus `SymbolProse` per symbol). ## `dep_target_block`
`pub(crate) fn dep_target_block(spec: &FileSpec) -> String`
### Summary
Renders the `dep_targets:` block of a file spec's frontmatter: the list of which dependency each entry's `deps_hash` was built from, so a later check can say which one moved.
### Behavior
It walks the file's own entry first (under the owner name `file`), then each symbol in declaration order, and writes one line per recorded dependency in the form `  <owner> -> <target>: <hash>`, indented two spaces, order within an owner kept as stored. If no entry has any recorded dependency it returns an empty string, with no header at all, so a spec with no resolved dependencies, or one written before the record existed, renders exactly as it did before. ## `parse`
`pub fn parse(content: &str) -> Result<FileSpec>`
### Summary
Parses a file spec document's own rendered text back into a structured `FileSpec`, the inverse of `render`. It only needs to handle exactly what `render` produces; tolerating arbitrary human reformatting or reordering of a hand-edited spec is not what it is for.
### Behavior
Requires the document to start with a `---` line opening the frontmatter, erroring otherwise. It walks the frontmatter line by line with two nested-block modes. After a `symbols:` line, each two-space-indented line is one symbol entry, split at the flow map's opening `{` rather than the first `:`, since a symbol's own id contains `::` (like `file.ts::name`); an entry with no `{` is an error. After a `dep_targets:` line, each indented line is handed to `record_dep_target`, which attaches the pair to the file or to the symbol it names; a line it cannot attribute is skipped, not an error. Every other frontmatter line is split on the first `:` into a key and value, and a line with no colon is an error. `source_paths` is unwrapped from its `[...]` brackets, and `file` is parsed into a `HashPair`; unknown keys are ignored. Parsing stops at the closing `---`.

The body after it is scanned for the file's `## Summary` section, bounded by the next `## ` heading. Then, for each symbol recorded in the frontmatter, it looks for that symbol's `` ## `name` `` heading, where `name` is the short name, and takes the block up to the next `## ` heading, and within it the `### Summary` and `### Behavior` text into a `SymbolProse`. The attribution line under the title is never read, so documents with or without it parse the same. Limits: sections are found only for ids in the frontmatter, so a section with no hash record is invisible; a symbol whose heading is missing is silently skipped; and the heading is located by the first match of its short name, so two symbols sharing a short name would both read the first block.

## `record_dep_target`
`fn record_dep_target(line: &str, file: &mut HashPair, symbols: &mut [(String, HashPair)])`
### Summary
Reads one line of the frontmatter's `dep_targets:` block and attaches the `(target, hash)` pair it names to the right owner: the file itself or one of its symbols.
### Behavior
A line has the form `<owner> -> <target>: <hash>`, already stripped of its two-space indent. The owner is the word `file` or one of the symbol ids the frontmatter declared. Several can match a line as a prefix, because a symbol id may itself contain ` -> ` (an `impl Fn() -> u8` header), so it takes the longest matching owner rather than splitting at the first arrow. The hash is whatever follows the last `: `, because a target id can contain `: ` too (`impl<T: Clone> ...`), and it is trimmed. If no declared owner matches, or the remainder has no `: `, the line is silently skipped, never an error, so an old or hand-damaged line cannot make a document unreadable. The pair is appended to the owner's `dep_targets` in the order lines appear. One catch: a symbol id that is a prefix of another is handled only by the longest-match rule, and an owner id that appears twice in the frontmatter receives the pair on its first entry.

## `read_existing`
`pub(super) fn read_existing(root: &Path, source_path: &str) -> Result<Option<FileSpec>>`
### Summary
Reads and parses a file's spec document off disk, if it exists.
### Behavior
Computes the spec's expected path via `spec_path`; if nothing exists there, returns `Ok(None)` rather than an error, since a file not having a spec yet is a normal state. If the file does exist, it reads the contents and parses them with `parse`, propagating any read error (with the path attached) or parse error. A document that exists but is malformed is therefore an error, not `None`, so callers cannot mistake damaged data for a missing spec. It checks existence first and reads second, so a file deleted between the two steps surfaces as a read error. The crate-visible wrapper `read_file_spec` simply calls this.

## `write`
`pub(super) fn write(root: &Path, graph: &Graph, file_id: SymbolId, spec: &FileSpec) -> Result<()>`
### Summary
Saves a file's spec to disk as a markdown document under `docs/specs/`, creating folders as needed.
### Behavior
Works out the output path from the file's source path with `spec_path`, creates any missing parent directories, and writes the string produced by `render` through `write_replacing`, which writes a flushed temporary file and renames it over the target. A crash mid-write therefore leaves either the old document or the new one, never a partial one. Errors from creating the directory are returned with context naming the path, and errors from the write come from `write_replacing`. It overwrites whatever was there and reads nothing back: anything calling it has already merged the new prose with the existing prose, and the dependency lines and signatures in the output are recomputed from the graph at that moment.

## `write_replacing`
`pub(super) fn write_replacing(path: &Path, content: &str) -> Result<()>`
### Summary
Replaces a file's contents without a moment in which it is empty or half written. It is the one way any spec document (file, feature, rollup, system) reaches disk.
### Behavior
It writes the new content to a staging file next to the target, named by appending `.tmp` to the full path, flushes the bytes to disk with `sync_all`, closes the file, and only then renames it over the target. A crash or a full disk during the write leaves the previous document whole instead of a torn one that would end up in git. If the write or the flush fails, the error names the staging path; if the rename fails, the staging file is removed rather than left behind to be committed, and the error names the target. The fixed `.tmp` name is safe only because a single server process writes specs, so two writers to the same document would share a staging file. A stray `.tmp` file from a process killed between create and rename is not cleaned up here.

- externals: anyhow, std
