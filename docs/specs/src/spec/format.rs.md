## Summary
This file is the per-file spec document: the types that hold one file's spec in memory, the hand-written code that turns it into a markdown page and back, and the read and write that put it on disk. The types are `HashPair` (the five things recorded per entry: source hash, a fingerprint kept for the file's own entry only, dependency hash, prose hash, and the per-dependency breakdown), `SymbolProse` (a symbol's summary and behavior text) and `FileSpec` (the file's hashes, one entry per top-level symbol in source order, the file summary, and the per-symbol prose). `render` writes the header block between two `---` lines, starting with the standard-format keys from `file_okf_frontmatter` (built with `okf_frontmatter`, with `yaml_quoted`, `yaml_flow_item` and `path_from_doc` making sure paths and sentences cannot break the header), then the hashes. After the header come the title, which is the file's path linked to its source file (`file_title_line`, `linked_title`), the "Generated using CodeOwl" line, the file summary, and one section per symbol. The signature and the "Depends on" list in each section are recomputed from the code graph on every render and never stored: `linked_dependency_lines` writes each dependency as a link to its section in the other file's spec, while `dependency_lines` is the plain-text version used by the quality check, both built by `dependency_lines_with` and `link_to_spec`. A section is written only for a symbol that has a hash record. `parse` is the reverse, and understands only what `render` writes: it reads the symbol and dependency blocks (with `parse_hash_pair` and `record_dep_target`), ignores the standard-format keys, the title, the credit line and any unknown header key, and finds a symbol's prose by its heading, so a symbol whose heading is missing is skipped rather than failing the page. A small set of helpers (`has_provenance`, `with_provenance`, `without_provenance`) adds the credit line to, and removes it from, the title-led bodies of feature and system specs, so the stored and hashed body never contains it. The rest covers `extract_section` (the text under a heading up to the next marker), `read_file_spec` (a missing page is `None`, a malformed one is an error), `write`, and `write_replacing`, through which every spec document is saved: it writes a flushed temporary file beside the target and renames it over the old one, so a crash leaves the old page or the new one and never half of each. The temporary file has a fixed `.tmp` name, which is safe because only one server process writes specs.

## `HashPair`
`pub struct HashPair`
### Summary
The record stored with each written spec, holding the fingerprints and the breakdown later used to tell whether the spec still matches the code. It has five fields, and one such record exists for the file as a whole and one for each symbol in it.
### Behavior
`source_hash` fingerprints the item's own code at the time the spec was written. `fingerprint` is a file's own entry only (empty for a symbol): the language pack's hash of what a file summary could quote, and a file spec is current while it equals the graph's current fingerprint for that file. A spec written before fingerprints existed has it empty, so it reads as changed until it is migrated or regenerated. `deps_hash` fingerprints the public shape (the `interface_hash`, see `GLOSSARY.md`) of everything the item depends on, as observed at that moment; it catches the case where the item's own text is unchanged but something it imports changed shape. `dep_targets` is the list of `(target id, shortened hash)` pairs that `deps_hash` was made from, kept so a later check can name which dependency moved. It is empty for a spec written before it existed (the cause then reads "unknown") and when there are no resolved dependencies, and it is never compared against `deps_hash`, which stays the single staleness key. `spec_hash` fingerprints the prose the agent wrote, so a hand edit can be detected; staleness never uses it for invalidation. The struct is plain data with public fields and no logic.

## `FileSpec`
`pub struct FileSpec`
### Summary
The in-memory form of one file's spec document: the file's own fingerprints, a fingerprint per function or type, and all the prose. It is kept separate from the markdown text so the code that saves and merges specs never has to re-read what it just wrote.
### Behavior
Fields: `source_path` (the file's repo-relative path), `file` (a `HashPair` for the whole file), `symbols` (an id plus `HashPair` for each top-level function or type, in declaration order), `file_summary` (the prose under the file's `## Summary`), and `sections` (an id plus `SymbolProse` per symbol). Lists of pairs are used rather than maps to keep declaration order. Three helpers exist: `blank` makes an empty spec for a path with every other field defaulted, and `symbol_hash` and `section` find one symbol's hashes or prose by id with a linear scan, returning `None` when the id is absent. Scans are fine because a file has few top-level symbols. `symbol_hash` is visible across the crate, while `blank` and `section` are visible only inside `spec/`. A section is tied to its hash record: when a document is read back, a section is picked up only for an id that has an entry in `symbols`, and when one is rendered, a section is written only for an id in `symbols`. A section with no hash record is therefore invisible to everything built on this type.

## `dep_target_block`
`pub(crate) fn dep_target_block(spec: &FileSpec) -> String`
### Summary
Renders the `dep_targets:` block of a file spec's frontmatter: the list of which dependency each entry's `deps_hash` was built from, so a later check can say which one moved.
### Behavior
It walks the file's own entry first (under the owner name `file`), then each symbol in declaration order, and writes one line per recorded dependency in the form `  <owner> -> <target>: <hash>`, indented two spaces, order within an owner kept as stored. If no entry has any recorded dependency it returns an empty string, with no header at all, so a spec with no resolved dependencies, or one written before the record existed, renders exactly as it did before. Otherwise the lines are joined under a single `dep_targets:` line. It does not shorten or validate the hashes and does not escape anything: the parser relies on the `<owner> -> ` prefix and on the hash being whatever follows the last `: `, since both a symbol id and a target id can contain ` -> ` or `: ` themselves.

## `has_provenance`
`pub(super) fn has_provenance(text: &str) -> bool`
### Summary
Answers whether a spec document already carries its "Generated using CodeOwl" credit line directly under its title.
### Behavior
Splits the text into lines, takes the second one, and compares it exactly with the provenance line (the `> Generated using [CodeOwl](…)` quotation CodeOwl puts under every title). Splitting into lines also drops a trailing carriage return, so a file saved with Windows line endings still matches. ## `yaml_quoted`
`pub(super) fn yaml_quoted(s: &str) -> String`
### Summary
Turns any piece of text into a quoted value that is safe to write in the header block at the top of a spec file, whatever characters the text contains.
### Behavior
Wraps the text in double quotes and walks it one character at a time. A double quote and a backslash each get a backslash in front. Every control character (a tab, a newline, a stray bell character, DEL) and the two Unicode line-separator characters (U+2028 and U+2029) are written as `\uXXXX` with four uppercase hex digits, so a heading written by a model can never end the line the value sits on. Everything else, including brackets, colons and non-English letters, is copied unchanged, because inside double quotes those cannot confuse a YAML reader (YAML is the plain-text format the header uses). Example: `say "hi"` becomes `"say \"hi\""`. It only escapes; it never rejects or shortens its input, and it does not give a way to tell whether the result will be valid for some other quoting style.
### Depends on
- (none)

## `yaml_unquoted`
`pub(super) fn yaml_unquoted(s: &str) -> String`
### Summary
Reads a value back out of a spec file's header: it removes the quotes `yaml_quoted` put around it and undoes the escapes, and leaves an unquoted value alone.
### Behavior
First trims the surrounding whitespace. If the result does not both start and end with a double quote, it is returned as it is, which is what lets specs written before quoting existed read exactly as before. Otherwise the quotes are removed and the text is read one character at a time. A backslash followed by `u` takes the next four characters as a hex number and turns it into the character it names; if those four are not valid hex, or name no real character (a lone surrogate half), the text is kept literally as `\u` plus the four characters. A backslash followed by any other character just drops the backslash and keeps that character, so `\"` becomes `"` and `\\` becomes `\`, but `\n` becomes the letter `n`, not a newline. A backslash at the very end is dropped. Only the escapes `yaml_quoted` writes are understood properly; it is not a general YAML reader, and it does not handle single-quoted values.
### Depends on
- (none)

## `yaml_flow_item`
`pub(super) fn yaml_flow_item(path: &str) -> String`
### Summary
Decides how a file path is written inside the one-line list `source_paths: [...]` in a spec's header: plainly for ordinary paths, in quotes for paths that could confuse a reader of that list.
### Behavior
A path is written as it is when it is not empty, does not start with a hyphen, and every character is an ASCII letter or digit or one of `_ . / - +`. It only looks at characters: a path made of safe characters that YAML would still read as something other than text, such as a bare `null`, `true` or `12`, stays unquoted.

## `render`
`pub fn render(graph: &Graph, root: &Path, file_id: SymbolId, spec: &FileSpec) -> String`
### Summary
Turns a file's stored spec data into the markdown document saved under `docs/specs/`. It mixes the prose an agent wrote with facts CodeOwl recomputes on every call, such as signatures and dependency lists, so those facts never go stale and are never invented.
### Behavior
The output is built in this order. First a header block between two `---` lines: the standard-format keys from `file_okf_frontmatter` (type, title, description, who generated it, and the source file), then `source_paths`, then one line with the file's hashes, where `fingerprint` is written only when it is non-empty, so an older file entry renders without it. Next, when there are symbols, one hash line per symbol id (source, dependency and spec hash, never a fingerprint), and then the `dep_targets:` block from `dep_target_block`, which is empty when nothing is recorded. After the header comes the title line, linked to the source file, the "Generated using CodeOwl" line, and `## Summary` with the trimmed file prose.

Then, for each symbol in `spec.symbols` order: a second-level heading holding the symbol's short name in code style (from `short_name`), the symbol's current signature looked up in the graph (left out if the id no longer resolves), `### Summary` and `### Behavior` from the matching stored section (empty if none was stored), and a `### Depends on` list from `linked_dependency_lines`, or `- (none)` when that list is empty. The list is empty both when the symbol uses nothing from elsewhere and when its source text cannot be read from `root` or the symbol is not in the graph, so `(none)` does not always mean "no dependencies". `root` is needed only so the dependency list can read the symbol's own source off disk and name just what that symbol uses, not every import in the file. All prose is trimmed and each part ends with a newline. The function builds a string and has no side effects. It writes sections only for ids in `spec.symbols`: a stored section with no hash record is dropped from the output.

## `parse`
`pub fn parse(content: &str) -> Result<FileSpec>`
### Summary
Reads a saved file spec back into structured data (the file's hashes, its symbols, its summary and each symbol's prose); it is the reverse of `render`. It only has to understand what `render` writes: coping with a spec someone reformatted or reordered by hand is not what it is for.
### Behavior
The document must start with a `---` line that opens the header, otherwise it fails. The header is read line by line, with two nested modes. After a `symbols:` line, each line indented by two spaces is one symbol entry, split at the opening `{` of its hash record and not at the first colon, because a symbol's own id contains `::` (as in `file.ts::name`); an entry with no `{` is an error. After a `dep_targets:` line, each indented line goes to `record_dep_target`, which attaches the (dependency, hash) pair to the file or to the symbol it names, preferring the longest matching owner; a line with no known owner or no `": "` separator is skipped quietly. Every other header line is split at its first colon into a key and a value, and a line with no colon is an error. `source_paths` is unwrapped from its `[...]` brackets and unquoted by `yaml_unquoted`, and `file` becomes a `HashPair`. All other keys are ignored, which is why the standard-format keys at the top (`type`, `title`, `description`, `generated`, `resource`) and an older `kind:` line make no difference. Reading stops at the closing `---`.

The body is then searched for the file's `## Summary` section, which ends at the next `## ` heading. For each symbol listed in the header it looks for the `` ## `name` `` heading (using the short name), takes the block up to the next `## ` heading, and reads `### Summary` and `### Behavior` from it. The title line (now a link), the "Generated using" line and each "Depends on" list are never read, so a spec with or without them parses the same. It stops short in these ways: sections are found only for symbols in the header, so a section with no hash record is invisible; a symbol whose heading is missing is skipped without a complaint; and the heading is located by its first match, so two symbols with the same short name would both read the first block.

## `record_dep_target`
`fn record_dep_target(line: &str, file: &mut HashPair, symbols: &mut [(String, HashPair)])`
### Summary
Reads one line of the frontmatter's `dep_targets:` block and attaches the `(target, hash)` pair it names to the right owner: the file itself or one of its symbols.
### Behavior
A line has the form `<owner> -> <target>: <hash>`, already stripped of its two-space indent. The owner is the word `file` or one of the symbol ids the frontmatter declared. Several can match a line as a prefix, because a symbol id may itself contain ` -> ` (an `impl Fn() -> u8` header), so it takes the longest matching owner rather than splitting at the first arrow. The pair is appended to the owner's `dep_targets` in the order lines appear. One catch: a symbol id that is a prefix of another is handled only by the longest-match rule, and an owner id that appears twice in the frontmatter receives the pair on its first entry.

## `write`
`pub(super) fn write(root: &Path, graph: &Graph, file_id: SymbolId, spec: &FileSpec) -> Result<()>`
### Summary
Saves a file's spec to disk as a markdown document under `docs/specs/`, creating folders as needed.
### Behavior
Works out the output path from the file's source path with `spec_path`, creates any missing parent directories, and writes the string produced by `render` through `write_replacing`, which writes a flushed temporary file and renames it over the target. A crash mid-write therefore leaves either the old document or the new one, never a partial one. Errors from creating the directory are returned with context naming the path, and errors from the write come from `write_replacing`. It overwrites whatever was there and reads nothing back: anything calling it has already merged the new prose with the existing prose, and the dependency lines and signatures in the output are recomputed from the graph at that moment.

## `write_replacing`
`pub(super) fn write_replacing(path: &Path, content: &str) -> Result<()>`
### Summary
Replaces a file's contents without a moment in which it is empty or half written. It is the one way any spec document (file, feature, rollup, system) reaches disk.
### Behavior
It writes the new content to a staging file next to the target, named by appending `.tmp` to the full path, flushes the bytes to disk with `sync_all`, closes the file, and only then renames it over the target. A crash or a full disk during the write leaves the previous document whole instead of a torn one that would end up in git. If the write or the flush fails, the error names the staging path; if the rename fails, the staging file is removed rather than left behind to be committed, and the error names the target. The fixed `.tmp` name is safe only because a single server process writes specs, so two writers to the same document would share a staging file. A stray `.tmp` file from a process killed between create and rename is not cleaned up here.
