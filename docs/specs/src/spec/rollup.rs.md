# [`src/spec/rollup.rs`](../../../../src/spec/rollup.rs)

## Summary
This file handles the directory rollup, the document that summarises a folder from its files' own summaries, and the list of such folders that the system spec and the coverage report both use. A rollup is stored at `docs/specs/<dir>/_index.md` and is one document with one hash, closer to a feature spec than to a file spec: the agent writes only the summary paragraph, and CodeOwl fills in a contents list of the folder's files underneath it, rebuilt from the current files on every render. The file builds the rollup's OKF frontmatter and its linked title, renders and parses the page, and reads it back from disk.

A rollup records, for each spec-bearing file directly in the folder, that file's current spec hash. That list is what staleness is judged on. A file whose spec is missing or behind its source counts as an empty hash, so a rollup is never offered, and never accepted, while any file below it is unfinished. The rollup is current when the stored list equals the present one and its body passes the quality check, so adding or removing a file, rewriting a file spec, or a flagged body all send it back for a rewrite. Generation follows the same bottom-up order as everywhere else: the folder's files go first, through the file ladder, and only then does the rollup task appear, carrying each file's summary. Submitting trims the text, rejects an empty or flagged body, and writes the page by replacing the old file in one step.

Only a folder with at least two spec-bearing files of its own gets a rollup, and only its immediate files count; rollups do not aggregate their subfolders, so the module list is flat at every depth. That list leaves out the repo root, whose path is reserved for the system spec, and any folder that is test code. The parser is small and strict about the frontmatter shape: it reads the directory, the file hash list and the rollup hash, ignores the other keys, and fails on a frontmatter line with no colon.

### Summary
Decides whether a folder needs a new summary page and, if so, collects the file summaries the agent will write it from. It returns nothing while any file in the folder is still unfinished, and when the folder summary is already current.
### Behavior
An empty `dir_path` (the repo root) is an error, because its rollup would collide with the reserved top-level system spec path. It returns `Ok(None)` when the folder has fewer than two spec-bearing files (`directory_is_spec_bearing`). It then computes `current_file_hashes`, and if any hash is empty, meaning that file's spec is missing or stale, it returns `None`, so a folder summary is never written on top of out-of-date file summaries.

The rollup counts as current when the stored list of file hashes equals the current list (`diff_hash_lists` finds no difference) and its stored body passes `body_smells`. A file added to or removed from the folder, or a file spec rewritten since, therefore triggers a rewrite, and so does a stored body that a quality check distrusts. Otherwise it gathers each spec-bearing file's stored summary, keeping a spec only when `file_changes` reports nothing changed in it (a comparison of the file's fingerprint, not the raw source), and fails with a message to exhaust `next_task_for_directory` first if one is missing. The result is a `RollupTask` holding the directory and those summaries in path order.

It is read-only. Unlike the file ladder, a rollup offered here carries no draft of its previous text, so the agent writes the paragraph from the file summaries alone.

## `submit_rollup`
`pub fn submit_rollup(
    graph: &Graph,
    root: &Path,
    dir_path: &str,
    content: &str,
) -> Result<RollupSpec>`
### Summary
Saves the agent's folder summary, together with fingerprints of the file summaries it was based on, as that folder's `_index.md`. It refuses text that is empty, weak, or written while the files below it are not ready.
### Behavior
Checks run in order, and each failure is an error with nothing written. The directory must be spec-bearing (at least two spec-bearing files). The trimmed content must be non-empty. It must pass `reject_if_smelly` over `body_smells`, so a cop-out phrase, too little text, stray markup or a code span that never closes is refused, and the error names the check. It then computes `current_file_hashes`; if any file has an empty hash (no current spec) it fails naming that file and telling the caller to generate its file spec first.

On success it builds a `RollupSpec` whose `spec_hash` is the hash of the trimmed body, creates the directory if it is missing, and writes the output of `render_rollup` through `write_replacing`, which writes a temporary file and renames it, so a reader never sees a half-written page. The `Contents` list is recomputed by the render, not taken from the submitted text. It returns the `RollupSpec`.

The recorded file hashes are what later make the folder summary go stale when any file's spec is rewritten or the file set changes. It does not look at what the prose says: a summary that is long and well-formed but wrong is accepted.

## `enumerate_modules`
`pub fn enumerate_modules(graph: &Graph) -> Vec<String>`
### Summary
Lists every folder in the repo that qualifies for its own summary page. This flat list is what the top-level system summary draws on.
### Behavior
Takes the parent directory of every indexed file (backslashes normalised to `/`), sorts and de-duplicates them, and keeps a directory only if it is non-empty, is not test code, and passes `directory_is_spec_bearing` (at least two spec-bearing files directly inside it). The repo root, whose path is the empty string, is always excluded, because its rollup path is reserved for the system spec itself. The test check appends a `/` to the directory before asking the language pack, so a folder like `tests` is recognised as a test root under a Rust repo.

The list is deliberately flat at every nesting depth: a folder's summary does not roll up its subfolders' summaries, so no hierarchy is invented on top of documents that are not structured that way. A folder with only one spec-bearing file of its own is not listed even if its subfolders qualify, and a parent whose subfolders hold all the code is missing from the list. The result is alphabetical, is computed from the graph alone, and cannot fail.

## `current_module_hashes`
`pub fn current_module_hashes(graph: &Graph, root: &Path) -> Result<Vec<(String, String)>>`
### Summary
Lists every module folder with the fingerprint of its current folder summary, or an empty value if that summary is missing or out of date. The top-level system summary compares this list with what it stored to know whether it must be rewritten.
### Behavior
For each directory from `enumerate_modules`, in that alphabetical order, it computes the current file hashes and reads the stored rollup. The rollup's `spec_hash` is used only when its recorded file list matches the current one (`diff_hash_lists` finds no difference), which means the rollup is current; otherwise the value is an empty string. It follows the same convention that `current_file_hashes` uses one level down: an empty hash means "not ready", so the system spec cannot count as current while any module summary is missing or behind its files.

The comparison looks only at the file hash list. It does not run the quality check on the rollup body, so a stored rollup that `next_rollup_task` would re-offer for a smell still reports its hash here. Any failure reading a spec file from disk is returned as an error; an absent rollup is just an empty hash.
