## `classify_in`
`fn classify_in(graph: &Graph, path: &str) -> FileRole`
### Summary
Says whether a file is ordinary code, test code, or something else, using the conventions of the language stack the repo was indexed with. It exists so spec prioritisation doesn't assume every repo lays out its tests the same way.
### Behavior
Forwards straight to `Graph::file_role(path)`, which asks the stack stored on the graph (Rust treats `tests/` as a test root, TypeScript uses the JS naming conventions). No state is read or changed and there is no error case: an unknown path simply gets whatever role the stack gives unrecognised files.

## `spec_path`
`pub fn spec_path(root: &Path, source_path: &str) -> PathBuf`
### Summary
Computes where a given source file's spec document lives on disk, mirroring the source tree under `docs/specs/`.
### Behavior
Joins the repo root with `docs/specs/` and the source path with `.md` appended — deliberately not stripping the source file's own extension, so `lib/utils.ts` maps to `docs/specs/lib/utils.ts.md` rather than `docs/specs/lib/utils.md`. Keeping the original extension avoids a collision if two same-named files with different extensions existed in the same directory, and makes the mapping trivially reversible by eye.

- externals: std

## `is_test_path`
`pub fn is_test_path(graph: &Graph, path: &str) -> bool`
### Summary
Answers "is this file test code?" for a repo-relative path. Test files stay in the index but are documented last, and are never treated as a product module.
### Behavior
Calls `classify_in` and returns true only when the role is `FileRole::Test`; every other role (source, config, and so on) gives false. The stack decides what counts as a test, so `tests/` is a test root in a Rust repo and `.test.`/`__tests__` names are in a TypeScript one. The function itself does no string handling, so the rollup/feature id prefix mentioned in its doc comment is not stripped here.

## `file_is_spec_bearing`
`pub fn file_is_spec_bearing(graph: &Graph, file_id: SymbolId) -> bool`
### Summary
Decides whether a file gets its own spec document at all. A file qualifies when it declares at least one function or type-like thing (a class, struct or similar) at its top level, so files that only re-export names or hold constants are skipped.
### Behavior
Returns false immediately if the file's role is `FileRole::Generated` (code produced by a build step, such as a codegen'd interface), however much it exports, because specs describe hand-written code. Otherwise it looks at the file's direct children and returns true if any has kind `Callable` or `Container`. `Value` leaves (constants, type aliases, interfaces, enums) do not count on their own. Whether a declaration is `pub`/exported is deliberately ignored: a file full of private code, such as an integration-test file, still deserves a spec. A child id that no longer resolves to a symbol is treated as not matching rather than an error.

## `GeneratedSourcesSummary`
`pub struct GeneratedSourcesSummary`
### Summary
A small report saying how many files in the repo live in the folders where the build tool puts generated code. It lets the coverage report warn that generated code may be missing, for example because the project was never compiled locally.
### Behavior
Holds two fields: `checked_dirs`, the generated-source directories the language pack looks in, and `found`, the number of indexed files under them. It is only built for packs that declare such directories (Java today); for the others the report omits it, since a zero would be misleading. A `found` of 0 with a non-empty `checked_dirs` is the useful signal: entry points defined only on generated interfaces will not be visible until the build has run. The struct is plain data with no logic of its own.

- (none)

## `generated_sources_summary`
`pub fn generated_sources_summary(graph: &Graph) -> Option<GeneratedSourcesSummary>`
### Summary
Builds the "generated sources" report for a repo, or returns nothing when the repo's language has no such concept.
### Behavior
Looks up the language pack named on the graph and asks it for its generated-source directories. If the list is empty it returns `None`. Otherwise it counts the files whose role, as decided by `classify_in`, is `FileRole::Generated` and returns them with the directory names as strings. The count comes from the file roles rather than a fresh disk scan, so it reflects exactly what the index already holds. It cannot fail.

## `spec_bearing_children`
`pub(crate) fn spec_bearing_children(graph: &Graph, file_id: SymbolId) -> Vec<SymbolId>`
### Summary
Lists the top-level items in a file that get their own section in the file's spec: its functions and its classes, structs or similar types, public or private.
### Behavior
Takes the file's direct children in their stored order and keeps those whose kind is `Callable` or `Container`, returning their ids. `Value` children (constants, type aliases, interfaces, enums, destructured names) are dropped, so they have no section of their own. A container's members are not listed separately, because they are described inside the container's section. A child id that does not resolve to a symbol is skipped. Both `file_is_spec_bearing` and the task-ordering code rely on this same rule, so the two stay in agreement.

## `directory_is_spec_bearing`
`pub fn directory_is_spec_bearing(graph: &Graph, dir_path: &str) -> bool`
### Summary
Decides whether a folder gets a summary page of its own (an `_index.md`). It does when at least two of the files directly inside it are themselves worth documenting, so folders holding a single file don't produce noise.
### Behavior
Calls `spec_bearing_files_in` for the directory and checks that the result has two or more entries. Only immediate children count; files in subfolders are not included. The path is repo-relative with no trailing slash, and the empty string means the repo root, although the rollup task code guards that case separately. The function has no failure mode: an unknown directory just has no files and returns false.
### Depends on
- `src/graph.rs::Graph` — crate::graph

## `files_in`
`pub(super) fn files_in(graph: &Graph, dir_path: &str) -> Vec<SymbolId>`
### Summary
Returns every file that sits directly in one folder, in alphabetical order, whether or not it is worth documenting. Files in subfolders are not included.
### Behavior
Walks all files in the graph and keeps those whose parent directory equals `dir_path`. Backslashes in the parent are normalised to `/` first, so Windows-style paths compare correctly. A top-level file's parent is the empty string, which matches `dir_path == ""`. Each match is turned back into a symbol id via `graph.find`, and files that cannot be found are dropped. The result is sorted by path string so repeated runs give the same order.

## `spec_bearing_files_in`
`pub(super) fn spec_bearing_files_in(graph: &Graph, dir_path: &str) -> Vec<SymbolId>`
### Summary
Returns the files directly inside a folder that are worth documenting, in alphabetical order. It is the list a folder summary is built from.
### Behavior
Takes the output of `files_in` (already path-sorted) and keeps only the ids for which `file_is_spec_bearing` is true. Because filtering preserves order, the result stays sorted, which keeps generated folder summaries stable between runs. A directory's files have no meaningful declaration order, so path order is the only one that is used. An empty or unknown directory gives an empty list.
