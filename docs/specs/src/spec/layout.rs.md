## Summary
This file answers two questions about the spec documents: which ones the granularity rules say should exist, and where each lives and how other specs link to it. A file's spec sits at the file's own path under `docs/specs/` with `.md` appended, and the source extension is never stripped, so `lib/utils.ts` becomes `docs/specs/lib/utils.ts.md`. The naming rule is in one private function that both the path builder and the link builder follow. The link side is the other half of the layout: `spec_link` builds the relative path from one spec to another (relative, because a leading slash means the repository root on GitHub), `link_destination` percent-escapes the characters that would break a markdown destination, and `heading_anchors` and `section_anchor` work out the GitHub anchor of a symbol's section from the graph alone, so a dependency link can land on the section instead of the top. When the anchor cannot be known, the link simply opens the top of the page.

A file is spec-bearing when at least one of its top-level symbols is function-like or type-like. That holds whether or not the declaration is exported, so a file of entirely private code such as an integration-test file still gets a spec, while a barrel file or a file of constants does not. A file whose role is generated (build output such as a codegen'd interface) is never spec-bearing, however much it exports. The symbols that get their own section are chosen by the same kind test, in source order, and constants get none; a container's members are covered inside the container's own section. A directory gets a rollup only when at least two of its immediate files are spec-bearing, which keeps single-file route directories from producing noise. The directory helpers look one level deep, not recursively, and return files in path order so generated pages are stable between runs. Test code is recognised by `is_test_path`.

Whether a path is test code or generated is not decided here: both questions go through the language pack named on the graph, so the layout rules are not tied to one language's conventions. The file also builds the generated-sources report that coverage surfaces: nothing for a language with no such concept, otherwise a count of files with the generated role and the directories the pack knows about, where a count of zero is the actionable case. `symbol_file` takes the file part of a symbol id and `short_name` the part after the last `::`, which is what a section heading uses.

## `link_destination`

### Summary

### Behavior

## `heading_anchors`

### Behavior
Each heading is trimmed and lowercased, then every character is dropped except letters and digits (any script), `_`, `-`, spaces and the combining marks U+0300 to U+036F (which GitHub keeps, so a decomposed accent survives). ## `directory_is_spec_bearing`
`pub fn directory_is_spec_bearing(graph: &Graph, dir_path: &str) -> bool`
### Summary
Decides whether a folder gets a summary page of its own (an `_index.md`). It does when at least two of the files directly inside it are themselves worth documenting, so folders holding a single file don't produce noise.
### Behavior
Calls `spec_bearing_files_in` for the directory and checks that the result has two or more entries. Only immediate children count; files in subfolders are not included. The path is repo-relative with no trailing slash, and the empty string means the repo root, although the rollup task code guards that case separately. The threshold of two exists because route trees such as Next.js are full of single-file directories, and a page for each would be noise. The function has no failure mode: an unknown directory just has no files and returns false.

## `files_in`
`pub(super) fn files_in(graph: &Graph, dir_path: &str) -> Vec<SymbolId>`
### Summary
Returns every file that sits directly in one folder, in alphabetical order, whether or not it is worth documenting. Files in subfolders are not included.
### Behavior
Walks all files in the graph and keeps those whose parent directory equals `dir_path`. Backslashes in the parent are normalised to `/` first, so Windows-style paths compare correctly. A top-level file's parent is the empty string, which matches `dir_path == ""`. Each match is turned back into a symbol id via `graph.find`, and files that cannot be found are dropped. The result is sorted by path string so repeated runs give the same order. It is one directory level, not a recursive walk: nested subdirectories get their own rollup rather than being folded into this one. It scans every file in the graph on each call.

## `spec_bearing_files_in`
`pub(super) fn spec_bearing_files_in(graph: &Graph, dir_path: &str) -> Vec<SymbolId>`
### Summary
Returns the files directly inside a folder that are worth documenting, in alphabetical order. It is the list a folder summary is built from.
### Behavior
Takes the output of `files_in` (already path-sorted) and keeps only the ids for which `file_is_spec_bearing` is true. Because filtering preserves order, the result stays sorted, which keeps generated folder summaries stable between runs. A directory's files have no meaningful declaration order, so path order is the only one used. An empty or unknown directory gives an empty list. Generated files are excluded because `file_is_spec_bearing` rejects them.

## `short_name`
`pub(super) fn short_name(id: &str) -> &str`
### Summary
Gives the short name a section heading uses: the part of a top-level symbol's stable id after the `file::` prefix.
### Behavior
Splits the id on `::` from the right and returns the last piece, borrowed from the input, so no copy is made. An id with no `::`, such as a bare file path, is returned whole. Only the final segment is kept, so an id with several separators (a method id such as `file.ts::Class.method` keeps the dotted part, but a nested path like `a::b::c` gives `c`) loses everything before the last `::`. Two symbols in one file that share a short name therefore get the same heading, which the spec parser cannot tell apart.
### Depends on
- (none)
