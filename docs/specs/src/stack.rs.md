## Summary
This file defines `StackPack`, the single interface through which every language- or framework-specific decision passes, which is what keeps CodeOwl's core (extraction, resolution, spec assembly) free of any one language. A pack answers questions such as which files it reads and how, what role a path plays, how to parse declarations and imports, how to resolve imports to targets, what extra links exist beyond imports (a web call, a database query, a rendered component), whether the stack has a notion of features, which classes are database tables, which test code to leave out of a file summary's input, and what fingerprint decides whether a file's spec is current. Methods with defaults are the optional ones: no feature model, no schema symbols, text kept whole, a whole-text fingerprint, and no generated-source folders. The file implements the trait four times: `TypeScriptNextStack`, `RustStack`, `JavaStack` and `PythonStack`; exactly one is chosen for a repo by `detect`. Only the Rust pack overrides test stripping and the fingerprint; only Java and Python override the table check, and only Java declares generated-source folders. Most methods are thin hand-offs to the code that lives in that language's own file (`extract.rs` and friends for TypeScript, `rust.rs`, `java.rs`, `python.rs`). What is specific to this file is the small set of decisions each pack makes inline: test and generated-code path rules; the Java check that a class is a table when it carries an `Entity` annotation (exact name match) or its own `extends` clause names a Panache entity base, after stripping all generic angle-bracket groups so a bound like `T extends PanacheEntityBase` does not false-match; and the Python check that a class is a table when its base list holds `table=True`, `Base` or `DeclarativeBase`, using a plain comma split that could misparse a nested generic comma. A bare `SQLModel` or `BaseModel` base is deliberately not a table. `for_name` turns a saved pack name back into the pack, falling back to the TypeScript pack for an empty or unknown name, so code that only holds a graph can recover its stack. `typescript_next` returns the TypeScript pack as the default.

## `StackPack`
`pub trait StackPack: Send + Sync + std::fmt::Debug`
### Summary
The one interface a language and framework combination fills in to teach CodeOwl about itself. Everything the language-neutral core needs to know about Rust, TypeScript, Java or Python goes through these methods, so the core never names a language.
### Behavior
One pack is chosen per repo by `detect`. The trait requires `Send + Sync` because the file watcher carries the pack to a background thread, and `Debug` so the structs that hold one can still derive it.

Required methods: `name` returns a stable identifier saved with the cache, so switching packs forces a rebuild. `source_kind(path)` says how a file's contents are read, or `None` if the pack ignores it; a file is walkable exactly when this returns `Some`. `classify(rel_path)` gives the file's role (product, UI primitive, test, generated) for spec ordering. `extract_symbols(rel_path, source)` parses one file into declarations. `extract_imports(rel_path, source)` parses one file's import and re-export statements. `resolve_imports(root, file_imports, graph)` resolves every tracked import in the repo to a target symbol or `None` for externals and failures, and each pack owns its own resolver. `extract_flow_edges` and `resolve_flow_edge` handle the "this file reaches that thing" links the import graph cannot see (a `fetch("/api/..")` call, a `.from("table")` query, a `<Component/>` tag): extraction returns raw strings with no resolution, and resolution is a separate step run per edge once the graph is built, giving `Unresolved` when the string points nowhere. A pack with no such conventions returns an empty list.

Methods with defaults: `feature_model` returns the stack's model of what a feature is, or `None` for a stack without a runtime entry surface, such as a command-line tool or library (only the Rust pack takes the default; the Java pack returns its Quarkus model even for a plain library, which then simply finds zero entry points, so `Some` does not promise that a repo has any feature). It returns a `'static` reference because the model has no state and can be recovered from just a pack name. `is_schema_symbol(sym)` says whether a freshly extracted symbol is a database table, and the generic pipeline retags those as schema symbols, so an ORM model class can count as a table with no `.sql` file; the default is "no persistence model". `strip_test_code(rel_path, source)` returns the source without test code kept inside source files, used only for the text a file summary is written from; the default returns the text unchanged, and the Rust pack drops its `#[cfg(test)]` modules. The file's hashes still cover the whole file. `file_fingerprint(rel_path, source, symbols, imports)` returns the hash that decides whether a file's own spec is current; the default hashes the whole raw text, which can over-report staleness but never hide a change, and a pack overrides it with a rule that ignores edits a summary would not mention (the Rust pack uses shape, doc comments and body literals). `generated_source_dirs()` lists build-output folders that can hold real source files generated from a contract (Maven's `target/generated-sources`, Gradle's `build/generated`) and that a normal ignore file would hide, so the indexer reads them anyway; the default is none, and a repo that has never been built simply has nothing there, which is not an error.

## `detect`
`pub fn detect(root: &Path) -> anyhow::Result<Box<dyn StackPack>>`
### Summary
Works out which language the repo is written in and returns the matching language pack, or fails with a clear message instead of quietly serving an empty index. It runs once at startup.
### Behavior
For each of the four candidates (TypeScript/TSX, Rust, Java, Python) it walks the repo and counts the files the pack classifies as ordinary code, skipping folders that do not define a repo's identity. Test folders (`tests`, `test`, `benches` at the top level, or any path containing `src/test/`) are skipped so a TypeScript fixture read by a Rust test cannot make a Rust repo look like TypeScript. Tooling folders (`utility`, `scripts`, `tools`, `hack`) are skipped so build scripts cannot make a repo look like it has a second language. The walk respects ignore files. A `.sql` schema file is not counted, since it is not ordinary code, so a Rust repo with migrations stays a Rust repo.

Packs with a count above zero are the hits. With exactly one hit, a fresh instance of that pack is returned. With none, it fails, saying no extractable source files were found and naming all four supported stacks. With more than one, it fails listing each stack and its file count and suggests pointing CodeOwl at a subdirectory, since one stack per repo is a deliberate limit. A repo that genuinely mixes two stacks therefore cannot be indexed as a whole. Because tests and tooling are skipped only for the count, they are still parsed once the pack is chosen. The directory-name match is by exact top-level segment, so a nested `scripts` folder deeper in the tree is still counted, and any single code file in a second language outside those folders is enough to make the repo ambiguous.

## `extends_panache_entity`
`fn extends_panache_entity(signature: &str) -> bool`
### Summary
Checks whether a class's signature `extends` one of Panache's two active-record base classes (`PanacheEntity` or `PanacheEntityBase`).
### Behavior
Strips out every balanced `<...>` span in the signature first — a generic type parameter's bound (`class Foo<T extends PanacheEntityBase>`) always sits inside one of these, before the real `extends` clause of the class itself even starts. Without stripping these first, a plain substring search over the whole signature would wrongly match a class whose only relation to `PanacheEntityBase` is an unrelated generic bound, not its own actual superclass.

After stripping, it scans the remaining words for the first `extends` keyword and checks whether the very next word starts with `"PanacheEntity"` — a prefix check deliberately covering both `PanacheEntity` and `PanacheEntityBase` in one comparison. If no `extends` keyword remains at all, it returns `false`.

## `strip_angle_bracket_groups`
`pub(crate) fn strip_angle_bracket_groups(s: &str) -> String`
### Summary
Removes every balanced `<...>` span from a string — Java's generic type parameters and arguments — so text like `"Foo<T extends Bar>"` becomes `"Foo"`.
### Behavior
Walks the string character by character, tracking bracket depth: a `<` increases depth, a matching `>` decreases it, and any character seen while depth is above zero is dropped rather than copied to the output. This isn't a general parser — it assumes `<`/`>` only ever mean generics in whatever text it's given, which holds for a class's own signature (the text before its body) but wouldn't hold inside a method body, where `<`/`>` can be ordinary comparison operators instead.

Used both by `extends_panache_entity`'s `extends`-clause parsing and by the equivalent `implements`-clause parsing elsewhere, since both need to strip the same generic-bound noise before looking for the real superclass or interface name.

Decides whether a Python class declaration is a database table (an ORM — object-relational mapper — model, i.e. Python code that represents a table), by inspecting the class's signature line: its name and parenthesized base classes/keyword arguments (e.g. `class Item(SQLModel, table=True):`).
### Behavior
Finds the parenthesized part of the signature and splits it on commas into individual base-class names or keyword arguments. Returns `true` if any of them, once whitespace is stripped, is exactly `table=True` (SQLModel's convention for marking a model as a real table) or is the bare base class `Base` or `DeclarativeBase` (SQLAlchemy's declarative-base conventions). Deliberately returns `false` for a bare `SQLModel` or `BaseModel` base with no `table=True` — those represent request/response validation schemas, not database tables. The comma split is naive: a base class written with a nested comma, such as a generic type like `Generic[T, U]`, could misparse, but that shape is considered unlikely for a real ORM model class.</content>
