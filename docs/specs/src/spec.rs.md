# src/spec.rs
## Summary
This file is the heart of CodeOwl's spec system: it defines the on-disk document format for every kind of spec (per-symbol/per-file, per-feature, per-directory rollup, and the one whole-repo system spec), reads and writes them, and decides what needs (re)generating and in what order. Each document type follows the same basic recipe — a small hand-parsed YAML frontmatter block holding deterministic hashes, followed by the actual prose content — hand-parsed rather than run through a general YAML library because the shape is entirely CodeOwl's own fixed design, not arbitrary human-authored YAML, so a narrow parser is simpler and easier to reason about than a full general-purpose one.

The file distinguishes what CodeOwl itself computes deterministically (signatures, dependency lists, hashes, the file/rollup "Contents" listings) from what only an LLM writes (summaries, behavior descriptions, feature narratives) — every render function recomputes the deterministic parts fresh rather than trusting a stored snapshot, so they're always accurate even if the underlying code moved since the prose was last written. Staleness itself is tracked through three-part hashes: a symbol or file's own source text, a hash over its dependencies' public shapes, and a hash over the actual generated prose — comparing these against freshly recomputed values is what lets `next_task`/`next_feature_task`/`next_rollup_task`/`next_system_task` figure out exactly what's changed and needs another look, including the quiet "human edited the prose by hand" case, which gets reconciled without any LLM call at all.

Beyond individual documents, this file also computes the whole-repo coverage inventory (`coverage`/`summarize`) and prioritizes what a budgeted `/codeowl generate --all` run should tackle first (`prioritize`) — shared high-fan-in code, then feature specs, then the long tail, then rollups, then tests, with the system spec always last since it's the one document that can only be written once everything it composes from is current. A deterministic, non-LLM quality check (`prose_smells`/`body_smells`/`file_spec_smells`) catches prose that looks like a stub or a cop-out even when its hashes are perfectly current, so a low-quality document doesn't silently escape attention just because nothing in the code moved.</content>

## `classify_in`
`fn classify_in(graph: &Graph, path: &str) -> FileRole`
### Summary
Classifies a repo-relative path's role (ordinary code, test code, a shared UI primitive, generated code) using the classification rules of whichever language stack actually built the given graph, rather than assuming one fixed stack.
### Behavior
Looks up the stack pack by the graph's own recorded `pack_name` (via `stack::for_name`) and delegates to that pack's `classify` method. This exists so that spec prioritization logic works correctly across every supported stack — a Rust repo's `tests/` convention, a TypeScript repo's `*.test.ts` convention, and so on — instead of being hard-wired to always call the TypeScript stack's classification rules regardless of what kind of repo is actually being indexed.</content>

## `spec_path`
`pub fn spec_path(root: &Path, source_path: &str) -> PathBuf`
### Summary
Computes where a given source file's spec document lives on disk, mirroring the source tree under `docs/specs/`.
### Behavior

## `is_test_path`
`pub fn is_test_path(graph: &Graph, path: &str) -> bool`
### Summary
Checks whether a repo-relative path is test code, so spec generation can deprioritize it — documenting the test harness is rarely the point of a spec corpus, so test files sort to the very bottom of a `--all` generation run rather than competing with real product code for attention.

Delegates to `classify_in` and checks whether the result is `FileRole::Test`. ## `file_is_spec_bearing`
`pub fn file_is_spec_bearing(graph: &Graph, file_id: SymbolId) -> bool`
### Summary
Decides whether a file is worth generating a spec document for at all — the granularity rule that keeps a barrel file, a const-only route config, or purely metadata boilerplate from getting a useless, empty-feeling document.
### Behavior
Checks the file's top-level symbols for at least one that is both exported and either a `Callable` (function/method) or a `Container` (class/struct-like type). ## `spec_bearing_children`
`fn spec_bearing_children(graph: &Graph, file_id: SymbolId) -> Vec<SymbolId>`
### Summary
Lists the top-level symbols in a file that get their own section within that file's spec document — the individual functions and types worth documenting one at a time.
### Behavior
Filters a file's top-level children down to `Callable`s and `Container`s only, regardless of whether they're exported — unlike `file_is_spec_bearing`'s stricter "does this file deserve a document at all" gate, this includes unexported symbols too, since the point of a file spec is to explain how the file works internally, not only to document its public API. A top-level `Value` (a plain constant) never gets its own subsection. ## `directory_is_spec_bearing`
`pub fn directory_is_spec_bearing(graph: &Graph, dir_path: &str) -> bool`

## `files_in`
`fn files_in(graph: &Graph, dir_path: &str) -> Vec<SymbolId>`
### Summary
Lists every file directly inside a given directory — one directory level only, not a recursive walk of the whole subtree, so a nested subdirectory's files aren't folded into this directory's own listing.
### Behavior
Filters every file in the graph down to those whose parent path exactly matches `dir_path`, comparing the file's own containing-directory path against the given one (with backslashes normalized to forward slashes, so this works consistently regardless of platform path separators). A file in a nested subdirectory has a different parent path and is excluded — it belongs to its own directory's listing instead, which is how directories end up with their own separate rollup documents rather than one giant rollup covering an entire subtree. Results are sorted by string id for deterministic ordering.</content>

The three hashes stored alongside a spec entry that together decide whether it's still current, stale, or needs regenerating — capturing "did the symbol's own text change", "did something it depends on change", and "is this the prose we actually wrote."
### Behavior
`source_hash` is the symbol's or file's own content fingerprint at the time the spec was written. `deps_hash` is a hash over every resolved dependency's `interfaceHash` (a hash of a symbol's public signature — see `GLOSSARY.md`) as observed at generation time; comparing it against a freshly recomputed value catches the case `source_hash` alone can't see — nothing in this symbol's own text changed, but something it imports had its public shape change. `spec_hash` is a hash of the actual generated prose, used to detect whether the stored spec content still matches what was last written (relevant for change detection unrelated to code drift, like manual edits). Together these three let CodeOwl distinguish "the code moved" from "the dependency's public surface moved" from "the prose itself is different than expected," which is the basis for the missing/current/stale status reporting throughout the rest of this file.</content>

## `dependency_lines`

## `symbol_span_text`

    rel_path: &str,
    sym: &Symbol,
) -> Result<String>`
### Summary
Reads the actual source text a symbol's spec should be based on — its own line span, plus the line spans of any of its children that live elsewhere in the file (a case that only arises for a Rust type whose separate `impl` blocks were merged into it during extraction). ## `next_task`
`pub fn next_task(graph: &Graph, root: &Path, target_file_id: SymbolId) -> Result<Option<SpecTask>>`
### Summary
The heart of CodeOwl's generation loop at file granularity: given a file, figures out the single next thing (one symbol, or the file's own summary) that still needs writing — or `None` if the file isn't worth a spec at all, or everything on it is already current. This is what `get_next_spec_task` calls repeatedly to drive a `/codeowl generate` run, one step at a time.
### Behavior
Returns `None` immediately if the file isn't spec-bearing. Otherwise it reads the file's existing spec (if any) and walks its spec-bearing symbols in order. For each symbol, it compares four possible states — whether the symbol's source/dependencies changed (`symbol_changes`) and whether its stored prose was hand-edited since generation (`symbol_prose_is_human_edited`) — following the four-case "Human corrections" rule from `ARCHITECTURE.md`:
- **Never generated at all** (no stored hash for this symbol): returns a fresh `Symbol` task immediately, `prior: None`.
- **Case 1 — nothing changed, no human edit**: normally skipped and the loop continues to the next symbol, *except* if the stored prose fails a deterministic quality check (`prose_smells`) — a low-quality phrase a reader would distrust — in which case a fresh task is returned anyway, with no `prior` since there's nothing worth preserving from prose that's already flagged.
- **Case 2 — source changed, no human edit**: a plain regeneration task, `prior: None`.
- **Case 3 — source unchanged, but a human edited the prose**: reconciled *silently*, with no task returned and no LLM call — `reconcile_symbol_hash` just re-stamps the hash to match the human's edit, and the loop continues to the next symbol.
- **Case 4 — both source changed and a human edit exists**: a regeneration task carrying the human's prior prose as `prior`, so the writing agent can preserve whatever of their correction is still accurate rather than silently discard it.

Once every symbol is current (or reconciled), it applies the same four-case logic to the file's own `## Summary`, with one added wrinkle: a spec object can exist on disk purely because a symbol was submitted first (which lazily creates a blank `FileSpec` shell), even though the file's own summary was never actually written — detected by an empty `spec_hash`, the file-level analogue of a missing per-symbol hash entry. In that case, or if no spec exists at all yet, a fresh `File` task is returned. ## `submit`
`pub fn submit(graph: &Graph, root: &Path, id: &str, content: &str) -> Result<HashPair>`
### Summary
Persists an agent's LLM-written prose for a symbol or file id — the write side of the generation loop, called by `submit_spec`'s MCP handler. Returns the hashes the persisted entry now carries.
### Behavior
Looks up the id in the graph and branches on whether it names a file or a symbol.

For a **file** id, the raw `content` is treated as plain prose (trimmed) and checked against the quality smell check (`reject_if_smelly`) before anything is written. A fresh `HashPair` is built from the file's current `source_hash`, a freshly computed `file_dependency_hash`, and a hash of the submitted summary text. The existing spec (or a blank one, if none exists yet) is updated with the new summary and hash, its symbol ordering fixed up via `reorder_symbols`, and the whole spec written back to disk.

For a **symbol** id, it first requires the symbol to have a containing file (a symbol with no parent can't be attached to any spec document), then extracts the `### Summary` and `### Behavior` sections out of `content` — failing with a clear error if either is missing or empty, since a symbol-level spec's structure is a hard requirement, not optional. Both sections are then checked against the quality smell check together, with each finding labeled by which section it came from (`"Summary: ..."` / `"Behavior: ..."`) so the error message tells the agent exactly where to fix it. A `HashPair` is built from the symbol's `source_hash`, a freshly computed `dependency_hash`, and a hash of the combined summary+behavior text. The symbol's entry is upserted into both the spec's `symbols` hash list and its `sections` prose list, the file's spec is loaded (or started blank), symbol ordering is fixed up, and the whole spec is written back to disk.

In both branches, a quality-check failure aborts the whole operation before anything is written — nothing partial is ever persisted.</content>

## `CoverageItem`
`pub struct CoverageItem`

## `prose_smells`
`pub fn prose_smells(text: &str) -> Vec<String>`
### Summary
A deterministic, non-LLM check for prose that looks like a stub or an evasion rather than genuine content — independent of hash-based staleness entirely, since a spec can have perfectly matching hashes and still contain worthless prose. This is what catches the two failure modes called out by name in `CLAUDE.md` and the generation prompt: a phrase that defers the reader elsewhere instead of actually explaining the behavior, and prose so short it can only be a placeholder — both found concretely in real pre-quality-check specs during an audit (things like a one-clause non-answer or a two-word deflection).
### Behavior
Checks the (lowercased) text against a small, explicitly named denylist of deflecting phrases that punt the reader back to reading the code themselves instead of actually describing what it does, flagging one smell if any of them appear anywhere in the text. Separately, flags a second smell if the text has fewer than four whitespace-separated words — too short to be a real explanation of anything. Deliberately not exhaustive or clever: a small fixed list plus a word-count floor, both easy to reason about and cheap to extend if a new failure mode is ever found in practice, rather than an attempt at a general-purpose quality classifier.</content>

- (none)

## `file_spec_smells`
`pub fn file_spec_smells(
    graph: &Graph,
    root: &Path,
    file_id: SymbolId,
    spec: &FileSpec,
) -> Vec<String>`
### Summary
Combines every quality smell found anywhere in a file's spec — its own summary, every symbol's prose, and a whole-file structural check for a specific historical bug's signature — into one list. This is the coarse "does this document need another look at all" signal `get_spec_coverage` needs at the whole-document level; checking one specific symbol's own prose directly is what `get_spec` does instead, for a narrower answer.
### Behavior
Checks the file's own summary against `prose_smells`, but only if the file summary has actually been generated at all — a file spec created lazily as a shell around a just-submitted symbol (via `FileSpec::blank`) has an empty summary and an empty `spec_hash`, and that empty state is a normal mid-generation gap, not a genuine short-prose smell, so it's skipped rather than wrongly flagged. Every symbol's summary and behavior prose is also checked individually via `prose_smells`, with results combined.

If the file has two or more symbols, it also runs a structural check for a specific historical bug's shape: every symbol in the file having the exact same, non-empty list of *resolved* (intra-repo) dependencies — comparing only resolved lines, since several symbols in a small module all sharing a common `externals: ...` line (everyone returning `anyhow::Result`, say) is entirely normal and not a sign of anything wrong. If every symbol's resolved dependency list matches and is non-empty, it flags `"identical_dependencies_across_symbols"` — the fingerprint of an older bug where dependencies were attributed to the whole file rather than scoped per symbol. That bug is structurally impossible to reproduce in a freshly-generated spec after the per-symbol scoping fix, but this check remains as a way to detect any spec that predates the fix and was never regenerated since. The final combined list is sorted and deduplicated.</content>

## `file_pending_generations`

## `prioritize`
`pub fn prioritize(items: Vec<CoverageItem>, graph: &Graph) -> Vec<CoverageItem>`
### Summary
Filters a full coverage inventory down to just the documents still needing attention, and orders them the way a budgeted `/codeowl generate --all --budget=N` run should spend its budget — high-value shared code first, then feature specs, then the long tail, then rollups, then test code, with the system spec always last since it can only be written once everything else is current.
### Behavior
First computes a fan-in cutoff for the "shared code" tier: among every candidate `Domain`-role file in the *entire* inventory (not just the ones still pending), it takes the highest fan-in values down to the `SHARED_CODE_MAX_FILES`-th one, floored at `SHARED_CODE_FAN_IN`. This cutoff is deliberately computed off the full `items` list rather than the filtered pending list — anchoring it to the whole repo means that once the real top-N shared files are generated and become current, the shared-code tier genuinely empties out and features take priority, rather than the cutoff silently recomputing on each run and promoting a fresh batch of files into tier 0 forever.

It then filters to items that are non-current or carry a quality smell — deliberately including a `"current"` item if it's smelly, since hash-based staleness only verifies a spec's inputs haven't moved, never that its prose was ever actually meaningful; without this, a low-quality stub, once written, would stay hash-`"current"` forever and a `--budget=N` run could complete while silently leaving known-bad content untouched.

The remaining items are sorted by a composite key: first by tier (0 = high-fan-in shared domain files, 1 = feature specs, 2 = the long tail of files — everything below the fan-in cutoff, plus UI primitives and generated files at any fan-in, 3 = directory rollups, 5 = test-code files, 6 = the system spec, 7 = anything unrecognized); then within a tier, by urgency (`"missing"` before `"stale"` before a merely-smelly `"current"` item); then by descending fan-in; then by id, for a stable, fully reproducible order run to run.</content>

- `src/graph.rs::Graph` — crate::graph
- `src/lang.rs::FileRole` — crate::lang
