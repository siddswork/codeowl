# src/spec.rs
## Summary
Everything about the spec documents themselves: where they are saved under `docs/specs/`, what they look like, how CodeOwl tells whether each one is still accurate, and what work is left. It covers five kinds of document, namely a file spec (one per source file, with a section per function or type), a folder summary, a feature spec, and a single system spec for the whole repo. Each one stores fingerprints of the code and dependencies it was written from, so a later change can be noticed without comparing prose. The file decides which files and folders deserve a document at all, builds the "what to write next" tasks the generate loop asks for, checks and saves what the agent submits (rejecting empty or evasive text), and quietly accepts hand edits. It also produces the coverage report: current, stale and missing counts, quality warnings, leftover documents whose subject was deleted, and the order in which a limited budget should be spent, with widely imported code first and the system summary last.

## `classify_in`
`fn classify_in(graph: &Graph, path: &str) -> FileRole`
### Summary

## `dependency_lines`

## `scoped_symbol_deps`

    graph: &Graph,
    from_file: &str,
    symbol_text: &str,
    self_id: Option<SymbolId>,
) -> ScopedDeps`
### Summary
Given one symbol's source text, finds which of its file's imports it actually mentions and sorts them into in-repo targets and outside packages.
### Behavior
Goes through every import in the graph and keeps those that come from `from_file`, whose imported name appears as a whole word in `symbol_text` (`contains_identifier`), and whose target is not `self_id`. The last check matters for the synthetic edge CodeOwl adds from a trait impl to its type in the same file: that edge's imported name is the type's own name, which the type's own text always contains, so without the exclusion a type would appear to depend on itself. Duplicates are skipped and `externals` is sorted at the end; `resolved` keeps graph order and is not de-duplicated. The text match is a heuristic: a name inside a comment or string would count too.

## `merged_symbol_spans`
`pub(crate) fn merged_symbol_spans(graph: &Graph, sym: &Symbol) -> Vec<[usize; 2]>`
### Summary

### Behavior
Starts with the symbol's own line range. ## `cap_generation_text`
`pub(crate) fn cap_generation_text(text: String, max_bytes: usize) -> String`
### Summary
Shortens a piece of text so it fits a byte limit, and adds a visible note when it had to cut. This keeps a very large class from producing an agent task bigger than the MCP client can accept, without the agent being unaware that text is missing.
### Behavior
If the text is already within `max_bytes` it is returned unchanged. Otherwise the limit includes the truncation marker. All subtractions are saturating or bounded, so tiny limits, including 0, cannot underflow or panic.

## `parse`

### Summary

## `next_task`
`pub fn next_task(graph: &Graph, root: &Path, target_file_id: SymbolId) -> Result<Option<SpecTask>>`
### Summary
Decides what spec writing a file still needs next: a particular function or type, the file's own summary, or nothing. It is the core of the generate loop, which keeps asking until the answer is "nothing left".
### Behavior
Returns `Ok(None)` at once if the file is not spec-bearing. Otherwise it loads the existing spec document (if any) and goes through the file's spec-bearing symbols in declaration order, deciding for each by whether the code or dependencies changed (`symbol_changes`) and whether a human edited the prose (`symbol_prose_is_human_edited`):
- Never written: return a `Symbol` task with no `prior`.
- Unchanged and not edited: skip, unless the prose fails the quality check (`prose_smells`), in which case it is offered again for a rewrite.
- Changed, not edited: return a task with no `prior`.
- Unchanged but hand-edited: quietly record the edit with `reconcile_symbol_hash`, with no task, and move on.
- Changed and hand-edited: return a task whose `prior` is the human's text, so it can be kept where still accurate.

Once all symbols are done, the file's own summary is judged the same way. An empty file `spec_hash` means the file entry was never written, which can happen even when symbols were stored first, so it gets a `File` task. Otherwise the same four cases apply, with smelly prose also triggering a rewrite and the unchanged-but-edited case reconciled with `reconcile_file_hash`. Despite being safe to call repeatedly, it may write a small fix to disk in those reconcile cases. It errors if the id is not a file or if disk reads and writes fail.

- `src/graph.rs::Graph` — crate::graph
- `src/symbol.rs::SymbolId` — crate::graph
- `src/symbol.rs::Symbol` — crate::symbol
- externals: anyhow, std

## `reject_if_smelly`

### Summary
A small guard that turns a non-empty list of quality-check failures into an error, refusing to let low-quality spec prose be persisted. ## `submit`
`pub fn submit(graph: &Graph, root: &Path, id: &str, content: &str) -> Result<HashPair>`
### Summary
Saves prose an agent wrote for a file or for one function or type into that file's spec document, and returns the fingerprints recorded alongside it. It is the write half of the generate loop, and it rejects text that is too thin to be useful.
### Behavior
Looks the id up in the graph, and fails with "unknown id" if it is absent. Then there are two cases.

File id: the content is trimmed and checked with `prose_smells`; a failure is returned as an error naming what tripped. The existing spec is loaded from disk (or a blank one created), the summary and hashes replaced, symbols reordered to declaration order, and the document written.

Symbol id: the symbol must have a parent file. Hashes come from the symbol's `source_hash`, its `dependency_hash`, and a hash of summary and behavior joined by a newline. The symbol's entry and prose are inserted or replaced (`upsert`, `upsert_section`), symbols reordered, and the file written.

Nothing is written when validation fails, so a rejected submission leaves the existing spec intact. The returned `HashPair` is what staleness checks later compare against.

## `prose_smells`
`pub fn prose_smells(text: &str) -> Vec<String>`
### Summary
A deterministic, non-LLM check for prose that looks like a stub or an evasion rather than genuine content — independent of hash-based staleness entirely, since a spec can have perfectly matching hashes and still contain worthless prose. This is what catches the two failure modes called out by name in `CLAUDE.md` and the generation prompt: a phrase that defers the reader elsewhere instead of actually explaining the behavior, and prose so short it can only be a placeholder — both found concretely in real pre-quality-check specs during an audit (things like a one-clause non-answer or a two-word deflection).
### Behavior
Checks the (lowercased) text against a small, explicitly named denylist of deflecting phrases that punt the reader back to reading the code themselves instead of actually describing what it does, flagging one smell if any of them appear anywhere in the text. Separately, flags a second smell if the text has fewer than four whitespace-separated words — too short to be a real explanation of anything. Deliberately not exhaustive or clever: a small fixed list plus a word-count floor, both easy to reason about and cheap to extend if a new failure mode is ever found in practice, rather than an attempt at a general-purpose quality classifier.</content>
### Depends on
- (none)

## `file_spec_smells`
`pub fn file_spec_smells(
    graph: &Graph,
    root: &Path,
    file_id: SymbolId,

### Summary
Scans a whole file spec for signs of poor quality and returns a list of problem labels, empty if it looks fine. The coverage report uses this to flag a spec that is up to date by hash but whose prose should not be trusted.
### Behavior
Collects problems from three places, then sorts and de-duplicates them. The file summary is checked with `prose_smells` only once it has actually been written; an empty `spec_hash` means the file entry was never generated, and a blank summary in that state is a mid-generation gap rather than a cop-out. If a symbol id cannot be resolved the lists are not all comparable and the identical-dependencies check is skipped. It never fails.

## `system_status`
`fn system_status(graph: &Graph, root: &Path) -> Result<(String, Vec<String>)>`
### Summary
Works out whether the top-level repo summary is missing, stale or current, with any quality problems listed separately.
### Behavior
If there is no stored system spec the status is `missing` with no smells. Otherwise it joins the current module hashes and the current feature hashes into one list, joins the stored module and feature hashes into another, and compares them. Equal lists mean `current`, and any difference means `stale`: a module or feature spec was rewritten, went stale (its hash became empty), or was added or removed. The smells are `body_smells` of the stored body and are independent of the status. Errors if reading any of the underlying spec files fails.

## `within_scope`
`pub(crate) fn within_scope(path: &str, scope: &str) -> bool`
### Summary
Tells whether a file or folder path lies inside a given folder, matching whole path pieces and not just starting letters. It is used to narrow coverage reports and code searches to one directory.
### Behavior
Returns true if `scope` is empty (everything matches), if `path` equals `scope`, or if `path` starts with `scope` followed by a `/`. The slash is what keeps matching honest: scope `lib/email` matches `lib/email` and `lib/email/send.ts` but not `lib/email.ts` or `lib/email-utils/x.ts`, which a plain string-prefix test would wrongly accept. A trailing slash on `scope` is not handled specially, so `lib/` would only match paths that begin with `lib//`. The coverage code and `search_code` both use it so their boundaries agree. Pure function, no failure mode.

## `coverage`
`pub fn coverage(graph: &Graph, root: &Path, scope: Option<&str>) -> Result<Vec<CoverageItem>>`
### Summary
Builds the full inventory of documents a repo should have and the state of each: file specs, folder summaries, feature specs and the system spec. The coverage report is made from this list.
### Behavior
Returns a list of `CoverageItem`s in this order. First, every spec-bearing file in path order, with its status and smells from `file_status`, its `fan_in`, and its remaining `generations` from `file_pending_generations`. Second, every module folder from `enumerate_modules` as a `rollup:<dir>` item, costing one generation unless current. If `scope` is given, files and folders outside that directory (by `within_scope`) are skipped. Third, only when there is no `scope`, every feature entry point as a `feature:<slug>` item and finally the single `system` item, each costing one generation unless current. Features and the system spec are repo-wide ideas, so any scope removes them entirely, even an empty one. The first error from reading any spec file or hashing a participant stops the whole call and is returned.

## `CoverageSummary`
`pub struct CoverageSummary`
### Summary
The headline numbers of a coverage report: how many documents are current, stale or missing, how many have quality problems, and what a complete run would cost. It also gives two percentages that answer different questions: how much is written, and how much of that is still right.
### Behavior
Stored fields are `current`, `stale`, `missing`, `smelly` and `generations_remaining`. `smelly` counts items of any status with at least one quality problem, so it overlaps `current` on purpose, to surface specs that are up to date by hash but poor in content. `generations_remaining` is the sum of every item's cost and is the `--budget` value for a complete pass; a file with 20 uncovered symbols counts 21.

Three methods derive the rest. `total()` returns `current + stale + missing`, not stored so it cannot drift out of sync. `freshness()` is `current / (current + stale)`, ignoring missing documents, because writing a spec and regenerating one are different fixes; it returns 1.0 when nothing exists yet. `coverage_ratio()` is `(current + stale) / total`, the share that has any spec at all, and returns 1.0 for an empty report. A repo can score high on one and low on the other.
### Depends on
- (none)

## `weighted_freshness`
`pub fn weighted_freshness(items: &[CoverageItem]) -> f64`
### Summary
A freshness score that counts a stale, widely imported file as a bigger problem than a stale file nobody imports. It says how much of the code that others depend on has an up-to-date spec.
### Behavior
Considers only file items that already have a spec (status not `missing`); missing ones are a coverage problem, not a freshness one. It returns the sum of `fan_in` over the current files divided by the sum of `fan_in` over all of those files, so each file's weight is its import fan-in. When the total fan-in is 0 there is nothing to weight by, so it falls back to the plain share of current files among them, and returns 1.0 if there are none at all. The result is between 0 and 1. A repo where only unimportant files are stale scores close to 1, and one where a hub file is stale scores low even if most files are fine. It is a pure calculation with no failure mode.

- (none)

## `OrphanedSpec`
`pub struct OrphanedSpec`
### Summary
Describes one spec on disk whose subject no longer exists, such as a deleted file or a removed feature. It is leftover clutter to delete, not something to regenerate.
### Behavior
Fields: `id` uses the same names as the coverage report (a feature has the `feature:` prefix, a folder summary the `rollup:` prefix) and names what is gone, so it should not be passed to the generate tools. `kind` is one of `file`, `rollup`, `feature` or `symbol`; the system spec is never orphaned because it always has a repo to summarise. `path` is relative to the repo root: for a file, rollup or feature it is the orphaned document itself, which a caller can delete. For a `symbol` it is the containing file's spec, because only a section inside a still-valid document is dead, and that section is dropped automatically the next time the file is written (`reorder_symbols`). Different from stale, where the target still exists. Plain data, no logic.

## `find_orphaned_specs`
`pub fn find_orphaned_specs(
    graph: &Graph,
    root: &Path,
    scope: Option<&str>,
) -> Result<Vec<OrphanedSpec>>`
### Summary
Finds spec documents whose subject has been deleted, so they can be removed. The coverage report only looks outward from the code, so a spec for a file that no longer exists would never show up there. This walks the spec folder inward to catch those.
### Behavior
Returns an empty list at once if `docs/specs/` does not exist. Otherwise it collects orphans from three places:
- Features: only when no `scope` is given, it lists the `.md` files in `docs/specs/_features/`, treats each filename (without the extension) as a slug, and reports any slug that no current feature entry point has. A failure listing that folder is an error.
- Files and folder summaries: it delegates to `find_orphaned_files_and_rollups`, passing the sets of live file paths and live module folders, so a spec counts as an orphan when its implied target is not in those sets.
- Symbol sections: `find_orphaned_symbol_sections` reports sections inside still-valid file specs whose function no longer exists.

Targets are worked out from the mirrored folder layout and filenames alone (a file spec is its source path plus `.md`, a rollup is an `_index.md`, a feature is `_features/<slug>.md`), so no document is parsed. `scope` narrows files and folders by directory, and removes feature orphans entirely because a feature has no directory of its own. It only reports and never deletes.

## `find_orphaned_symbol_sections`
`fn find_orphaned_symbol_sections(
    graph: &Graph,
    root: &Path,
    scope: Option<&str>,
    orphans: &mut Vec<OrphanedSpec>,
) -> Result<()>`
### Summary
Finds sections inside a still-existing file's spec that describe a function or type since deleted from the file. Without this, the file could look fully up to date while still carrying a description of code that is gone.
### Behavior
Goes through every file in the graph in path order, skipping those outside `scope`, and skipping files with no stored spec. For each remaining file it collects the ids of its current spec-bearing symbols and compares them to the symbol ids stored in the spec. Each stored id missing from the current set is added to `orphans` as an `OrphanedSpec` of kind `symbol`, with the path of the containing file's spec (`docs/specs/<path>.md`). It only covers files still in the graph, because a deleted file's whole spec is already reported as a file orphan, and double-reporting would be noise. The status check cannot see these, since it only walks current symbols. The dead section is dropped automatically the next time the file's spec is written. Errors if a spec file cannot be read.

## `find_orphaned_files_and_rollups`
`fn find_orphaned_files_and_rollups(
    dir: &Path,
    specs_root: &Path,
    features_dir: &Path,
    live_files: &std::collections::HashSet<String>,
    live_modules: &std::collections::HashSet<String>,
    scope: Option<&str>,
    orphans: &mut Vec<OrphanedSpec>,
) -> Result<()>`
### Summary
Searches the spec folder tree for file specs and folder summaries whose subject no longer exists. It is the file-and-folder half of orphan detection and adds what it finds to a shared list.
### Behavior
Reads the directory entry by entry. It skips the `_features/` folder (features are matched by name elsewhere) and recurses into every other subfolder. For a file it works out the path relative to `docs/specs/` with backslashes turned into `/`, then decides:
- `_index.md` files: one directly at the top is the system spec and is skipped, since it can never be orphaned. Otherwise the folder path is the part before `/_index.md`; unless it is outside `scope`, it is reported as a `rollup:<dir>` orphan when it is not in `live_modules`.
- Other `.md` files: the source path is the filename minus `.md`. Anything outside `scope` is skipped. The file must be readable and must actually parse as a CodeOwl-written spec (`parse` succeeds), so a hand-written guide such as `STYLE.md` is never flagged, as telling a human to delete their own document would be a false positive. A parsed spec whose source path is not in `live_files` is reported as a `file` orphan.

Files with other extensions are ignored. Errors reading a directory (with a "reading <path>" message) are returned, but an unreadable individual file is silently skipped.

- externals: anyhow, std

## `top_stale_by_impact`
`pub fn top_stale_by_impact(items: &[CoverageItem], n: usize) -> Vec<CoverageItem>`
### Summary
Picks the files whose out-of-date specs would do the most harm, ranked by how many other files import them. It answers "what should I fix first" and is separate from the order a budgeted generation run follows.
### Behavior
Keeps only file items that need attention, meaning the status is not `current` or the spec is current but has quality problems. Folder summaries, features and the system spec are left out since only files have a real fan-in. The candidates are sorted by `fan_in`, highest first, and cut to the first `n`. The sort is stable, so files with equal fan-in stay in the order the coverage list gave them (path order). It returns clones and has no failure mode; `n` of 0 gives an empty list.

## `by_kind`
`pub fn by_kind(items: &[CoverageItem]) -> Vec<(String, CoverageSummary)>`
### Summary
Splits the coverage list by document type (file, rollup, feature, system) and summarises each group, so a report can say how many feature specs exist and how many are current.
### Behavior
For each kind in the fixed order `KIND_ORDER`, it picks the items of that kind and, if there are any, calls `summarize` on them and returns the pair of kind name and `CoverageSummary`. A kind with no items is left out rather than shown as an all-zero row, so a scoped coverage call that never produces feature or system items simply has no such rows. Using the same `summarize` as every other summary means a count such as "total feature specs" is read from one calculation, never counted a second way. The output order follows `KIND_ORDER`, not the input order. It cannot fail.

## `module_of`
`fn module_of(item: &CoverageItem) -> Option<String>`
### Summary
Says which folder a coverage item belongs to when results are grouped by folder. Files and folder summaries have one; features and the system spec do not, because they cover the whole repo.
### Behavior
For a file item the folder is the parent directory of its path, so `lib/email/foo.ts` goes under `lib/email`. For a rollup item it is the folder the rollup summarises, found by stripping the `rollup:` prefix, so `rollup:lib/email` lands in the same group as the files in `lib/email`, which gives a true "what is left in this folder" count. Any other kind returns `None`, as does a path with no parent. A file at the repo top level, whose parent is the empty string, is grouped under `"."` and never under an empty name. No failure beyond returning `None`.

## `by_module`
`pub fn by_module(items: &[CoverageItem]) -> Vec<(String, CoverageSummary)>`
### Summary
Groups the coverage list by folder and summarises each group, so a report can show how documented each directory is. A folder's own summary page counts together with the files inside it.
### Behavior
For each item it asks `module_of` for its folder and skips items with none (features and the system spec). Items are collected into buckets by folder name, using a linear search of the existing buckets, which is fine for the number of folders in a repo. Buckets are sorted by path, so the output is deterministic and reads like a file tree, and each is summarised with `summarize`. The result is a list of folder path and `CoverageSummary` pairs. Nothing can fail; an empty input gives an empty list.

## `prioritize`
`pub fn prioritize(items: Vec<CoverageItem>, graph: &Graph) -> Vec<CoverageItem>`
### Summary
Takes the full coverage list, keeps only the documents that still need work, and puts them in the order a limited generation budget should be spent. Widely used shared code comes first, because its written summaries make every later spec better, and the system summary comes last, because it can only be written once everything below it is done.
### Behavior
First it fixes the cutoff for the top tier: the larger of `SHARED_CODE_FAN_IN` and the `SHARED_CODE_MAX_FILES`-th highest fan-in among all domain files in the whole repo. It is computed before filtering on purpose. Computed from only the pending items, it would move on every run as the top files got finished and quietly promote the next batch forever; anchored to the whole repo, the top tier empties once the real top files are current. Ties at the cutoff can make the tier slightly larger.

Items are kept when their status is not `current`, or when they are current but have quality problems, because matching hashes never prove the prose was meaningful and filtering them out would leave known-bad text in place after a "complete" run.

Sorting uses a tier number, then urgency, then fan-in, then id. Tiers: 0 shared domain files at or above the cutoff, 1 feature specs, 2 other files (the long tail, including low-level helper files at any fan-in), 3 folder summaries, 5 test code (always after product code whatever its fan-in), 6 the system spec. A generated-code file is mapped to tier 2 but never reaches here, because such files are excluded earlier. Within a tier a `missing` item comes before a `stale` one, which comes before a merely smelly one; then higher fan-in first; then id for a stable, repeatable order.
