## `RouteLiteral`
`pub struct RouteLiteral`
### Summary
One `fetch("/api/...")` call found anywhere in a file's client code — the raw evidence CodeOwl uses to connect a page to the API route it actually calls, since that connection is a string match, not an `import`.
### Behavior
`from_file` is the file the call was found in. `static_path` is the matched path, already stripped of any query string and guaranteed to start with `/api/`. The search isn't limited to top-level code — these calls are almost always inside an event handler or a `useEffect`, so the whole file is scanned regardless of nesting. `RouteLiteral`s are persisted on the `Graph` itself (the same way a `ResolvedImport` is) so that `get_next_spec_task` doesn't have to re-walk every file's syntax tree (the structure `tree-sitter` produces from the source text) on every call — they're computed once and read back out.
### Depends on
- (none)

## `walk_for_fetch`
`fn walk_for_fetch(node: Node, source: &str, rel_path: &str, out: &mut Vec<RouteLiteral>)`
### Summary
The recursive tree-sitter visitor behind `extract_route_literals` — checks whether a node is a `fetch(<literal>)` call and recurses into every child.
### Behavior
At each node: if it's a `call_expression` whose `function` field is the bare identifier `fetch` and whose first argument yields a static path via `static_path_from_literal`, a `RouteLiteral` is pushed. The identifier check is literal — `window.fetch(...)` or an aliased `f(...)` is not matched. Then it descends into all children unconditionally, so nesting depth doesn't matter and a file can contribute many literals. Only the *first* argument is inspected; a second `RequestInit` argument is ignored.
### Depends on
- externals: tree_sitter

## `static_path_from_literal`
`fn static_path_from_literal(node: Node, source: &str) -> Option<String>`
### Summary
Extracts a fully-static `/api/...` path from the first argument of a `fetch` call — a plain string, or a template string whose path portion has no interpolation. Returns `None` rather than guess at a partially-dynamic path.
### Behavior
For a `string` node it reads the inner content and defers to `path_from_raw` with `path_complete = true`. For a `template_string` it takes named children only (skipping the backtick tokens); if the first isn't a `string_fragment` it bails. It then decides whether the path is complete: it is if there's no `${...}` substitution at all, *or* if the static fragment already contains a `?` — meaning any later interpolation lands in the query string, which is stripped anyway, not in the path. That completeness flag is passed to `path_from_raw`, which is what actually enforces the `/api/` prefix and drops the query string. Any other node kind → `None`.
### Depends on
- externals: tree_sitter

## `path_from_raw`
`fn path_from_raw(raw: &str, path_complete: bool) -> Option<String>`
### Summary
The final filter turning a raw literal string into an accepted route path: drops the query string, keeps it only if it begins with `/api/`.
### Behavior
Bails immediately (`None`) when `path_complete` is false — the caller has decided an interpolation makes the path unreliable. Otherwise it takes everything before the first `?` and returns `Some(that)` iff it starts with `/api/`. So `/api/submit?x=1` → `Some("/api/submit")`, `/other/thing` → `None`, `https://…` → `None`. The `/api/` gate is what scopes route-literal resolution to Next.js App Router API routes specifically.

## `resolve_route_literal`
`pub fn resolve_route_literal(graph: &Graph, static_path: &str) -> Option<SymbolId>`
### Summary
Turns an API path written in code, such as `/api/users/42`, into the route file that handles it, by following the Next.js folder naming convention. It is how a page's `fetch("/api/...")` call is connected to the server code behind it.
### Behavior
Strips a leading `/api/` from the path and splits the rest on `/`, dropping empty pieces. It then looks through the repo's files for one whose own route path (from `api_route_segments`, which only recognises `app/api/.../route.ts`-style files) has the same number of pieces and where each piece either is a dynamic segment (`[id]`, `[...slug]`, which matches any single piece) or equals the corresponding piece exactly. The first such file in graph order is returned as its arena id, so if two route files could both match, only one is reported. There is no prefix or fuzzy matching: the counts must be equal, so an incomplete path never matches, and a guard elsewhere (`static_path_from_literal`) keeps incomplete paths from reaching here. A catch-all segment is compared as one piece, so it does not absorb several path pieces. If no file matches it returns `None`. Pure read.
### Depends on
- `src/graph.rs::Graph` — crate::graph
- `src/symbol.rs::SymbolId` — crate::graph

## `api_route_segments`
`fn api_route_segments(file_id: &str) -> Option<Vec<&str>>`
### Summary
Given a repo-relative file path, returns its API-route path segments if it *is* a Next.js App Router API route file — `app/api/<segments>/route.ts` — or `None` otherwise.
### Behavior
Requires both the `app/api/` prefix and the `/route.ts` suffix; either missing → `None`. The middle is split on `/` into borrowed segments, dynamic markers (`[id]`) included verbatim. Only `route.ts` is recognised, not `route.tsx` or `route.js` — a Phase-1 narrowing. This is the candidate-side half of `resolve_route_literal`'s match.

## `is_dynamic_segment`
`fn is_dynamic_segment(seg: &str) -> bool`
### Summary
Whether a route path segment is a Next.js dynamic placeholder — `[id]`, `[slug]`, `[...rest]` — which matches any literal segment during route resolution.
### Behavior
A bracket check: `true` iff the segment starts with `[` and ends with `]`. It doesn't distinguish single (`[id]`) from catch-all (`[...slug]`) forms — both are treated as "matches one literal segment", which is why `resolve_route_literal` also enforces an exact segment count and a true catch-all route wouldn't resolve a multi-segment path. Adequate for the routes in the pilot repo.

## `TableRef`
`pub struct TableRef`
### Summary
One `.from("<table>")` call found in application code — the Supabase/PostgREST convention for naming which database table a query runs against, since that's also a string reference rather than anything an `import` can resolve.
### Behavior
`from_file` is the file the call was found in; `table` is the table name matched inside the `.from(...)` call. Like `RouteLiteral`, these are stored on the `Graph` rather than re-derived per lookup, and get resolved against the schema nodes `schema.rs` extracts from `CREATE TABLE` statements — a `TableRef` whose `table` matches an extracted schema node becomes the flow edge that lets `get_callers` on a table answer "what app code actually touches this."
### Depends on
- (none)

## `extract_table_refs`
`pub fn extract_table_refs(source: &str, rel_path: &str) -> Vec<TableRef>`
### Summary
The per-file pass that finds every `.from("<table>")` member call in a TypeScript source, producing the `TableRef`s that become code→table flow edges (M10).
### Behavior
Parses with `ts_parser` (empty vec on parse failure), then `walk_for_from` descends the whole tree. Deliberately narrow: the argument must be a single plain string literal shaped like a table name (`[a-z_][a-z0-9_]*`), which is what rules out `Array.from(...)` / `Buffer.from(...)` and any `.from(tableVar)`. An ORM-aware matcher (`db.payments`, `Payment.findMany`) is out of scope for Phase 1.

- `src/typescript/conventions.rs::ts_parser` — super::conventions

## `walk_for_from`
`fn walk_for_from(node: Node, source: &str, rel_path: &str, out: &mut Vec<TableRef>)`
### Summary
The recursive tree-sitter visitor behind `extract_table_refs` — recognises a `<receiver>.from("table")` call and recurses into every child.
### Behavior
A node contributes a `TableRef` only if all of: it's a `call_expression`; its function is a `member_expression` whose property is `from`; the receiver is not a known builtin (`is_builtin_from_receiver` filters `Array`/`Object`/`Buffer`); there is exactly one argument (`named_child(1)` is `None`); that argument is a `string` literal; and its content passes `is_table_name`. The single-argument rule is deliberate — `Array.from(x, fn)` and RxJS `from(a, b)` are excluded even if they somehow slipped past the receiver check. Then it descends into all children.
### Depends on
- externals: tree_sitter

## `is_table_name`
`fn is_table_name(s: &str) -> bool`
### Summary
Whether a string looks like a SQL table identifier — `[a-z_][a-z0-9_]*` — the shape check that keeps `.from("...")` extraction from picking up arbitrary string arguments.
### Behavior
Non-empty, first character an ASCII lowercase letter or underscore, every character lowercase / digit / underscore. Rejects uppercase (`.from("SomeClass")`), paths (`.from("./x")`), URLs, and anything with a dot or dash. Intentionally strict — a schema that uses mixed-case or quoted identifiers would be missed, which is acceptable for the Supabase/Postgres convention this targets.
### Depends on
- (none)

## `is_builtin_from_receiver`
`fn is_builtin_from_receiver(member: Node, source: &str) -> bool`
### Summary
Heuristic that rejects a `.from(...)` whose receiver is a global constructor (`Array.from`, `Buffer.from`, `Object.fromEntries`-adjacent) rather than a query builder.
### Behavior
Returns `true` only when the member expression's `object` is a bare `identifier` whose first character is ASCII uppercase. The reasoning: a Supabase/query-builder receiver is always a lowercase-initial variable (`supabase`, `db`) or a call expression (`createClient().from(...)`), so an uppercase-initial identifier is a reliable tell for a builtin. A receiver that's a member access or call is *not* flagged here — it's assumed to be a real query builder.
### Depends on
- externals: tree_sitter

## `resolve_table_ref`
`pub fn resolve_table_ref(graph: &Graph, table: &str) -> Option<SymbolId>`
### Summary
Finds the database table definition that a table name written in code refers to, so a `.from("payments")` query can be linked to the `CREATE TABLE` it targets.
### Behavior
Searches every symbol in the graph for one of kind `Schema` (a table produced by schema extraction, including an in-language model retagged as a table) whose table name, taken from the end of its id with `table_name_of`, equals the given name exactly, and returns its arena id. The match is case-sensitive and the first match in graph order wins. If nothing matches it returns `None`, which happens for a database view, a typo, or a table created outside the indexed schema files. The match is by name only, so a name that happens to be defined in two schema files resolves to whichever comes first. It only reports a plausible candidate, not a guarantee that the query really targets it. Pure read.

## `RenderedComponent`
`pub struct RenderedComponent`

## `extract_rendered_components`
`pub fn extract_rendered_components(source: &str, rel_path: &str) -> Vec<RenderedComponent>`
### Summary
The per-file pass listing every distinct `<Component/>` a TypeScript/TSX file renders — the `RenderedComponent`s that let `assemble_participants` walk a feature two components deep.
### Behavior
Parses with `ts_parser` (empty vec on failure), collects tag names into a `BTreeSet` via `walk_for_jsx` (so the result is deduplicated and in sorted order — deterministic for hashing), then wraps each name in a `RenderedComponent` tagged with this file. ## `walk_for_jsx`
`fn walk_for_jsx(node: Node, source: &str, out: &mut BTreeSet<String>)`
### Summary
The recursive tree-sitter visitor behind `extract_rendered_components` — collects the name of every uppercase-initial JSX element tag into a set.
### Behavior
At a `jsx_opening_element` or `jsx_self_closing_element`, it takes the first child of kind `identifier` as the tag name and inserts it if the first character is ASCII uppercase. Taking only a plain `identifier` child is what skips namespaced tags (`<Foo.Bar/>`, a `member_expression`). Then it recurses into all children, so components rendered inside other JSX are still found. The `BTreeSet` dedupes repeats within a file.

- externals: std, tree_sitter

## `resolve_rendered_component`
`pub fn resolve_rendered_component(graph: &Graph, from_file: &str, name: &str) -> Option<String>`
### Summary
Finds the file that defines a component a page shows with a tag like `<Header/>`, so the component's code can be included in that page's feature description.
### Behavior
It first checks the file's resolved default imports for one whose local name equals the tag name (`import Header from './header'`), the way React components are almost always imported, and returns that import's resolved target file. If none, it falls back to a named import in the same file whose imported name equals the tag name, and returns the path of the file that contains the resolved symbol (the target's parent, as text). If the import points outside the repo, such as an external UI library, or did not resolve at all, it returns `None`. The default-import check uses the local name, but the named fallback compares the original exported name, so a renamed named import (`import { Header as H }` rendered as `<H/>`) is not found. Namespace-qualified tags such as `<UI.Button/>` are not handled here. Pure read.
### Depends on
- `src/graph.rs::Graph` — crate::graph

## `file_does_data_work`
`fn file_does_data_work(graph: &Graph, file: &str) -> bool`
### Summary
Says whether a file does real data work, meaning it calls an API route or queries a database table. A component that does is treated as part of a feature's behavior, and one that doesn't is treated as just layout.
### Behavior
Returns true if any flow edge in the graph starts in the given file and has the kind `route-literal` (a `fetch("/api/...")` call) or `table-ref` (a `.from("table")` query). The edge counts whether or not its target resolved, because an unresolved one still shows the file does data work. Other edge kinds, such as a rendered-component edge, do not count, so a component that only renders other components is not data work by itself. It decides whether a rendered component joins a feature's core set. It scans all flow edges in the repo on every call, so it is linear in their number. It looks only at the file's own edges, not those of files it imports. Pure read.
### Depends on
- `src/graph.rs::Graph` — crate::graph

## `is_colocated`
`fn is_colocated(component_file: &str, entry_file: &str) -> bool`
### Summary
Whether a component file lives in the entry point's own directory subtree — the other way (besides doing data work) a rendered component joins a feature's `core`.
### Behavior
Takes the entry file's directory (everything before its last `/`) and returns `true` iff `component_file` starts with that directory plus a trailing slash. So `app/submit/artwork-uploader.tsx` is co-located with `app/submit/page.tsx`; `components/ui/button.tsx` is not. An entry file at the repo root (no `/`) makes `entry_dir` empty and the check returns `false` — nothing is "co-located" with a root file, which avoids treating the whole repo as one feature.

- (none)

## `TypeScriptNextFeatureModel`
`pub struct TypeScriptNextFeatureModel`
### Summary
Defines what counts as a "feature" in a Next.js project using the App Router: each page, plus any API route that no page refers to, becomes a feature, and the components and API routes a page uses are pulled into it.
### Behavior
`enumerate_entry_points` builds the list in two parts. First, it collects the files that are the target of a resolved `route-literal` flow edge, meaning an API route that some code calls. Then, every file that `is_page` becomes an entry of kind `page`. Every file that `is_api_route` and is not in that targeted set is added after the pages as kind `api-route`, so an API route that something already calls is not a feature of its own but part of that caller's feature. Each entry gets its slug from `feature_slug`, its title from the route path (`entry_route_path`), and its file. Only a resolved call counts as targeting, so a route called only through an unresolvable path still shows up as its own feature.

`admits_to_core` is asked about each file reached from an entry through a resolved edge. It returns true if the file is an API route, or sits next to the entry file (`is_colocated`), or does data work (`file_does_data_work`: it calls an API route or queries a table). Otherwise the file is only a one-hop dependency. An API route is always admitted, which reproduces the older rule that route-literal targets join the feature unconditionally. Rendered components, which are `.tsx` files, fall through to the co-location and data-work tests, so a shared presentational component from elsewhere stays a dependency. The struct has no fields.

- `src/features.rs::FeatureModel` — crate::features
- `src/features.rs::feature_slug` — crate::features
- `src/graph.rs::FlowTarget` — crate::graph
- `src/graph.rs::Graph` — crate::graph
- externals: std, tree_sitter

## `entry_route_path`
`fn entry_route_path(entry_file: &str) -> String`
### Summary
Derives the URL path an entry file serves — `app/submit/page.tsx` → `/submit`, `app/page.tsx` → `/`, `app/api/stripe-webhook/route.ts` → `/api/stripe-webhook`. Used only for `EntryPoint::title`.
### Behavior
Strips the `app/` prefix, then trims a trailing `page.tsx` or `route.ts`, then a trailing `/`, then prepends `/`. The root page collapses cleanly to `/`. Dynamic segments (`[id]`) are left as-written in the path — it's a display string, not something resolved against.
