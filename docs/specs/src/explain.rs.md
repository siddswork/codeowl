# src/explain.rs
> Generated by [CodeOwl](https://github.com/siddswork/codeowl)
## Summary
This file answers "why is this spec out of date?". The rest of CodeOwl can say that a spec is stale, because a stored hash no longer matches; this file names the reason, as a short chain: the declaration's own text changed, a named dependency changed, a dependency was added or removed, or a child document the spec summarizes is itself stale (with that child's reason nested inside). `explain` takes any document id (a declaration, a file, `rollup:<dir>`, `feature:<slug>` or `system`) and returns its state, `missing`, `current` or `stale`, with a list of causes, each carrying a short kind label, the thing that moved and a plain-language sentence. For folders and the whole-repo spec the chain follows stale children down at most three levels (system, folder, file). It also tells apart a spec that predates the file fingerprint, which is reported as an unknown cause with the fix to apply, from a real edit, and says when a dependency changed but the spec has no record of which one. `explain_corpus` runs this over every spec and counts the causes by combination, lists the ten dependencies that make the most specs stale, and counts the importers that depend on something with no recorded public shape, where any edit to the target would make them stale. The file only reads the graph and the stored specs; it never writes a spec or asks for one to be written.

## `StaleCause`
`pub struct StaleCause`
### Summary
One reason a spec is out of date, such as "the source of `foo` changed" or "a function it depends on changed its signature". A stale spec can have several of these, and one can in turn contain the reasons behind a stale child.
### Behavior
`kind` is a short label, one of `source`, `dependency`, `added`, `removed`, `child`, `rewritten`, `participant` or `unknown`. `target` names the thing that moved (a symbol id, a file path) and is `None` when there is no single thing to point at. `detail` is a human-readable sentence about it. `because` is a list of nested causes and is empty except when the cause is a stale child, where it holds why that child is stale; this is how a folder or system spec can explain itself down to the file that actually changed. The private `new` constructor takes a kind, an optional target and a detail, and always starts with an empty `because`. The type holds data only and does no checking, so nothing stops a `kind` outside the list above.

## `explain`
`pub fn explain(graph: &Graph, root: &Path, id: &str) -> Result<Explanation>`
### Summary
Answers "why is this spec stale?" for any document id: it works out what kind of document the id names and hands it to the matching explainer. For example, `src/spec.rs` gets the file explainer, `system` gets the whole-repo one.
### Behavior
It picks the explainer from the shape of the id. `system` goes to `explain_system`, `rollup:<dir>` to `explain_rollup`, and `feature:<slug>` to `explain_feature`. The system and rollup explainers start the nesting depth at 1, which is what limits how far a chain of stale children is followed (`MAX_DEPTH`, three levels: system, folder, file). Anything else is looked up in the graph. An id the graph does not know is an error whose message includes the id, so a typo is reported and is not turned into an answer. A known id that is a file goes to `explain_file`; any other known id is a symbol and goes to `explain_symbol`. A document with no spec comes back as `missing` and not as an error, by the explainers themselves. The function only reads the graph and the spec files and never writes. The only caller found is the server module (`mcp.rs`).

## `explain_symbol`
`fn explain_symbol(graph: &Graph, root: &Path, sym_id: SymbolId) -> Result<Explanation>`
### Summary
Says whether one function, class or other declaration has a current spec, and if it is stale, whether its own text changed, something it depends on changed, or both.
### Behavior
It looks the symbol up, then finds the spec file that holds it. A class member lives in its file's spec, not its parent's, so it asks for the owning file and not the containing class. If that file has no spec, or the spec has no entry for this symbol, the answer is `missing`. Otherwise it asks `spec::symbol_changes` what moved since the spec was written, and an empty answer means `current`.

For a stale symbol it adds at most two kinds of cause, because `symbol_changes` compares exactly two things, the symbol's own text (`changed:source`) and its dependencies (`changed:dependencies`), and reports nothing else. So a stale symbol always comes back with at least one cause. It returns an error if the id is not a symbol, if its file is missing from the graph, or if the spec file cannot be read. It reads only and writes nothing.

## `explain_file`
`fn explain_file(graph: &Graph, root: &Path, file_id: SymbolId) -> Result<Explanation>`
### Summary
Says whether a file's own summary is current and, if not, why: the file changed in a way its summary would notice, something it imports changed, or one of its declarations has a missing or stale spec.
### Behavior
It reads the file's spec. If there is none, or the spec only holds per-declaration sections and the file's own summary has never been written (its `spec_hash` is empty), the answer is `missing`, since there is nothing yet to be stale.

Otherwise it asks `spec::file_changes` what moved. That compares the file's current fingerprint (not its raw text) and its dependencies with the stored values. A `changed:source` entry becomes one of two causes. When the stored spec has no `fingerprint` (it was written before files had one), the cause is `unknown`, saying the spec predates the file fingerprint and to run `migrate-file-fingerprint` or regenerate it; that is not an edit, and the text says so. When the fingerprint exists, the cause is `source`, "the file changed in what its summary is based on". A `changed:dependencies` entry recomputes the file's dependency hashes and names each dependency that moved through `dependency_causes`, or adds the "unreadable" cause if they cannot be computed.

If the file itself shows no change, it still counts as stale while any of its declarations is missing or stale, so it adds `stale_symbol_causes` to name them. That mirrors how `get_spec_coverage` counts the file. No causes at all means `current`; any cause means `stale`. It reads only and writes nothing. It returns an error if the id is not a file or if the spec file cannot be read.

## `dependency_causes`
`fn dependency_causes(
    graph: &Graph,
    now: &[(String, String)],
    stored: &HashPair,
) -> Vec<StaleCause>`
### Summary
Works out which of a spec's dependencies are responsible when its dependency hash no longer matches: ones that changed, ones that are new, and ones that are gone. It does this by comparing the dependency list recorded when the spec was written with the list as it is now.
### Behavior
It first shortens the current hashes (`now` carries full ones, the record carries shortened ones) so the two can be compared. If the stored spec has no record of its dependency targets, there are two cases. If its stored dependency hash equals the hash of an empty list, it recorded that it had none, so every current dependency is new and each gets an `added` cause. Otherwise the spec predates the record, nothing is known, and it returns a single `unknown` cause saying a dependency changed but the spec has no record of which one.

With a record, it goes through the current dependencies. One whose id is stored with the same hash is unchanged and ignored. One stored with a different hash gives a `dependency` cause whose detail comes from `target_detail`. One not stored at all gives `added`. Then it goes through the stored dependencies, and any that is no longer present gives `removed`. If no cause came out of all that, it returns an `unknown` cause saying the dependencies changed but no single one explains it, so a stale answer is never left with an empty reason. Causes come out in the order: current dependencies first, then removed ones.

### Behavior

## `explain_rollup`
`fn explain_rollup(graph: &Graph, root: &Path, dir: &str, depth: usize) -> Result<Explanation>`
### Summary
Says whether a folder's summary is current and, if not, which files in the folder are the reason: files that were added, removed, or whose own summary is stale, missing or rewritten since.
### Behavior
It builds the id as `rollup:<dir>` and reads the folder's stored spec; no spec means `missing`. A rollup records the summary hash of each file in the folder when it was written. It computes those hashes as they are now (`current_file_hashes`) and compares the two lists with `diff_hash_lists`; an empty difference means `current`.

For each difference it splits the entry into an action and a target. `added` becomes an `added` cause, "a new file in this folder", and `removed` becomes a `removed` cause, "no longer in this folder". That function decides whether the file is `stale`/`missing` or `rewritten`, and whether to nest the file's own causes. Entries it cannot split are skipped. The result is `stale` with those causes. It reads only. It returns an error only if reading the spec or a file's explanation fails.

## `explain_feature`

### Summary
Says whether a feature's spec is current and, if not, which of the feature's parts (files, symbols, tables) were added, removed or changed since it was written.
### Behavior
It builds the id as `feature:<slug>`. It first looks up the feature model for the repo's language (`feature_model_for`); a repo whose language has no feature model is an error saying so, and an id whose slug matches none of the model's entry points is an "unknown id" error. Otherwise it assembles the feature's current participants from the entry point (`assemble_participants`), computes their current hashes, and compares them with the list stored in the spec (`diff_hash_lists`). An empty difference means `current`. Each difference becomes one cause, in the order listed: `added` is "a new part of this feature", `removed` is "no longer part of this feature", and anything else is a `participant` cause whose detail comes from `target_detail` (its interface changed, its text changed, or its file changed). Unlike the folder and system explainers, it does not look inside the parts for further causes, so there is no nesting. It reads only. Errors come from the two lookups above or from reading the spec and hashing the parts.

## `explain_system`
`fn explain_system(graph: &Graph, root: &Path, depth: usize) -> Result<Explanation>`
### Summary
Says whether the whole-repo summary is current and, if not, which folders or features it was built from have since been added, removed or changed, following each one down to why it changed.
### Behavior
It reads the system spec; none means `missing`. The system spec records the summary hash of every module (folder) and every feature it was written from. The function computes those hashes as they are now, joins the two lists, and compares them with the stored ones (`diff_hash_lists`); no difference means `current`.

For each difference it splits the entry into an action and a target. `added` becomes "a new folder or feature" and `removed` becomes "this folder or feature is gone". Any other action means that child's summary hash changed. It then builds an explanation of the child: if the target is one of the repo's modules, with `explain_rollup` at one level deeper, and otherwise with `explain_feature`, falling back to a `missing` feature explanation if that fails (the error is dropped, not returned). That explanation, the child's current hash and the current depth go to `child_cause`, which labels the child stale, missing or rewritten and nests the child's own causes while the depth is below `MAX_DEPTH`. Entries it cannot split are skipped. The result is `stale` with these causes. It reads only. Errors come from reading the spec, computing the hashes, or explaining a folder.

## `CorpusSummary`
`pub struct CorpusSummary`
### Summary
A repo-wide tally of why specs are stale: how many documents there are, how many are stale, which causes are most common, which dependencies hold back the most specs, and how many importers depend on something that is tracked coarsely.
### Behavior
`documents` is the number of documents counted and `stale` how many of them are stale. `by_cause` counts stale documents by the combination of causes they have, so a label like `source`, `dependency`, `source + dependency` or `child` is a group of documents with exactly that set. `top_targets` lists the dependencies that make the most symbol and file specs stale, as (target id, count) pairs. `coarse_dependants` counts importers that rest on a target with no interface hash, meaning any change to the target's text, not just its public shape, would stale them; it is counted whether or not anything is stale right now, so it measures exposure and not current damage. The type holds data only; the counting is done by `explain_corpus`.

- (none)

## `explain_corpus`
`pub fn explain_corpus(graph: &Graph, root: &Path) -> Result<CorpusSummary>`
### Summary
Looks at every spec the repo has, explains each one, and tallies the result: how many documents exist, how many are stale, the most common combinations of causes, and the ten dependencies that make the most specs stale.
### Behavior
It first collects the ids to look at. It asks the coverage report for every document (files, folders, features, the system spec), and for each file also adds the ids of the declarations in that file's spec, then the document's own id. Each id is run through `explain`. An id that errors is skipped, so one document that cannot be explained does not hide the rest. `missing` documents are skipped and are not counted at all, so `documents` means documents that exist.

For each remaining document it increments `documents`, and if it is stale it increments `stale` and the count for its cause label (`cause_label`, such as `source + dependency`). For stale symbol and file documents only, it also counts each `dependency` cause by its target, which feeds `top_targets`; folder, feature and system causes do not count there. `by_cause` and `top_targets` are both sorted by count, highest first, with ties broken by name so the order is the same every run, and `top_targets` is cut to the top 10 (`TOP_TARGETS`). `coarse_dependants` comes from a separate count over the whole graph, whether or not anything is stale. It reads only and returns an error only if the coverage report cannot be built or a spec file cannot be read.

## `cause_label`
`fn cause_label(e: &Explanation) -> String`
### Summary
Turns a stale document's list of causes into one short label for counting, such as `source`, `dependency` or `source + dependency`, so documents with the same set of reasons can be grouped.
### Behavior
It collects the distinct kinds among the causes into a sorted set, renames some of them, and joins them with ` + `. For a symbol or file (the "leaf" documents), `dependency`, `added` and `removed` all become `dependency`, since a new, removed or moved dependency all mean the dependency list changed. For any other document (folder, feature, system), `added` and `removed` become `added or removed`. `rewritten` becomes `rewritten child`. Every other kind keeps its own name. Because the labels go through a set, a document with several causes of the same kind gets that label once, and the order is alphabetical, not the order the causes were found. A list with no causes gives an empty label; the explainers always give a stale document at least one cause, so this does not arise for the documents it is called on. It does not read the graph or any file.
### Depends on
- (none)

## `coarse_dependants`
`pub fn coarse_dependants(graph: &Graph) -> usize`
### Summary
Counts how many importing files depend on something in another file that has no recorded public shape, so that any edit to that thing, even to its body, makes the importer's spec stale. It measures how exposed the repo is to that kind of staleness, whether or not anything is stale right now.
### Behavior
It walks every resolved import in the graph and skips those with no target. A target counts as coarse in two cases. If it is a symbol, it counts when it has no interface hash and sits in a different file from the importer; an import of something in the same file is never counted. If it is not a symbol (an import that resolved to a whole file), it always counts. For each coarse import it records the pair of importing file and target id in a set, so the same file importing the same target through several import lines counts once. The result is the size of that set. It reads the graph only and cannot fail.

- [`src/graph.rs::Graph`](graph.rs.md) — crate::graph
