# src/java.rs
## Summary
The Java language pack's parsing layer — the equivalent of `extract.rs` (TypeScript) or `rust.rs`, plus the Java parts of `imports.rs` and `resolve.rs`. It has two jobs. First, `extract_file` walks a `.java` file with `tree-sitter-java` and pulls out its declarations: every class, interface, enum, `@interface`, and record becomes a `Container` symbol (a record is just a restricted `final class`, so it's treated the same); methods, constructors, and annotation elements become `Callable`; fields and interface constants become `Value`; nested types recurse fully. Method bodies, statements, and lambdas are skipped — CodeOwl doesn't document those. The rest of the file — `type_name`, `signature_before_body`, `leading_doc`, `annotations`, and the small tree-sitter helpers — feed that walk. Second, the import half: `extract_imports` parses `import` statements into `(package, name)` pairs, and `resolve_imports` turns them into dependency edges two ways — matching a fully-qualified name to the `.java` file whose path ends with the matching directory path (so any project layout works with no configuration), and scanning each file's source for same-package classes it uses without importing, which Java allows. Rust and TypeScript keep their equivalents elsewhere; this file is entirely Java's.

## `extract_file`
`pub fn extract_file(source: &str, rel_path: &str) -> Vec<ExtractedSymbol>`
### Summary
Reads one Java file and returns a flat list of the things it declares — classes, interfaces, enums, annotation types, records, and their methods, constructors, and fields. This is the Java pack's version of the extraction step every language pack has; its output feeds straight into building the code graph.
### Behavior
Parses the source with `tree-sitter-java` (the Java grammar, compiled into CodeOwl). If parsing fails outright it returns an empty list. Otherwise it walks the top-level nodes of the parse tree and hands each to `visit_item`, which recurses into type bodies. The parse tree is dropped before the function returns — everything needed is copied out into owned values first — so no borrowed parser state escapes. The result is in source order, parent before children (a class appears before its methods).
### Depends on
- `src/symbol.rs::ExtractedSymbol` — crate::symbol
- externals: tree_sitter

## `visit_item`
`fn visit_item(
    node: Node,
    parent_id: Option<&str>,
    source: &str,
    file: &str,
    out: &mut Vec<ExtractedSymbol>,
)`
### Summary
Handles one Java declaration during the walk: works out what kind of symbol it is and adds it — and, for a type, its members — to the growing list.
### Behavior
A match on the parse-tree node kind:
- `class`, `interface`, `enum`, `@interface` (annotation type), and `record` all go to `visit_container`, which records the type and recurses into its body. All five map to the `Container` symbol kind; the exact keyword is kept separately in `raw`.
- a method → a `Callable` symbol with nothing nested in it (a "leaf").
- a constructor or compact constructor → a `Callable` leaf named `<init>`.
- an annotation-type element (the `String value();` inside an `@interface`) → a `Callable` leaf.
- a field or interface constant → one `Value` leaf **per name**: `int a, b;` is a single declaration binding two names, so it produces two symbols.
- the `; ...` tail of an enum body (where an enum's own methods live) → recurse into each child.
- anything else → ignored.

`parent_id` is the enclosing type's id, or `None` at the top level of the file. It's threaded through every call so a nested type or a member gets an id scoped under its container.
### Depends on
- `src/symbol.rs::ExtractedSymbol` — crate::symbol
- `src/symbol.rs::SymbolKind` — crate::symbol
- externals: tree_sitter

## `visit_container`
`fn visit_container(
    node: Node,
    raw: &str,
    parent_id: Option<&str>,
    source: &str,
    file: &str,
    out: &mut Vec<ExtractedSymbol>,
)`
### Summary
Records one Java type — a class, interface, enum, `@interface`, or record — as a `Container` symbol, recurses into its body to pick up its members and nested types, and rolls their content hashes up into the type's own hash, so a change anywhere inside it registers as a change to the type.
### Behavior
Builds the type's id — `<file>::<Name>` at the top level, `<Outer>::<Inner>` when nested — then walks the type's body (`visit_item` on each child, passing this type as their parent), which fully recurses into any nested types.

Then it fills in the symbol's fields:
- `children` and the hash rollup use *direct* members only. A nested type has already folded its own members' hashes into its own `source_hash`, so folding just the nested type's hash here covers them indirectly.
- `source_hash` is a hash of the type's declaration line plus each direct member's `source_hash`, newline-joined — the "Merkle fold" (see `GLOSSARY.md`): editing any method moves that method's hash, which moves the type's.
- `signature` is the header up to the opening brace (`public final class Foo implements Bar`).
- `docstring` is the Javadoc comment directly above.
- `markers` are the annotations on the declaration (`@Deprecated`, `@FunctionalInterface`).
- `is_exported`: a top-level Java type is always at least package-visible, so it's always `true`; a nested type needs `public` or `protected`. The interface hash (which reference edges key on) is set only when exported.

Finally it inserts the container symbol into the output list *before* its members, keeping the list in parent-then-child order.
### Depends on
- `src/hash.rs::hash_text` — crate::hash
- `src/symbol.rs::ExtractedSymbol` — crate::symbol
- `src/symbol.rs::SymbolKind` — crate::symbol
- externals: tree_sitter

## `push_leaf`
`fn push_leaf(

    raw: &str,
    parent_id: Option<&str>,
    source: &str,
    file: &str,
    out: &mut Vec<ExtractedSymbol>,

### Summary
Adds a member symbol (a method, an interface constant) whose name is taken from the parse-tree node's own `name` field, then hands the actual work to `push_named_leaf`.
### Behavior
Reads the node's `name` field; if there isn't one, does nothing — the declaration is silently skipped. Otherwise it calls `push_named_leaf` with that name. This covers the cases where the grammar puts the name directly on the node: methods and annotation-type elements. Constructors (whose name is `<init>`) and multi-name field declarations get their names from elsewhere, so they call `push_named_leaf` directly.

## `push_named_leaf`
`fn push_named_leaf(
    node: Node,
    name: &str,
    kind: SymbolKind,
    raw: &str,
    parent_id: Option<&str>,
    source: &str,
    file: &str,
    out: &mut Vec<ExtractedSymbol>,
)`
### Summary
Builds one leaf symbol — a method, constructor, field, or interface constant — from a parse-tree node plus an explicitly given name, and appends it to the output list. The common back end that `push_leaf`, constructors, and multi-name fields all funnel into.
### Behavior
Makes the id `<parent>::<name>` for a member (or `<file>::<name>` at the top level, which never happens for members since they always have a parent), then fills in:
- `signature` — the declaration up to the body (`public static boolean isEmpty(CharSequence cs)`).
- `source_hash` — a hash of the node's full text; unlike a container, a leaf has no member rollup.
- `docstring` — the Javadoc directly above.
- `markers` — the annotations on the declaration.
- `is_exported` is always `false` for a member. A Java method or field is never imported on its own — it's only reached through its class — so it isn't a target for a reference edge (the same stance the TypeScript and Rust extractors take). The interface hash is therefore left unset for members too.
- `children` is always empty.

- `src/hash.rs::hash_text` — crate::hash
- `src/symbol.rs::ExtractedSymbol` — crate::symbol
- `src/symbol.rs::SymbolKind` — crate::symbol
- externals: tree_sitter

## `signature_before_body`
`fn signature_before_body(node: Node, source: &str) -> String`
### Summary
Pulls out a declaration's signature — everything before its `{` body: modifiers, keyword, name, type parameters, `extends`/`implements`, parameter list, return type. Used for both types and members, since Java writes all of that the same way up to the brace.
### Behavior
Takes the source text from the declaration's start byte to wherever its `body` node begins. If there is no body — an abstract or interface method, a bodyless `record Foo(int a);` — it goes to the end of the declaration instead. Then it trims trailing whitespace, a trailing `;`, and any whitespace before that. The result is the header exactly as written in the source, possibly spanning several lines.
### Depends on
- externals: tree_sitter

## `has_public_or_protected`
`fn has_public_or_protected(node: Node) -> bool`
### Summary
Reports whether a declaration is marked `public` or `protected`. Used to decide whether a *nested* type or a member is visible outside its class, and so whether it's a valid target for a reference edge.
### Behavior
Finds the declaration's `modifiers` node (via `modifiers_of`); if there isn't one — the declaration is package-private or `private` — returns `false`. Otherwise returns `true` if any modifier is the keyword `public` or `protected`. Doesn't look at `private` explicitly: anything that isn't `public`/`protected` is treated as not exported.
### Depends on
- externals: tree_sitter

## `modifiers_of`
`fn modifiers_of(node: Node<'_>) -> Option<Node<'_>>`
### Summary
Finds a declaration's `modifiers` node — the group holding `public`, `static`, `final`, and any annotations — smoothing over a grammar inconsistency in how different declaration kinds expose it.
### Behavior
Tries `child_by_field_name("modifiers")` first, which works for most declaration kinds. If that returns nothing, falls back to scanning the direct children for a node of kind `"modifiers"` — a few node types only attach it as a plain child, not a named field. Returns `None` when there are no modifiers at all (a package-private class with no annotations).
### Depends on
- externals: tree_sitter

## `leading_doc`
`fn leading_doc(node: Node, source: &str) -> Option<String>`
### Summary
Pulls the Javadoc comment directly above a declaration and returns its text with the `/**`, `*/`, and per-line leading `*` markers stripped. `None` when there's no doc comment.
### Behavior
Walks backwards from the declaration through its preceding siblings in the parse tree, accepting only comments that are *directly adjacent* — each has to end on the line the next thing begins, with no blank line between. A blank line, or any non-comment node, ends the walk, so a stray comment two declarations up isn't misattributed.

For each adjacent comment: a Javadoc `/** … */` block contributes its cleaned-up lines (via `doc_comment_body`); a plain `//` or `/* */` comment is stepped over without adding text. Because the walk runs backwards, lines are collected in reverse and flipped at the end; an empty result becomes `None`.

Java annotations don't get in the way here — they sit inside the declaration's `modifiers` node, not as preceding siblings.
### Depends on
- externals: tree_sitter

## `doc_comment_body`
`fn doc_comment_body(raw: &str) -> Option<Vec<String>>`
### Summary
Turns a raw Javadoc comment string into its content lines, stripped of the comment markers. Returns `None` for anything that isn't a `/** … */` block, which is how `leading_doc` tells a real doc comment apart from an ordinary comment to step over.
### Behavior
Only proceeds if the string both starts with `/**` and ends with `*/` — otherwise `None`. For the text between, it splits into lines and for each one: trims whitespace, drops a leading `*`, trims again, and keeps it only if non-empty. So `* @param x the value` becomes `@param x the value` and blank `*`-only lines are dropped.
### Depends on
- (none)

## `annotations`
`fn annotations(node: Node, source: &str) -> Vec<String>`
### Summary
Collects the annotations written on a declaration — `@Deprecated`, `@Override`, `@Path("/x")` — as verbatim strings. These become the symbol's `markers`, which the Java pack will read back to build its feature and schema models (M17). Mostly empty for a plain library like commons-lang.
### Behavior
Finds the declaration's `modifiers` node (via `modifiers_of`); no modifiers → empty list. Otherwise it takes the children that are annotations — both the bare `@Deprecated` form (`marker_annotation`) and the `@Path("/x")` form with arguments (`annotation`) — and for each one returns its source text with internal whitespace collapsed to single spaces, so a multi-line annotation comes back on one line.
### Depends on
- externals: tree_sitter

## `extract_imports`
`pub fn extract_imports(source: &str, _rel_path: &str) -> FileImports`
### Summary
Reads a Java file's `import` statements and returns them as `(package, name)` pairs — `import java.util.List;` becomes `("java.util", "List")`. The Java pack's version of the import-parsing step; the output is later resolved to the actual classes.
### Behavior
Parses with `tree-sitter-java`, then for each top-level `import` declaration:
- Splits the fully-qualified name on its last `.`: `import java.util.List;` → specifier `java.util`, name `List`. A `static` import (`import static a.b.C.m;`) is split the same way, so the class stays in the specifier (`a.b.C` / `m`) — the `static` keyword doesn't change extraction, only resolution.
- A wildcard import (`import a.b.*;`) records `*` as the name. It names no single class, so it later resolves to nothing; most Java projects, commons-lang included, forbid wildcard imports via checkstyle anyway.
- A single-segment `import C;` from the default package has no `.` to split on and is skipped.

Java has no re-exports or default imports, so only the `imports` part of the result is ever populated. A parse failure returns an empty result.
### Depends on
- `src/imports.rs::FileImports` — crate::imports
- `src/imports.rs::ImportRef` — crate::imports
- externals: tree_sitter

## `resolve_imports`
`pub fn resolve_imports(
    root: &Path,
    file_imports: &HashMap<String, FileImports>,
    graph: &Graph,
) -> Vec<ResolvedImport>`
### Summary
Turns a Java repo's parsed imports into resolved dependency edges, and adds the *implicit* edges Java has that no `import` records — a class using another class in the same package. This is the Java pack's whole resolution step.
### Behavior
Two passes, both producing `ResolvedImport` edges:
1. For every explicit `import` in every file — files walked in sorted path order, so the saved edge list is stable and diffable — it calls `resolve_explicit` to find the target class. An unresolved one (a JDK class, a third-party library) is kept in the list with no target, same as the other packs.
2. `same_package_edges` scans each file's source for uses of sibling classes in its own package that were never imported, and emits an edge for each.

Unlike the Rust and TypeScript resolvers, this one actually reads files off disk (via `root`): the same-package scan needs each file's body text, which the graph doesn't retain.
### Depends on
- `src/graph.rs::Graph` — crate::graph
- `src/imports.rs::FileImports` — crate::imports
- `src/resolve.rs::ResolvedImport` — crate::resolve
- externals: std

## `fqn_to_file`
`fn fqn_to_file<'a>(fqn: &str, file_imports: &'a HashMap<String, FileImports>) -> Option<&'a str>`
### Summary
Maps a fully-qualified Java name like `com.foo.Bar` to the repo file that holds it — the `.java` file whose path ends `com/foo/Bar.java`. This is how Java resolution finds a class file without needing to know the project's source-root layout.
### Behavior
Converts the dotted name to a path fragment (`com.foo.Bar` → `com/foo/Bar.java`) and looks for a walked file whose path is exactly that or ends with `/` + that. A longer name like `com.foo.Bar.member` still matches `com/foo/Bar/member.java`, which won't exist — callers handle that by trimming the last segment and retrying.

Matching on the path suffix means it works for any layout — Maven's `src/main/java/...`, Gradle's, a bare tree — with no configuration. If two files match (the same class under two source roots, e.g. `main` and `test`), the one that sorts first alphabetically wins, so the result is deterministic.
### Depends on
- `src/imports.rs::FileImports` — crate::imports
- externals: std

## `resolve_explicit`
`fn resolve_explicit(
    specifier: &str,
    name: &str,
    file_imports: &HashMap<String, FileImports>,
    graph: &Graph,
) -> Option<SymbolId>`
### Summary
Takes one parsed Java import and finds the exact symbol it points at, or `None` if it can't — a wildcard import, a JDK or third-party class, or a class that isn't in this repo.
### Behavior
A wildcard import (`name == "*"`) resolves to nothing straight away.

Otherwise it tries two readings:
1. **Plain `import a.b.C;`** — the whole `a.b.C` is a class. Look for the file `a/b/C.java` and the symbol `C` in it.
2. **`import static a.b.C.m;` or `import a.b.Outer.Inner;`** — here the *specifier* `a.b.C` is the class and `name` is a member (or a nested type). Look for the file `a/b/C.java`, then try, in order: the member `C::m`, a top-level `m` in that file, and finally the class `C` itself. So a static-method import CodeOwl can't pin to the exact method still resolves to the containing class rather than being dropped — a method-level edge is call-graph detail, which is deferred.

Returns the first match found, or `None`.
### Depends on
- `src/graph.rs::Graph` — crate::graph
- `src/symbol.rs::SymbolId` — crate::graph
- `src/imports.rs::FileImports` — crate::imports
- externals: std

## `same_package_edges`
`fn same_package_edges(
    root: &Path,
    sorted_files: &[(&String, &FileImports)],
    graph: &Graph,
) -> Vec<ResolvedImport>`
### Summary
Finds the dependency edges Java has that no `import` records: a class using another class in the same package, which Java allows without an import. Without this, a Java dependency graph would look artificially sparse.
### Behavior
First it collects every top-level class / interface / enum / record in the graph as `(simple name, id, directory)`; nested types are excluded.

Then, for each source file (in the pre-sorted order, for a stable result) it takes the *other* top-level types declared in the same directory — which for Java is the same package — reads the file's source off disk, and for each sibling checks whether that type's simple name appears in the source as a whole word (`mentions_identifier`). A hit becomes a `ResolvedImport` edge pointing at that sibling, with the package name as its `specifier` so the edge is visibly synthetic rather than a real written import.

Limits: it's a text scan, so it can't tell a genuine use from the name appearing in a comment or a string literal, and it would also fire for a same-package name that's actually shadowed by an explicit import of a different class with the same simple name. A file that can't be read (deleted mid-watch) is skipped.
### Depends on
- `src/graph.rs::Graph` — crate::graph
- `src/symbol.rs::SymbolId` — crate::graph
- `src/imports.rs::FileImports` — crate::imports
- `src/resolve.rs::ResolvedImport` — crate::resolve
- `src/symbol.rs::SymbolKind` — crate::symbol
- externals: std

## `package_of`
`fn package_of(dir: &str) -> String`
### Summary
Turns a package directory into its dotted Java package name — `src/main/java/com/foo` → `com.foo`. Purely cosmetic: it's only used as the `specifier` label on a synthetic same-package edge, to show the edge isn't a real written import.
### Behavior

## `mentions_identifier`
`fn mentions_identifier(text: &str, name: &str) -> bool`
### Summary
Whole-word search: reports whether `name` appears in `text` as a standalone identifier, not as a fragment of a longer name. This is what `same_package_edges` uses to decide a file actually references a sibling class.
### Behavior
Scans for each occurrence of `name` as a substring and accepts it only if the characters immediately before and after aren't identifier characters (letter, digit, `_`, `$`) — or are the start/end of the text. So searching for `Foo` matches `Foo.bar` and `new Foo()` but not `FooBar` or `myFoo`. An empty name never matches.

It's a plain text scan with no awareness of Java syntax, so it can't tell a real reference from the name appearing in a comment or a string. This is a deliberate copy of `spec::contains_identifier`, kept here so the Java pack doesn't depend on the spec-rendering module.
### Depends on
- (none)
