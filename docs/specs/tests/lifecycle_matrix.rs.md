# tests/lifecycle_matrix.rs
## Summary
A permanent test that holds Rust, TypeScript, Python and Java to the same rules about when written descriptions go out of date. It covers cascading versus local staleness, orphaned descriptions, a description deleted by hand, and a source file being renamed, and it runs one identical scenario against one small real sample project per language. Each sample has the same shape: an owner file defining a `Widget` type with one public field, one private field and one method, a consumer file that imports `Widget` and calls the method, and an unrelated bystander file that references neither, which proves a change reaches only real users and not the whole repo. One baseline of descriptions is written once per project. Each scenario then re-reads a differently edited copy of the same files and checks what is stale against that one baseline. A method body edit must go stale in the owner only. A public field changed, added or removed must also cascade one hop to the consumer. A private field change must stay local, because the public-surface fingerprint reads only public members. A public method's signature changing, with the body untouched, must cascade as a field does. A description deleted by hand must be offered again as if never written. A deleted source file must leave its description reported as an orphan, and a rename must leave the old path as an orphan while the new path starts out as needing a description. The scenario works at the level of the spec code directly, not through the asynchronous server tools, so it needs no runtime. The helpers create temporary folders, write files, rebuild the graph, run the writing loop with canned text, and look up the three files, and one test per language runs the shared scenario.

## `Fixture`
`struct Fixture`
### Summary
The description of one language's sample project for the lifecycle matrix test: two files, an owner type and a file that uses it, plus a set of ready-made edits to the owner. The same scenarios are then run against Rust, TypeScript, Java and Python so every language is held to the same staleness rules.
### Behavior
Identity: `stack` names the language. `scaffold` lists extra files needed before the paths resolve at all, such as a Rust `lib.rs` with its module declarations or a Python `pyproject.toml`, and is empty where nothing extra is needed. `owner_path` and `consumer_path` are the two files, and `owner_symbol_id` and `consumer_symbol_id` the two symbols whose staleness is checked.

Text: `owner_v1` is the starting owner, a type with public and private fields and a method. `consumer_src` is the file that uses it. Each of the following is an edit to the owner, chosen to isolate one rule:
- `owner_body_edit` changes only a method's message and keeps the public surface, so only the owner should go stale.
- `owner_field_type_change` changes a public field's type, so the owner and its consumer, one hop away, should go stale.
- `owner_private_field_change` changes a private field's type, which the public-surface fingerprint never reads, so only the owner should go stale, never the consumer.
- `owner_field_added` is the original plus one more public field. It is used in both directions: from the original to it proves an added field cascades, and from it back to the original proves a removed field does too.
- `owner_method_signature_change` adds a parameter to a public method while its body stays the same, so it cascades to the consumer where a body-only edit does not.

Bystander: `unrelated_path` and `unrelated_src` are a file that references none of the owner, which must stay fully current through every edit. Rename: `owner_renamed_path` and `owner_renamed_content` are the owner moved elsewhere, with the class renamed to match for Java, where a public class name must match its file name. The struct is plain data, built once per language.

## `tempdir`
`fn tempdir(tag: &str) -> std::path::PathBuf`
### Summary
A test helper that creates a fresh, empty temporary folder for one scenario to use, with a name that cannot collide with another scenario's, even when tests run at the same time.
### Behavior
Builds a folder name from the prefix `codeowl-lifecycle-`, the caller's tag, the process id, and a counter that increases on every call, under the system temporary directory. The counter is shared across the whole run, so two scenarios never share a folder even with the same tag. It creates the folder and any missing parents and returns its path. It panics if creation fails, which is fine in test code, and it does not delete the folder afterwards.

## `drain`
`fn drain(graph: &Graph, dir: &Path, file_id: SymbolId)`
### Summary
A test helper that runs the spec-writing loop to completion for one file, answering every request with canned text, so a scenario can bring a file's descriptions fully up to date before it edits something.
### Behavior
Repeatedly asks for the next task for the file and stops when there is none, the same bottom-up loop the real generate command runs. For a symbol task it submits a two-part summary and behavior text, and for a file task it submits a one-line summary. The text is deliberately real prose long enough to pass the quality check that rejects text that is too short, and not a placeholder short enough to trigger it, so no task is offered again and the loop ends. It panics if a submission is rejected, which would signal a bug in the test text. It writes the spec documents to the given folder and returns nothing.

## `is_fully_current`
`fn is_fully_current(graph: &Graph, dir: &Path, file_id: SymbolId) -> bool`
### Summary
A test helper that answers "is everything about this file up to date?", meaning every symbol's description and the file's own summary match the current code and dependencies.
### Behavior
Asks for the next writing task for the file and returns true if there is none, and false if there is one. Since the task finder offers work for every symbol that is missing, stale or has poor text, and then for the file itself, having nothing to offer means all of it is current. Because the task finder can also quietly record a hand edit as a side effect, calling this is not strictly read-only, though it does not change anything in these scenarios. It panics if the task finder returns an error. The scenarios use it to assert both that a file went stale after a relevant edit and that a bystander file stayed current.

### Summary
A test helper that returns the id of the next symbol the writing loop wants described for a file, or nothing if the file is fully current or only its own summary is left.
### Behavior
Asks the task finder for the file's next task. If it is a symbol task it returns that symbol's id. For anything else, either no task at all or the file-level summary, it returns `None`. ## `drain_symbol_task_ids`
`fn drain_symbol_task_ids(graph: &Graph, dir: &Path, file_id: SymbolId) -> Vec<String>`
### Summary
A test helper that collects every symbol the writing loop asks to be described for a file after an edit, answering each as it goes, so a scenario can check which symbols went stale without depending on the order they were offered.
### Behavior
Repeatedly gets the next symbol task id for the file, using `next_symbol_task_id`. For each, it submits canned text long enough to pass the quality check, which also makes that symbol current so it is not offered again, and adds the id to a list. It stops when no symbol task is left, meaning only the file's own summary, or nothing, remains, and returns the list in the order offered.

The scenarios deliberately check membership, not order. A Java consumer wraps its function in a class, so the containing class can legitimately be offered before the method, because it depends on the owner too through that method's body, whereas the Rust, TypeScript and Python consumers have a bare top-level function with no wrapper. So the assertion is "did the cascade reach this exact symbol anywhere in the list", not "was it the very next thing offered". It panics if a submission is rejected.

## `run_lifecycle`
`fn run_lifecycle(fx: &Fixture)`
### Summary
The scenario every language is put through: it builds a small project, writes complete descriptions for it, then makes a series of edits and checks, after each, that exactly the right descriptions go out of date and no others. It is the main proof that staleness works the same in Rust, TypeScript, Java and Python.
### Behavior
Setup: creates a temporary folder, writes the language's scaffold files and three files, an owner type, a consumer that uses it, and an unrelated bystander. It builds the graph, runs the writing loop to completion on all three, and asserts each is fully current. Between scenarios it uses a repeated pattern: restore the owner to its starting text, rebuild, re-write all descriptions, and assert both files are current again, so one scenario's leftover effect never confuses the next.

1. Method body edit: only a method's message changes. The owner's own symbol must be offered again, the consumer must stay current, and the bystander must stay current. Local effect only.
2. Public field type change: the owner is offered again, and the consumer's symbol must appear in its own writing list, so the change cascades one hop to real users, while the bystander stays current. This proves the public-surface fingerprint.
3. Private field change: the owner is offered again, since its whole-content fingerprint moved, but the consumer stays current, because the public-surface fingerprint reads only public members. The bystander stays current.
4. Public field added: must cascade to the consumer, since a structural change to the member list is a different path from a value change, and a fold that only walks previously known members would miss it. Then the same field removed, the opposite direction, must cascade too, since a naive diff by name could miss a removal.
5. Public method signature change, body unchanged: must cascade to the consumer, because a public method's signature now folds into the owner's public surface just as a field's does. The bystander stays current.
6. Spec deleted by hand: after the owner's spec file is removed, the owner is no longer fully current and no spec is on disk, as if never written. The loop then restores a clean baseline.
7. Source deleted: after the owner's source file is removed, its spec must be reported as an orphan of kind file.
8. Rename: the content reappears at a new path. The old path's spec must still be an orphan, and the new path must start as needing generation with no spec at all, like a brand-new file.

The temporary folder is removed at the end. The assertions carry messages naming the language, so a failure says which language and which scenario broke. Order-independent checks are used where a language's consumer wraps its function in a class, which can legitimately be offered first.
