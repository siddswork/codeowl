# CodeOwl

CodeOwl reads a codebase in TypeScript, Rust, Java or Python, builds a graph of what is declared in it and which files depend on which, and serves that graph, together with written descriptions of the code, to AI coding agents over MCP, a standard way for an agent to call tools. The descriptions (specs) are written by the connected agent itself, never by CodeOwl, which holds no language-model credentials and only hands out a piece of writing to do and saves what comes back. Each description carries fingerprints of the code and the dependencies it was written from, so CodeOwl can tell when one has gone out of date without comparing prose, and a change to something other code depends on marks only the real users as stale. The repository is the engine (`src`), a pair of small measuring tools (`examples`), and a set of tests that exercise the whole path on real-shaped sample projects.

## Key flows

**Indexing a repository.** The command-line entry point makes the path absolute and passes it to the index. Language detection counts each language's ordinary source files, skipping test and tooling folders, and requires exactly one winner. The chosen language pack then reads each file: an extractor records the declarations, an import reader records what each file brings in, and a resolver links those imports to real declarations. For a language with features, a feature model also finds entry points such as a page, an API route, a message handler or a scheduled job. Everything is assembled into the graph, which is saved with a format stamp so an out-of-date cache is rebuilt and not trusted.

**Starting up and staying current.** On start, the saved index is loaded and every file is compared by fingerprint, so only files that changed while nothing was running are re-read. While the server runs, the file watcher collects file-system events, waits briefly so a burst of saves counts once, re-reads only the changed paths, and swaps the rebuilt graph into a shared cell that requests read from. Handlers never wait on the watcher and each works from one consistent snapshot.

**Answering a question from an agent.** The server exposes tools to look up a declaration, read the real source behind it, list who uses it and what it uses, read its written description, and run a plain regular-expression search over the repo. Each is a read of the current graph or the files, with flags that say when a result was cut short or the index is behind the file on disk.

**Writing and saving descriptions.** The generate loop asks the server for the next piece of work. It goes bottom-up, from a file's functions and types, to the file, to any feature the file starts, to a folder summary, and finally to a single summary of the whole system, and each step is offered only once the ones beneath it are current. The agent writes the text from the source and the already-written summaries of dependencies, sends it back, and the server rejects empty or evasive text and saves it with fingerprints. A whole run ends when the server answers that nothing is left.

**Noticing what is out of date.** For every description the engine recomputes the fingerprints of the code and of the public shape of what it depends on and compares them with what was saved, so editing a method body marks only that file, while changing a public field or method signature also marks the files that use it. A coverage report lists every document as current, stale or missing, flags weak text, lists leftover descriptions of deleted code, and orders the remaining work so widely used code comes first and the system summary last.

## Modules
- `examples` — Small standalone tools for measuring CodeOwl against real repos, run with `cargo run --example <name>`. They are not part of the product. They are how design questions get answered with numbers before code is changed. `graph_stats` prints statistics about the dependency graph CodeOwl builds for any repos you point it at (how connected the files are, which are the hubs, which are isolated, where import cycles are), and is used to check whether a change to extraction or import resolution made the graph more complete. `measure_signature_fold` is a reusable playbook for one specific question: before letting a new kind of declaration count toward a type's public shape, it measures how many extra files would be marked out of date per edit, and how often the written specs actually mention the members involved. Both only read and print, and both open each repo through the normal index, which may refresh that repo's local cache.
- `src` — The whole of CodeOwl's engine. It reads a codebase, builds a graph of what is declared and which files depend on which, saves that graph and keeps it current, and serves it, along with written descriptions of the code, to AI coding agents over MCP (a standard way for an agent to call tools). It is organised in layers. At the bottom are the shared vocabulary of declarations (`symbol.rs`), the graph that holds them (`graph.rs`), stable fingerprints (`hash.rs`), and small text helpers (`text.rs`). Next come one reading layer per language, each with a declaration extractor, an import reader and an import resolver: TypeScript (`extract.rs`, `imports.rs`, `resolve.rs`, `lang.rs`), Rust (`rust.rs`, `rust_crates.rs`), Java (`java.rs`) and Python (`python.rs`), with SQL schema reading in `schema.rs`. `stack.rs` is the single interface those languages plug into, so the rest of the engine never names a language. Above that sits the feature layer (`features.rs`, `fastapi.rs`, `quarkus.rs`), which groups code around what a person actually uses, such as a page, an API route, a message handler or a scheduled job. `index.rs` caches what was extracted from each file so a rebuild only re-reads what changed, and `watch.rs` keeps that current as files are edited during a session. `spec.rs` defines the written descriptions, their fingerprints for noticing when they are out of date, and the coverage report and ordering for writing them. `search.rs` provides plain regex code search, and `mcp.rs` exposes all of it as tools, with `main.rs` as the command-line entry point. The engine never calls a language model: it hands the connected agent a piece of writing to do and saves what comes back.
