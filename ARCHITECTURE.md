# CodeOwl — Architecture Sketch (Working Draft)

> Status: early sketch, to be refined over time. Companion to `REQUIREMENTS.md`, which covers the problem statement, goals, users, and scope decisions (multi-repo/team ownership, hosting granularity) this architecture implements. Inspired by [MemoLink](https://github.com/pandaind/memolink)'s pattern of extract → store → serve, applied to code instead of notes.

## Design principles

- **Facts drive spec generation, not the other way around**: structural/behavioral facts (call graphs, API surfaces, dependency graphs, test coverage mapping) are extracted via static analysis *first*, and used to decide the scope and order of LLM-generated specs — not treated as a substitute for them. Specs are the primary queryable artifact ("the brain"); facts are the scaffolding that make spec generation cheap and accurate.
- **Specs are a cache, not a static deliverable**: every spec is generated by an LLM, cached, and keyed by a content hash of its inputs. It is never hand-maintained and never goes stale *undetectably* — the moment its inputs change, the hash mismatch makes it mechanically stale, and every read of it says so (see "Recursive spec generation" below). Note what this does and doesn't promise: staleness *detection* is automatic and free; regeneration is a separate, explicit act (`/codeowl generate`), never a silent side effect of reading. This is still different in kind from traditional hand-written design docs, which rot because nothing detects the drift at all — here you are never unknowingly served a spec that no longer matches its code.
- **CodeOwl orchestrates, it doesn't generate**: CodeOwl never calls an LLM API itself and never holds LLM credentials. It builds the dependency graph and a generation plan (what needs a spec, in what order, with what scoped context), then hands each unit off — via MCP tool calls — to whichever coding agent is already in the session (Claude Code, or VS Code/Kiro's assistant) to write the actual spec text. This is what makes the privacy and "which LLM" questions moot: CodeOwl is always working through whatever LLM access the user or org already has, never its own.
- **Specs live in git; the graph is a rebuildable cache**: specs are committed to the repo alongside the code they describe (valuable, human-reviewable, diffable in a PR). The dependency graph and embeddings are derived, cheap-to-rebuild data — kept as a local, gitignored cache, not committed. See "Storage" below.
- **Parsing is eager, generation is lazy and explicit**: these are different resources with different costs — parsing is CPU-only and cheap, spec generation is LLM tokens and comparatively expensive. Parsing always runs eagerly (it's also a prerequisite: even a single on-demand spec request needs the graph already resolved to know what a symbol depends on). Spec generation defaults to lazy in scope — nothing is pre-generated across the whole repo unasked — and is always explicit in trigger: reading a spec (`get_spec`) never produces one as a side effect; only the separate `/codeowl generate` command does, including its incremental `--budget=N` form for nudging the repo toward full coverage over time without ever doing so silently. See "Recursive spec generation" below for how this works in practice.
- **Local-first / privacy-first, scoped to embeddings**: embeddings are always local — ONNX models, same as MemoLink, never sent to an external API. This is narrower than it might sound: spec generation necessarily *does* put source code in front of whichever LLM is generating the spec (see "CodeOwl orchestrates, it doesn't generate" above) — that's a deliberate, separate choice, not an exception to this principle. What stays local unconditionally is embeddings and everything CodeOwl itself computes.
- **Lightweight, embedded infra**: no separate graph DB server. Embedded storage only (`tantivy` + lightweight graph store), matching MemoLink's "no extra infra" philosophy. (MemoLink uses Lucene; the equivalent under CodeOwl's Rust stack is `tantivy` — see "Implementation stack" below.)
- **Incremental**: re-index only what changed, not full re-scans. The trigger mechanism differs by phase — see "Incremental indexing" below.
- **Cache LLM-derived content**: any LLM-generated summary is cached, keyed by a content hash, and only regenerated when the underlying code changes. This is where the token savings come from.

## High-level architecture

This diagram shows the full, Phase 2 shape. Phase 1 (see `REQUIREMENTS.md`) runs the same pipeline scaled down to one laptop: the serving layer is a local stdio MCP server (no HTTP/SSE, no web viewer needed yet), storage is split between git (specs) and a local gitignored cache (graph + embeddings), and the "LLM" in the spec generation layer is always the calling agent (Claude Code), never a call CodeOwl makes itself — see "CodeOwl orchestrates, it doesn't generate" above.

## Components

### 1. Extractors (per language, pluggable)

Use **tree-sitter** rather than a hand-rolled parser per language — one grammar API covers C++, Java, Python, and is straightforward to extend (Go, JS, etc. later). This stage is syntax-only and per-file: it has no cross-file knowledge yet. Keeping it behind a per-language interface that always emits the same generic shape means the resolution and spec-generation stages downstream never need to know which grammar produced it — swapping or adding a language parser doesn't touch anything else in the pipeline.

Also parse build/dependency manifests (`pom.xml`, `CMakeLists.txt`, `pyproject.toml` / `requirements.txt`, etc.) to build the external dependency graph — this matters more to SREs/DevOps than call graphs do.

**Open question (1 below)**: tree-sitter is syntactic only — it won't resolve overloads, virtual dispatch, or type-dependent calls precisely, which matters a lot for C++. Plan: start with tree-sitter for speed/breadth, consider layering in LSP-based resolution (clangd/jdtls/pyright) later for languages where precision matters most. For TypeScript specifically this is already resolved one level further — module resolution via `oxc_resolver`, symbol-level precision deferred to a later LSP layer; see "Implementation stack" below.

### 2. Graph resolution (per language, on top of the extractor)

Tree-sitter tells you *that* a file has an import statement or a call expression — it does not tell you *which real file or symbol* that resolves to. This stage does that resolution (`import foo.bar` → an actual file node, `#include "bar.h"` → an actual header node, a call expression → the actual callee symbol where resolvable) and emits the common `Symbol` record that everything downstream operates on:

```
Symbol {
  id, kind (fn/class/module/file), file, lines,
  signature, docstring,
  parent: SymbolId, children: [SymbolId],       // containment — a tree
  calls: [SymbolId], calledBy: [SymbolId],       // reference — a cyclic graph
  imports: [SymbolId],
  testedBy: [SymbolId],
  interfaceHash,                                 // deterministic, LLM-free — see "Caching and invalidation"
  isExported: bool
}
```

`interfaceHash` is computed entirely at this stage, from structural facts this stage already produces — no LLM involved, no dependency on spec generation having run. For a leaf symbol it's a hash of its exported shape: signature (params/return types for functions, member shape for classes), or the resolved value/type shape for an exported const or type alias — never its docstring or body. For a file/module it's a hash of the sorted `interfaceHash`es of its *exported* containment children (the same merkle-style aggregation the containment tree already uses for specs, just over signatures instead of spec bodies). A barrel re-export (`export * from './foo'`) resolves to the underlying symbol's own `interfaceHash` rather than getting one of its own — it isn't a new interface, just a second path to an existing one.

The output of this stage is the dependency graph — the thing that makes both spec generation (below) and query-time tools (`get_callers`, `impact_analysis`, etc.) possible. This is also where the tree-sitter/LSP precision tradeoff (previous section) actually gets applied, since resolution accuracy is what LSP-based layering would improve.

**Containment vs. reference — two structurally different relationships, both needed explicitly.** `parent`/`children` is a tree (a function belongs to exactly one file, a file to exactly one directory) and terminates at leaf symbols. `calls`/`imports` is a dense, frequently cyclic graph — nearly everything imports a handful of shared utilities, and mutual imports (barrel files, type-only cycles) are routine in real codebases. Spec generation (see "Recursive spec generation" below) depends on this distinction being first-class in the graph, not inferred — it recurses across one and only reads the other.

### 3. Incremental indexing

The trigger differs by phase, and — for Phase 1 — by a boundary worth being precise about: the MCP server's own process lifetime.

**Phase 1.** The server is a subprocess the client (Claude Code, VS Code, Kiro) spawns when a session starts and kills when it ends — not a persistent background daemon (see "MCP server" below). That means indexing has two distinct moments, not one: on a **fresh spawn**, a catch-up pass hash-checks every file against the `.codeowl/` cache and reparses whatever changed while no process was running; for the **remainder of that session** (which may run for hours), an in-process file watcher reindexes incrementally in real time as files change, the same debounce-and-swap pattern as MemoLink's `GraphWatchService`. Both re-parse only what changed, committed or not — there's no separate canonical index to keep in sync with.

**Phase 2** is git-driven at the shared-instance level: on push/merge, diff changed files, re-parse only those, atomically swap the graph (old graph/index closed to free memory). Every Phase 2 index snapshot is tagged with the commit SHA it reflects.

This is also why the Phase 2 "local uncommitted-change overlay" open question (see `REQUIREMENTS.md`) doesn't exist in Phase 1: there's nothing to overlay onto, since the local instance already reads the working directory directly.

### 4. Storage

**Phase 1 (per `REQUIREMENTS.md`)**: a two-way split, not one storage layer.
- **Specs** are committed to git, in a **mirrored tree under `docs/specs/`** — deliberately *not* sidecar files next to the source, since specs exist at multiple hierarchy levels with no single natural sidecar for each, and a separate tree keeps `git status`, source listings, and IDE fuzzy-search clean of generated artifacts. Physical files exist at file level and above only (`docs/specs/<mirrored-path>/<filename>.md` for a file-level spec, `_index.md` for a directory/submodule rollup, `docs/specs/_index.md` for the system level); leaf function/class specs are *sections within* their containing file's spec document rather than files of their own. See `REQUIREMENTS.md`'s "Spec file location and granularity" for the full rationale. Each spec file carries **two** hashes as frontmatter — `source_hash` (the inputs it was generated from, which doubles as the cache-invalidation key) and `spec_hash` (the body as CodeOwl last wrote it, which is what makes a human edit detectable) — so no separate cache database is needed. See "Human corrections" below.
- **The dependency graph and embeddings** are a derived, gitignored local cache, rebuilt from source + specs by the local file watcher/manual run. Nothing here needs to be durable or shared — it's cheap to regenerate on a laptop-scale monorepo.
- `tantivy` index for keyword + semantic search still applies locally (the Rust-stack equivalent of MemoLink's Lucene — see "Implementation stack"), just scoped to one repo, one machine, no persistence guarantees required. Whether search belongs in Phase 1 at all is a separate, still-open trimming question — `search_code` could start as embedded ripgrep (`grep` crate) instead.
- Local ONNX embedding model (e.g. all-MiniLM-L6-v2, as MemoLink uses) for semantic search over symbols/docstrings.

**Phase 2** extends this into a durable, multi-repo, per-team store:
- Lightweight embedded graph store for edges (SQLite adjacency tables, or persisted in-memory graph) — no separate graph DB server.
- Dual-mode storage for scale, mirroring MemoLink: in-memory for smaller repos, disk-backed index + incremental timestamp tracking for very large monorepos.
- Specs stored per graph node (symbol/file/submodule/module/system) in the shared instance's store, still tagged with the content hash they were generated from — the same frontmatter convention from Phase 1 carries over, it just also gets indexed centrally.
- Per `REQUIREMENTS.md`'s hosting decision, one instance serves a whole team: storage is namespaced per repo (separate index/graph/spec-cache per repo, own commit SHA), all sharing one embedding model and one running process. Cross-repo, same-team edges resolve directly against another namespace in the same store; cross-team edges are stub nodes with no local target to resolve.

### 5. Recursive spec generation

This is the step that turns the dependency graph into "the brain." A spec is never generated in isolation from raw source alone — it's generated bottom-up, so that every level reuses the levels below it instead of re-reading their source.

**Generation recurses across containment edges only — never across reference edges.** This is the resolution to a real failure mode: "recursively ensure dependencies have specs first," applied uniformly to *both* edge types, doesn't terminate (reference edges cycle) and doesn't scale (nearly every file references a handful of near-universal utilities, so the first query against almost any file would transitively touch a large fraction of the repo). Splitting the two relationships apart removes both problems:

- Across a **containment** edge (file → its functions/classes, directory → files, module → submodules), generation recurses and composes normally — see "Bottom-up composition" below. This is a tree with a guaranteed base case (leaf symbols), so it always terminates.
- Across a **reference** edge (import/call), a spec never triggers generation of the thing it references. It only reads what already exists:
  - if the referenced node already has a current spec, its **summary section** (the file-/symbol-level summary from `REQUIREMENTS.md`'s spec granularity — not the whole document) is pulled in as context, at no LLM cost;
  - if it doesn't yet have one, a deterministic, non-LLM **stub** is used instead — signature plus any inline docstring/comment, read straight off the graph, again at no LLM cost.

One consequence worth naming: specs get richer over time without anyone forcing it. Early on, most references resolve to bare stubs, since little has been generated yet; as more of the repo accumulates specs — lazily, through ordinary queries, or via the opt-in batch command — later generations opportunistically see real summaries instead of stubs for the same references, for free. Whether an *already-generated* spec should ever be revisited later purely to upgrade a stale stub-reference into a real summary is open, and tied to invalidation policy (see "Caching and invalidation" below) rather than to this recursion rule — not required for correctness, deferred.

**Ordering — read and write are separate acts, both demand-driven, neither implicit in the other.** This is the resolution to a second real failure mode: the original design had `get_spec` transparently regenerate a stale/missing node inline before answering — but the only thing capable of actually writing spec text is the *calling agent's own LLM* (CodeOwl holds no credentials — see "Who actually writes the spec text" below), so "transparent" regeneration meant silently repurposing whatever turn the agent was mid-task on into a spec-writing detour. In practice that either derails the agent's actual task or gets silently skipped — neither honors the "silent regeneration" the requirements described. Splitting read from write removes the contradiction:

- **`get_spec(id)` is a pure read, always.** It never calls an LLM and never blocks on one.
  1. If a current spec exists (content hash matches), return it.
  2. If a spec exists but is stale (its `source_hash` or a referenced `interfaceHash` has moved since it was generated — see "Caching and invalidation" below), return that last-known-good spec anyway, flagged `stale: true`, plus which inputs moved (deterministic, off the graph — no LLM needed to say *that* something changed, only to re-describe it).
  3. If no spec has ever been generated, return the same deterministic stub used for reference-edge fallbacks (signature + inline docstring), flagged `missing`.
  A caller always gets an immediate, useful answer; whether staleness matters enough to pay for a refresh is the caller's call, not something forced into its turn.
- **Generation is a separate, explicit act**, driven by the `/codeowl generate` command (see below) — never nested inside a `get_spec` call. When it runs, for a given target `id` it still recurses across **containment children only** (not references — see above), the same memoized-recursion, containment-tree-guaranteed-to-terminate shape as before; it composes exactly the same inputs `get_spec` would have assembled inline under the old design.

The cascade-cap guardrail (a hard limit on how many nodes one `generate` invocation will regenerate before stopping and reporting instead of continuing silently) still applies — it now bounds a `/codeowl generate` run rather than a `get_spec` query, but the reasoning is unchanged: since the cascade only ever walks the containment tree beneath the target, and a widely-shared utility's *implementation* changing no longer forces regeneration of everything that *references* it (only of what actually *contains* it), this should rarely bind in practice.

**Unit boundaries.** The dependency graph tells you *where the valid cut points are* (a function, a class, a file, a package) — but structure alone doesn't guarantee a unit is small enough for one LLM call. A token-budget threshold decides, at each level, whether to generate a spec for the whole unit as-is or recurse one level deeper first (e.g. spec each class in a file individually before rolling them up into a file-level spec). This is the answer to "one spec per module or per submodule": both — every level of the hierarchy gets a spec, and the threshold decides how many levels deep you have to go before a unit is small enough to summarize directly.

**Bottom-up composition.** When generating the spec for a node with containment children (a module with several submodules, a file with several classes), the LLM is given:
- that node's own raw source,
- the *already-generated cached specs* of its containment children — never their raw source, and
- for each reference edge (import/call) leaving this node: the target's summary section if it has a current spec, otherwise a deterministic stub — never a demand to generate one (see "Generation recurses across containment edges only" above).

This is the core token-saving mechanism: a module with five submodules costs one LLM call over its own code plus five short cached summaries, not six modules' worth of raw source — and its imports cost a handful of one-paragraph summaries or bare signatures, never a chase through the rest of the codebase to produce them. It also means the same submodule's spec is generated exactly once and reused everywhere it's a containment child, rather than being re-derived per consumer.

**Who actually writes the spec text.** CodeOwl itself does not call an LLM (see "CodeOwl orchestrates, it doesn't generate" in Design principles). The mechanics are two MCP tool calls per unit, and they underlie every generation path — the only thing that varies is what triggers the loop:
1. The agent calls `get_next_spec_task()` (internally: "the next node on the path the `generate` target needs, that doesn't have a current spec yet" — for a scoped `/codeowl generate <id>`; or the next-highest-fan-in uncovered node in the whole graph, for `/codeowl generate --all` — see "Pushing toward completeness" below). It returns that unit's own source plus its dependencies' cached specs, already assembled.
2. The agent (using whatever LLM it's backed by — Claude Code's own model, or the org's licensed model in Phase 2) writes the spec text, then calls `submit_spec(id, content)`, which CodeOwl persists (to a git-tracked file in Phase 1, to the shared store in Phase 2) along with the content hash it was generated from.

This keeps CodeOwl fully out of the business of holding LLM credentials or picking a provider — it only ever assembles context and persists results. Crucially, this loop is never invoked *by* `get_spec` — only by `/codeowl generate`, run deliberately (see "Ordering" above). CodeOwl has no mechanism to run this loop unprompted either: there is no background daemon and no hook wired up in Phase 1 to trigger it automatically (see "Pushing toward completeness" below for why that's a deliberate deferral, not an oversight).

**Pushing toward completeness.** Lazy-by-default means specs only ever get generated for what's actually been asked about — left alone forever, coverage would track query patterns, not the whole repo. Closing that gap is still an explicit, manual act, never an automatic one (see above), via two flags on `/codeowl generate`:
- `/codeowl generate --all` — walks every currently missing-or-stale node in the graph, to exhaustion. Already the batch mode `REQUIREMENTS.md` scoped in.
- `/codeowl generate --all --budget=N` — the same walk, capped at `N` generations before stopping. This is the incremental version: run it occasionally (weekly, after a big merge, whenever `get_spec_coverage` shows a gap worth closing) instead of committing to a full sweep in one sitting.

Both reuse the identical `get_next_spec_task`/`submit_spec` loop — `--budget` is purely an early-termination parameter, not new mechanism. Traversal order for either flag prioritizes by **reference fan-in** (how many other nodes' `calledBy`/`imports` edges point at this one) rather than directory order: a budgeted run spends its N generations on the most-referenced utilities/hooks first, since — per "One consequence worth naming" above — those are exactly the nodes whose real summary (instead of a bare stub) upgrades the most other specs' context for free on their next generation. No new data is needed for this; fan-in is already computable from the existing graph edges.

`get_spec_coverage` is the dashboard this decision leans on — current/stale/missing counts, broken down by module, tell you whether a `--budget` run is worth it right now and roughly how big a budget would close the gap.

**Caching and invalidation.** Each spec is keyed by a content hash of its inputs, and the two edge types it consumes from (containment children's specs, reference targets' interfaces — see "Recursive spec generation" above) are hashed differently, deliberately:

- **Containment children** contribute the hash of their **own current spec**. If a leaf function's source changes, its `source_hash` changes, which — because regeneration only ever fires on a `source_hash` mismatch (see "Ordering" above) — is the *only* time its spec (and thus this hash) changes. That hash then changes the key the parent module's spec was keyed on, invalidating that too, propagating up the containment hierarchy only as far as the change actually reaches. This is safe to key on spec-body content precisely because a child's spec never regenerates — and so its hash never moves — unless its underlying source truly changed; LLM non-determinism never enters into it, since nothing re-runs the LLM against unchanged input.
- **Reference targets** contribute the target's **`interfaceHash`** (see the `Symbol` record above), never its spec/summary text. This is what avoids the trap a naive design falls into: hashing a dependency's LLM-written summary would mean any reword of that prose — not just a behavior change — cascades invalidation to every consumer. `interfaceHash` is computed once, deterministically, at graph-resolution time, straight off exported signatures/types, so it's stable across regenerations that don't touch the public surface (rewriting `cn()`'s implementation, or its docstring, invalidates nothing downstream) and only moves when something a consumer could actually observe changes (a new required param, a changed return type, a removed export).

Re-indexing after a commit only regenerates the specs on the path from the changed leaf to the containment root (via the first bullet) plus, lazily on next query, the direct referrers of anything whose `interfaceHash` moved (via the second) — never the whole tree, and never the whole reference graph reachable from a change.

**Human corrections — reconciliation, not overwrite.** Specs live in git, so a human edit is always visible as an ordinary commit — but visibility in history isn't the same as the edit persisting forward through the *next* regeneration, which is what actually matters. (Regeneration is explicit rather than silent — see "Ordering" above — but that only means a human is choosing *when* it happens, not reviewing each unit as it's rewritten: a `--all` run will still march straight over a hand-corrected spec unless something protects it.) Each spec file's frontmatter carries a second hash alongside `source_hash`: `spec_hash`, a hash of the generated body as CodeOwl itself last wrote it. Comparing the file's current content against `spec_hash` detects a human edit independently of whether the source changed. This gives four cases, not two:

1. **Source unchanged, spec untouched** — serve the cached spec, no LLM call.
2. **Source changed, spec untouched by a human** (current content still matches `spec_hash`) — plain regeneration from scratch, as described above.
3. **Source unchanged, but `spec_hash` mismatch** — a human edited the spec and the code didn't change; nothing is regenerated, the human edit simply *is* the current spec, and `spec_hash` is updated to match it.
4. **Both `source_hash` and `spec_hash` mismatch** — a **reconciliation regeneration**: the human-edited text is passed into the LLM's context as a prior, human-reviewed version, with an explicit instruction to preserve whatever correction is still accurate and change only what the actual source diff affects. Both hashes are updated on the result.

Only case 4 is new mechanism — the other three fall out of what's already designed. A reconciliation regeneration (case 4) still counts as one call against the cascade cap from "Ordering" above, same as any other regeneration.

**Result.** The stored graph ends up with a spec at every level: symbol/file specs at the leaves, submodule and module specs above them, and (optionally) a system-level spec at the root, all queryable independently — an agent asking about one function gets a precise leaf spec without pulling in the whole module's context, while a BA asking "what does this service do" gets the module- or system-level spec instead.

### 6. MCP server

**Phase 1**: stdio, per-process, exactly like MemoLink's default — one local instance, launched by Claude Code, talking to one repo on disk. No network-facing component at all. Lifecycle is entirely client-managed: the user never starts or stops it themselves — the client spawns it when a session begins and kills it when the session ends, the same model as a language server. It runs wherever the developer's actual toolchain lives — WSL, a devcontainer/DevBox, or directly on native Windows — not tied to any one OS (see `REQUIREMENTS.md`'s "Runtime environment", and "Implementation stack" below for how the Rust choice serves this).

**Phase 2**: served over HTTP/SSE instead, since this needs to be one shared service the whole team's IDEs/CLIs connect to concurrently. Since one instance hosts multiple repos (see Storage), tool calls are scoped by repo — inferred from the client's workspace/auth context, or passed explicitly — so a query always resolves against the right namespace.

Draft tool surface (query tools apply to both phases; the generation tools are the primitives `/codeowl generate` drives — see below):

- `search_code(query, repo?)` — hybrid keyword + semantic search
- `get_symbol(id)`
- `get_callers(id)` / `get_callees(id)`
- `get_dependencies(module)` — build/package dependency graph
- `get_tests_for(symbol)` — living-spec via tests
- `impact_analysis(symbol)` — what breaks if this changes
- `trace_path(from, to)` — call chain between two points; delegates to another team's instance if the path crosses a stub node
- `get_spec(id)` — the cached spec at any level of the hierarchy (symbol/file/submodule/module/system). Pure read, never triggers generation — returns the current spec, or the last-known-good spec flagged `stale` with what changed, or a deterministic stub flagged `missing`. See "Ordering" above.
- `get_next_spec_task()` — returns the next unit needing a spec: the next node on the path a scoped `/codeowl generate <id>` needs, or (in `--all` mode) the next uncovered node in the whole graph ordered by reference fan-in — with its source and its dependencies' cached specs already assembled. See "Pushing toward completeness" above.
- `submit_spec(id, content)` — persists a generated spec (to git in Phase 1, to the shared store in Phase 2), recording the content hash it was generated from
- `get_spec_coverage(scope?)` — reports how much of the graph has a current spec vs. stale vs. missing, broken down by module/directory, plus which specs carry a preserved human correction (`spec_hash` mismatch against the last-generated body — see "Human corrections" above). Needs no separate tracking: it's computed entirely by comparing each node's current hashes against its stored `source_hash`/`spec_hash`. Doubles as the progress/resumability signal for an explicit batch generation run.

**`/codeowl generate [id] [--all] [--budget=N]` is not an MCP tool** — it's a client-side command (a Claude Code slash command in Phase 1) that runs the `get_next_spec_task` → write → `submit_spec` loop above to completion or until `--budget` is spent. It has to live on the client side because the loop's write step needs an LLM, which CodeOwl itself never holds (see "CodeOwl orchestrates, it doesn't generate"). A B2-style trigger — a hook that shells out to a *separate*, headless Claude Code process (`claude -p "codeowl generate --budget=N"`) so completeness pushes happen automatically without touching an interactive session's context — is a plausible future addition, deliberately deferred out of Phase 1: it adds an automatic-token-spend surface before the core hypothesis (do specs even help) is validated, and the manual command is required regardless, so it's the smaller thing to build first.

### 7. Human-facing viewer

Graph browser (Cytoscape.js-style, as in MemoLink) for BAs/QA/SREs who aren't working inside an IDE. REST API backing it, same shape as MemoLink's (`/api/graph`, `/api/search`, `/api/traverse/{id}`).

### 8. Implementation stack

**CodeOwl is written in Rust.** (This is CodeOwl's own language — entirely separate from what it *parses*, which is TypeScript first per `REQUIREMENTS.md`'s pilot target.) The three requirements that drove it:

- **Cross-platform distribution.** `REQUIREMENTS.md`'s "Runtime environment" requires running wherever the developer's toolchain lives — WSL, devcontainer, or **native Windows**. Rust ships one self-contained binary per platform with no runtime to install. The Node alternative would require a Node install plus native addons with per-platform prebuilds, and native-addon builds on native Windows (node-gyp/MSVC) are a well-known sharp edge — precisely the environment called out as mainstream rather than edge-case.
- **Language genericity.** Each additional tree-sitter grammar is a compiled-in crate, or — better for the "add a language without touching the pipeline" goal — a **WASM grammar loaded at runtime**, which tree-sitter's Rust binding supports natively. Contrast Node, where each grammar is a separate native addon and the prebuild burden multiplies by language count.
- **Speed and footprint.** Honest scoping: this matters least in Phase 1, where parsing a laptop-scale repo is ~a second in any host language (tree-sitter is C regardless of binding) and the dominant latency is the LLM writing spec text. It binds in **Phase 2**, where one shared instance parses many repos on push and holds several graphs resident — there, memory footprint matters more than throughput, and that's a large multiple versus a JVM or Node host.

Selected crates: `rmcp` (official Rust MCP SDK), `tree-sitter`, `oxc_resolver` (Node/tsconfig-paths/`exports`-map module resolution — see below), `notify` (cross-platform file watcher, for Phase 1's in-session incremental indexing), `tantivy` (Lucene-equivalent keyword index, replacing the JVM-bound Lucene originally sketched), `ort` (ONNX Runtime, for Phase 2 embeddings), and the `grep` crate (ripgrep's engine, embeddable directly if `search_code` starts as plain text search).

**Module resolution vs. symbol resolution — a precision split this choice makes explicit.** A reasonable objection to a non-TypeScript host is that the TypeScript compiler API hands you path aliases, barrel files, and re-export chains for free. But spec generation needs to know which *file* an import resolves to (`@/lib/utils` → `src/lib/utils.ts`) in order to fetch that target's summary-or-stub — that's **module** resolution, which `oxc_resolver` solves off the shelf. Full type-checker-grade **symbol** resolution (which overload, which alias chain) mainly improves `impact_analysis` and `get_callers` precision, which are secondary tools. So the compiler-API advantage applies mostly to capabilities Phase 1 defers anyway. This is the same tradeoff as open question 1 (tree-sitter vs. LSP), just resolved concretely for TypeScript: start with module-level resolution, and layer in LSP-based symbol resolution later where precision earns its cost.

Two structural constraints follow from the language choice and are worth stating as design rules, not left to discover:

- **The graph is arena-indexed, never pointer-linked.** Nodes live in a flat collection and reference each other by `SymbolId` — never by Rust references or `Rc<RefCell<…>>`. The `Symbol` record above is already written this way (`parent: SymbolId`, `children: [SymbolId]`), which is both the idiomatic Rust answer for a cyclic graph and a prerequisite for cheap serialization of the `.codeowl/` cache.
- **The core is synchronous; async is a thin shell.** Extraction, resolution, hashing, and spec assembly are plain synchronous code. Async appears only at the edges that genuinely need it — the MCP transport (`rmcp` is tokio-based) and the file watcher. Keeping the boundary here means the bulk of the codebase never deals with async lifetimes or `Send` bounds.

## Open questions / decisions to revisit

Requirements-level open questions (whether something is in scope at all) live in `REQUIREMENTS.md`. These are design/implementation questions — what's in scope is settled, how to build it is not.

1. **tree-sitter vs. LSP** — precision vs. speed/breadth tradeoff, especially for C++.
2. **Token-budget threshold for spec unit boundaries** — the concrete rule (or heuristic) that decides, at each level of the hierarchy, whether a unit is small enough to spec directly or must be recursed into further. Needs a concrete number/algorithm, not just the principle.
3. **Polyglot & non-code artifact resolution within one repo** — not one problem, at least three:
   - **Call/invocation boundaries** — a script invoking a compiled binary via `subprocess`/`exec`/shell (e.g. a Python tool calling a C++ binary the repo also builds). Same stub-node treatment as the cross-repo case, but resolved with a lightweight, pattern-based detector rather than full semantic resolution, since it's within one repo.
   - **Schema/data boundaries** — SQL DDL (`CREATE TABLE`, etc.) defining tables that application code references via string literals or ORM calls, not via any call/import tree-sitter can see. Needs a dedicated SQL extractor producing schema nodes (tables/columns/constraints) plus a fuzzy, string/ORM-aware matcher on the application-code side — meaningfully less precise than resolved imports. Directly relevant to the Phase 1 pilot (Supabase SQL migrations), not a future/enterprise-only concern.
   - **Standalone tooling ("island" nodes)** — scripts with no inbound call edge at all (e.g. a perf-test-environment rebuild script, invoked manually or from CI, not from the main codebase). Still worth a leaf-level spec even with no edges into the rest of the graph; if a CI config or Makefile does reference it, that's a further artifact type worth resolving into an edge when possible, but the node's spec shouldn't depend on that being resolved.
4. ~~**CodeOwl's own implementation language/stack**~~ — Resolved: **Rust**. See "Implementation stack" above for the reasoning (cross-platform single-binary distribution, WASM-loadable tree-sitter grammars for language genericity, Phase 2 footprint), the selected crates, and the two structural rules that follow from it (arena-indexed graph, synchronous core with async only at the transport edges). The cross-platform constraint that framed this question — native Windows, Linux via WSL/devcontainer, and macOS, since a Java dev on native Windows is mainstream rather than an edge case — is what the decision is primarily optimizing for.
5. ~~**Reference-edge invalidation**~~ — Resolved: see the `interfaceHash` field on the `Symbol` record and "Caching and invalidation," both above. A reference target's contribution to a consumer's cache key is its deterministic `interfaceHash` (signature/exported-shape only), never its spec/summary text — so a dependency's prose can be reworded freely without invalidating anything downstream, and only an actual public-surface change (new param, changed return type, removed export) does.

## Non-goals (for now)

- Hand-maintained, static "spec documents" disconnected from the code — i.e. specs written once and never re-derived. Every spec CodeOwl produces is LLM-generated and hash-invalidated (see "Recursive spec generation"); this non-goal is about avoiding the traditional design-doc rot problem, not about avoiding spec generation itself.

Product-level non-goals (what CodeOwl does not do, for whom) live in `REQUIREMENTS.md`.
