# Decisions and open questions

The reasoning trail behind CodeOwl's design: every open question, the measurements taken, the alternatives rejected, and how each was resolved. `ARCHITECTURE.md` describes how the system is built; this file records *why* it is built that way, and what is still undecided. The index of all questions (open and resolved) is in `ARCHITECTURE.md` under "Open questions / decisions to revisit".

Original question numbers are kept as-is because `ROADMAP.md`, `CLAUDE.md` and `experiments/` cite them by number. Phrases like "above" and "see ... below" refer to `ARCHITECTURE.md`'s design sections, not to this file.

Requirements-level open questions (whether something is in scope at all) live in `REQUIREMENTS.md`. These are design/implementation questions — what's in scope is settled, how to build it is not. Grouped below by what they're actually about — stack/language coverage, CodeOwl's own internals, or the shape of generated spec output — rather than one flat numbered list; original numbers are kept as-is since other docs (`ROADMAP.md`, `CLAUDE.md`, `experiments/`) cite them by number.

## Stacks & polyglot coverage

<a id="q1"></a>
**1.** **tree-sitter vs. LSP** — precision vs. speed/breadth tradeoff, especially for C++.

<a id="q3"></a>
**3.** **Polyglot & non-code artifact resolution within one repo** — not one problem, at least three:
- **Call/invocation boundaries** — a script invoking a compiled binary via `subprocess`/`exec`/shell (e.g. a Python tool calling a C++ binary the repo also builds). Same stub-node treatment as the cross-repo case, but resolved with a lightweight, pattern-based detector rather than full semantic resolution, since it's within one repo. **Partially carved out:** one specific instance of this — an HTTP call from client code to an API route in the same repo (`fetch("/api/x")` → `app/api/x/route.ts`) — is resolved in Phase 1 by the route-literal resolver (see "Spec document format" → feature specs), because in a convention-based framework that mapping is a deterministic path join rather than semantic analysis, and because it's the single highest-value missing edge in the pilot repo. The general problem stays open; only the framework-convention case is settled.
- **Schema/data boundaries** — SQL DDL (`CREATE TABLE`, etc.) defining tables that application code references via string literals or ORM calls, not via any call/import tree-sitter can see. Needs a dedicated SQL extractor producing schema nodes (tables/columns/constraints) plus a fuzzy, string/ORM-aware matcher on the application-code side — meaningfully less precise than resolved imports. Directly relevant to the Phase 1 pilot (Supabase SQL migrations), not a future/enterprise-only concern. *Update (M17 — Python/FastAPI):* M10 built this as a **file-level** rule — a file is schema iff its name ends `.sql` (`SourceKind::Schema`, in the generic core), acted on only by the TS pack. That shape doesn't survive an ORM: SQLModel / SQLAlchemy / JPA / Django define tables as classes in ordinary code files, and a non-TS repo's `.sql` files are invisible because only the TS pack's `source_kind` claims them. M17 replaces it with a **symbol-level** pack hook — `is_schema_symbol(&ExtractedSymbol) -> bool`, default `false` — where the pipeline extracts a file normally, then retags whichever symbols the pack identifies as tables. A `.sql` file is the degenerate case where every symbol is a table, handled by a pack that *declares* it reads `.sql` (routing to the language-neutral `schema::extract_tables`), not by a hardcoded core branch. The code-side matcher stays the `resolve_flow_edge` seam — and for a class-referencing ORM (`select(Item)`) the edge falls out of ordinary import resolution once the model is a `Schema` node, no fuzzy matching needed. ORM coverage is partial and tiered by design — see open question 8.
- **Secondary-language subtrees** — a repo with one dominant language and a smaller second one in its own subtree (a FastAPI backend + a Vite/React frontend; a Python service + a Node CLI). `detect()` today picks exactly one stack by primary-source-file count and errors on ambiguity — so the smaller subtree is either miscounted as primary (`full-stack-fastapi-template`'s ~86 `.tsx` vs ~19 `.py`) or silently invisible. The M17 workaround is to point CodeOwl at the service subdirectory (`serve <repo>/backend`). The real fix — a "collection of graphs" model: one primary pack (full extraction + resolution + features) plus N secondary-language extractors running in a reduced mode (symbol/file/rollup specs only, no resolution, no feature model), with cross-language edges left unresolved — is now **the milestone before Java** (owner's call, 2026-09-10; `ROADMAP.md`, "Planned insert"), driven by `full-stack-fastapi-template` (Python backend + React frontend). Its scope is a paper spike first — how `detect()` picks a primary and enumerates secondaries, what "reduced mode" means for the trait, whether cross-language edges (the generated OpenAPI client, `fetch` → route) are in or out.
- **Standalone tooling ("island" nodes)** — scripts with no inbound call edge at all (e.g. a perf-test-environment rebuild script, invoked manually or from CI, not from the main codebase). Still worth a leaf-level spec even with no edges into the rest of the graph; if a CI config or Makefile does reference it, that's a further artifact type worth resolving into an edge when possible, but the node's spec shouldn't depend on that being resolved.

<a id="q8"></a>
**8.** **Schema / persistence — coverage is a growing list, not a closed set.** There is no universal "what is a table" signal: JPA `@Entity`, Panache `extends PanacheEntity`, SQLModel `table=True`, SQLAlchemy `class X(Base)`, Django `models.Model`, Prisma `schema.prisma`, Drizzle `pgTable(…)`, jOOQ codegen, MyBatis XML, and raw SQL strings are all distinct; several coexist per language; and which one a repo uses is independent of its primary language. The `is_schema_symbol` hook (open question 3) makes each a small pack-owned function, added when a target repo needs it — the same "wait for a real repo" rule as `feature_model()`. Behaviour degrades in tiers, not on/off: **full** (idiom recognised → table nodes + resolved code→table edges), **partial** (idiom unrecognised but a `.sql`/migration/schema file present → table nodes, weak edges), **none** (nothing recognised → no schema layer; feature specs describe behaviour but not data — the pre-M17 non-TS default). "None" is honest under-reporting, not a bug — but the risk it carries is a feature spec silently omitting "this writes to the database", so a target repo whose persistence style isn't yet covered must be a logged known-gap before its corpus is judged. M17 does SQLModel/SQLAlchemy; M18 adds JPA/Panache; the rest are added on demand.

<a id="q11"></a>
**11.** **Inheritance hides things — annotations, docstrings, and whole members can live on an ancestor, invisible to a plain per-file tree-sitter walk.** Surfaced 2026-09-15, during the M18 (Quarkus) annotation-source investigation, but the shape is general — every OOP stack this project supports or has discussed (Java interfaces/superclasses, TypeScript interfaces/abstract classes, Python ABCs) can hit it. Three distinct manifestations, not one:
- **Annotations/decorators declared on an interface, inherited by the implementor.** The concrete trigger: `quarkus-super-heroes`'s `HeroResource implements HeroesResource` carries no JAX-RS annotations itself — they're all on `HeroesResource`, whose file doesn't even exist in git (see open question 3 / `ROADMAP.md` M18 — it's build-generated from an OpenAPI spec). A class-body-only extractor sees nothing there regardless of whether the ancestor is reachable. **Confirmed empirically, not just read, during M18's dogfood pass (2026-09-17):** running the finished entry-point model (all four kinds — HTTP, Kafka, `@Scheduled`, `@GrpcService`) against the whole 7-module reactor found **4 entry points total** — `EnvResource`/`UIResource`'s two trivial hand-annotated root routes plus the one real Kafka listener (`SuperStats.processFight`) — and **zero** for the actual business surface (`rest-heroes`, `rest-villains`, `rest-fights`, `rest-narration` all use the identical generated-interface pattern, confirmed repo-wide, not just on `HeroResource`). This also means `ROADMAP.md` M18's stated validation criterion — a BA-style "how does *fights* call *heroes*" read of the cross-service edge — **could not be exercised at all** on this corpus: `FightResource` (the entry point that would start that walk) is itself invisible to `enumerate_entry_points` for the same reason. What *was* validated instead: the one real entry point each of `admits_to_core` and `is_schema_symbol` could reach (`GET /` on `rest-heroes` → `UIResource → HeroService → HeroRepository` in `core`, `Hero` correctly in `data`) came back completely correct, and the Kafka commit's same-class-constant channel resolution worked exactly as designed on the real `SuperStats` shape. So the four entry-point kinds and the two persistence/admission hooks are confirmed correct on every real shape they were built against — the gap is entirely upstream of them, in what counts as an entry point at all when the annotations are codegen-only.
- **Docstrings/contract text declared on an ancestor's method, missing from the `@Override`.** Observed live in the same file: `HeroResource.getRandomHero()` has `@Override` and no doc comment of its own — a spec generated from that method alone has no stated contract to draw on, only the body.
- **Members inherited but never overridden at all.** Real and callable, but no text representing them exists anywhere in the subclass's own file — invisible to a walk scoped to that file, regardless of the first two points.
- **Why not build general hierarchy navigation now.** This is a materially bigger capability than any existing pack hook — it's real type resolution (walk to every ancestor/interface, resolve inherited members) in a codebase that deliberately chose tree-sitter text extraction over an LSP-backed symbol table (see open question 1). Building it speculatively, before a real dogfooded repo's spec quality is visibly suffering for it, is exactly the premature-abstraction risk this project's "wait for a real repo" policy exists to prevent (same reasoning as open questions 8 and 10).
- **Measured, not guessed: a census across all three Java repos this project has touched.** Every `@Override` was checked for a preceding doc comment, and every case of a locally-undocumented one was checked for whether it implements a *repo-local* interface that itself carries real Javadoc (excluding JDK boilerplate — `equals`/`hashCode`/`toString`/`Comparable`, which document nothing worth inheriting either way). Result: `quarkus-super-heroes` (63 `@Override`s, 100% locally undocumented) and `quarkus-quickstarts` (107, 100% undocumented) both have **zero** cases of a repo-local documented interface being silently skipped — everyone in both repos skips Javadoc on overrides regardless of inheritance, so neither M18 test repo can ever surface this manifestation no matter how long it's dogfooded. `commons-lang` is the opposite: 991 `@Override`s, 52% locally undocumented, and **31 real cases** of a class implementing a repo-local, genuinely-documented interface with none of that documentation repeated locally — `MutableInt`/`MutableDouble`/`MutableByte`/`MutableShort`/`MutableLong`/`MutableObject`/`MutableBoolean` all implement `Mutable` (4 real Javadoc blocks on the get/set contract); `FastDateFormat`/`FastDateParser`/`FastDatePrinter` implement `DateParser`/`DatePrinter` (9–14 Javadoc blocks); `Memoizer implements Computable`; `AbstractCircuitBreaker implements CircuitBreaker`. So the annotation-inheritance manifestation is real and, as of the M18 dogfood pass, has a concrete design direction (below) even though it isn't built; the docstring-inheritance manifestation is real and live in `commons-lang` specifically, a repo already dogfooded once (M16) and scheduled for fuller corpus generation later.
- **Docstring/unoverridden-member manifestations: not yet decided, but the trigger condition is now concrete.** Logged so these two don't get rediscovered piecemeal mid-implementation. The forcing check is **not** M18/Quarkus — the census above shows it structurally can't surface there. It's `commons-lang`: whenever that repo's corpus generation reaches `Mutable*`, `FastDate*`, `Memoizer`, or `AbstractCircuitBreaker`, read the resulting symbol specs for their overridden methods. A hollow spec (nothing beyond the one-line body, no contract stated) is the real, no-longer-hypothetical evidence this question has been waiting for.
- **Annotation-on-generated-interface manifestation: a design direction, reasoned through 2026-09-17, still not built.** This case is narrower than the other two and worth separating out: it isn't really "an ancestor exists and we declined to walk to it" — `HeroesResource` doesn't exist in source *at all* until a build runs (see open question 3 / `ROADMAP.md` M18). Two approaches were considered and rejected before landing on a third:
  - **Rejected: CodeOwl runs the build itself** (`mvn generate-sources` or similar) to materialize the generated interface, then reads it normally. Rejected because it means executing arbitrary code from the target repo's build file — a real sandboxing concern this project has never accepted anywhere else — plus needing the right JDK/build-tool version, network access for dependency resolution, and handling build failures on repos that don't build cleanly. It also breaks the "point it at a repo, get an instant incremental index" experience, and doesn't generalize: "run the build" means something different per language/build system, so it isn't even a reusable capability.
  - **Rejected: parse the contract file directly** (`openapi.yml` itself, the way M10 already treats a `.sql` file as an alternate source of schema truth). Sound in principle — checked into git, cheap and deterministic to parse, no execution — but this pattern isn't OpenAPI-specific: `.proto` (gRPC — the exact thing M18's own gRPC commit already declared out of scope), GraphQL SDL, AsyncAPI, WSDL, Avro, and Thrift all generate real annotated code from a declarative contract the same way, and each would need its *own* bespoke parser plus its own heuristic for mapping a contract entry (an OpenAPI `operationId`, a `.proto` `rpc` line) back to the implementing method. An ever-growing list of parsers, one per format.
  - **The direction: read whatever's already been generated, if present, as read-only structural reference — never spec-bearing on its own.** Confirmed with real evidence (not assumed): `quarkus-openapi-generator-server` with the OpenAPITools backend emits real `.java` text (not bytecode-only Gizmo generation) at the documented, conventional path `target/generated-sources/quarkus-openapi-generator-server` (`target/generated-sources/jaxrs` for the Apicurio backend) after `mvn compile` — **required as `compile`, not `generate-sources` alone; both narrower alternatives were tried and found wrong, not just unnecessary (corrected 2026-09-20, superseding this section's own first draft of this claim).** `mvn generate-sources` in isolation produces **zero** files — confirmed empirically against a clean `rest-heroes`: the codegen goal isn't actually reachable at that phase in this repo's build, despite its name. Calling the Quarkus plugin's own goal directly (`mvn quarkus:generate-code`) is worse than unhelpful: it exits `0` and writes files, but from a placeholder default spec (`org.acme.ApiResource`, `org.acme.beans.Hero`), not the project's real `openapi.yaml` — the `copy-openapi-spec` step that stages the real spec (bound to the later `generate-resources` phase) hasn't run yet, so it silently generates the *wrong* content rather than failing. Only running through `compile` gets far enough for the real spec to be staged first. It's fine, even expected, for `compile` to then fail at the actual `javac` step over an unrelated Java-25 toolchain requirement the repo's pom targets — the generated interfaces are already correct and on disk by then, and nothing cleans them up afterward: confirmed `target/generated-sources` persists across the failed build and across unrelated sibling-module builds, until an explicit `mvn clean`. **Gradle: not yet verified.** No Gradle-based Quarkus repo has been dogfooded; don't assume an equivalent single command (`./gradlew build` or a narrower task) behaves the same way — including whether the same "isolated codegen task silently uses a placeholder spec" trap applies there too — until a real repo is checked. Once that file exists, it's just ordinary Java with real JAX-RS annotations — the *existing* extractor reads it with zero new parsing code, and the mapping from contract entry to implementing method comes for free too, since the codegen tool already wired the generated interface's method names to real annotations. This generalizes across every contract format for free: after codegen, a `.proto`-driven gRPC stub or a GraphQL-codegen resolver interface is likewise just real source-language code, read by the same per-language extractor CodeOwl already has — one mechanism instead of one parser per format. `lang.rs::FileRole::Generated` is an already-reserved seam for exactly this ("no Phase 1 path convention produces this yet — a `StackPack` supplies the rule (Supabase's `database.types.ts`, protobuf `*_pb.ts`, GraphQL codegen, …)") — this would finally be the real case that writes the rule.
  - **Detection vs. a blanket rule — resolved in favor of blanket.** Whether CodeOwl could *detect* that a repo needs a build (by parsing `pom.xml`/`build.gradle` for known codegen-plugin coordinates) was considered and rejected: it requires parsing build files (already declined elsewhere in this project — see `ROADMAP.md` M18: "only read the poms if a resolution ambiguity actually demands it"), needs an ever-growing list of plugin coordinates to recognize, and only buys a diagnostic message — not a functional improvement, since the blanket check below finds every real annotation regardless of whether CodeOwl "knew" why it was there. Instead: always check a small, fixed list of well-known generated-source directories per build tool (Maven's `target/generated-sources/**`, Gradle's `build/generated/**`), unconditionally, for every repo of that family — a cheap, mechanical existence check, not an interpretation of build config. A repo with no codegen simply has nothing there, at negligible cost. The nudge a developer would get from detection ("you haven't built yet") comes instead from an honest count reported through `get_spec_coverage`'s `generated_sources` field (`{checked_dirs, found}`), not a `codeowl serve` startup `eprintln` as first sketched here — that line is MCP stdio's stderr side channel, which the driving LLM never reads, only a human might; `get_spec_coverage` is the tool the generation loop actually calls, so that's the channel that's LLM-visible (corrected 2026-09-19, see `ROADMAP.md`'s M19 plan).
  - **The scope, as built (M19):** (1) extend the file walk to include the known generated-source directories, even though they're gitignored; (2) tag those files `FileRole::Generated` and exclude them from spec generation entirely — reference only, per the "only spec the hand-written code" principle; (3) the one genuinely new capability: when a class carries none of its own entry-point annotations but `implements` an interface whose file is `FileRole::Generated`, check that interface's matching method's annotations instead. Deliberately narrower than general interface-hierarchy navigation (still declined, see above) — gated specifically on "the interface lives in a directory known to be machine-generated," a one-hop, well-motivated rule, not general OOP semantics.
  - **The honest caveat, unresolved by this design:** it only helps once the developer has run a real `mvn compile` (or equivalent) locally — generated sources are gitignored regardless, so a fresh, never-built clone still shows zero entry points, exactly like today. Strictly no worse, not a guaranteed fix — same tiered-degradation shape as open question 8's schema-coverage tiers (full / partial / none).
  - **Built, M19, 2026-09-20.** Three commits (`ROADMAP.md`'s M19 plan): the walk extension, `FileRole::Generated` exclusion from spec generation, and the one-hop lookup. Validated against the real repo, not just fixtures: `mvn compile` run against all four business services (`rest-heroes`, `rest-villains`, `rest-fights`, `rest-narration` — `mvn generate-sources` alone was tried too and found insufficient, see the "not `generate-sources` alone" correction above), `enumerate_entry_points` went from the 4 this section's own dogfood pass recorded to 39 real entry points, including every one of `HeroResource`/`VillainResource`/`FightResource`/`NarrationResource`'s real endpoints, each correctly attributed to the hand-written file. **All of this validation is Maven-only — Gradle has not been tested at all.** `quarkus-super-heroes` has no Gradle module; every "(or the Gradle equivalent)" in this project's docs is an unverified assumption, not a checked fact, and should be treated that way until a real Gradle-based repo is dogfooded the same way.
  - **Two residual limitations found during that validation, logged rather than built out further (2026-09-20 code review):** (1) the one-hop lookup resolves an interface method purely by name (`{interface}::{method_name}`), with no parameter-list disambiguation — two overloaded methods of the same name on a generated interface collide on one id, silently picking whichever won the last insert. Not yet fixed: OpenAPI-generated interfaces don't produce overloaded methods in any real corpus dogfooded so far (one operation, one method), so building disambiguation now would guess ahead of evidence, the same policy this section already applies elsewhere. (2) `bare_annotation_name`'s package-qualification stripping (needed to recognize a generated interface's fully-qualified annotations at all) applies to every Java annotation check, not just ones on generated files — a hand-written class that deliberately writes an annotation fully qualified inline to disambiguate two same-named markers (a legitimate, if unusual, Java idiom) would now match by bare name regardless of package. No occurrence of this in any dogfooded repo; logged as a known precision tradeoff, not acted on.

<a id="q20"></a>
**20.** ~~**Rust resolution assumes one crate root per repo, so a multi-crate workspace resolves `crate::` paths against an arbitrary crate — and the answer changes from run to run.**~~ — Resolved, 2026-10-01 (`ROADMAP.md` M21.k); see the last two bullets for what was built and what is still not covered. Surfaced 2026-09-30, running the new `examples/graph_stats.rs` across the pilot repos: `ripgrep` (a workspace of 11 crate roots under 12 `Cargo.toml` files, 110 `.rs` files) produced a file graph with **3 edges** where a repo that connected should have far more, and 104 of its 110 files came out isolated.
- **Cause, confirmed by reading the code and by measurement, not assumed.** `rust.rs::crate_src_dir` returns the directory of the *first* `lib.rs`/`main.rs` it finds while iterating a `HashMap` of the walked files, and every `crate::` / `self::` / `super::` path is then resolved against that one directory. In a single-crate repo that is right. In a workspace it is one arbitrary crate's root, so `crates/globset/src/glob.rs`'s `use crate::Error` resolved to `crates/ignore/src/lib.rs` (the wrong crate), and 76 `crate`-rooted imports resolved to nothing. Because `HashMap` iteration order is random per process, **the result is not deterministic**: four consecutive runs on the identical, unchanged repo produced 8, 9, 8 and 4 file-level edges (a fifth earlier run gave 3).
- **Second, related gap, same root cause.** A cross-crate `use grep_regex::RegexMatcher` names another workspace member by its crate name; there is no mapping from a crate name to its root, so these are all treated as external (`globset` 9, `ignore` 4, `grep_matcher` 4, `grep_searcher` 2, `grep_regex` 1 in `ripgrep`) and never become edges.
- **What it affects.** Everything built on resolved imports for a multi-crate Rust repo: `get_callers`/`get_callees`, `dependency_hash`/`deps_hash` (so a spec can show `current` when a real dependency changed, and the hash can differ between two runs of the same code), and feature/rollup dependency assembly. **Correction, found the same day:** this entry first claimed single-crate repos (CodeOwl itself, `bat`) were unaffected. That was wrong. Any binary, test or example in a package that also has a `lib.rs` hits the second gap: CodeOwl's own `main.rs` and 9 test files were isolated in the graph because `use codeowl::index::RepoIndex` never resolved, so `main.rs`'s spec showed `current` while the types it depends on were invisible to it.
- **Built (M21.k), both fixes together.** (1) `crate::` is the root of the *file's own* crate: the nearest enclosing directory holding a `lib.rs` or `main.rs`, else `src` (`rust_crates.rs::CrateMap::crate_root`) — so two workspace crates each resolve inside themselves, and a binary with its own modules (`src/bin/tool/main.rs` plus siblings) resolves inside the binary. (2) A first path segment naming a library crate in the repo resolves like `crate::` inside that crate: the crate name comes from the `Cargo.toml` above the walked files (`[lib] name`, else `[package] name` with hyphens underscored; `[lib] path` honoured; a package with no walked lib root contributes nothing; a manifest that is missing or fails to parse is skipped). Read with the `toml` crate, a new dependency. This reverses the earlier "don't read build files" stance for Rust only, on the grounds that this is the ambiguity that stance reserved an exception for. Directories are visited in sorted order, so the answer is deterministic. `FORMAT_VERSION` 17 -> 18.
- **Validated on real repos, not only fixtures.** `ripgrep` (11 crate roots): file-level edges went from a random 3 to 9 across identical runs to **54, identical on four consecutive runs**; isolated files 104 -> 56. CodeOwl itself: edges 92 -> 127, isolated files 12 -> 0, one connected component. Measured staleness cost on CodeOwl's own specs: **one** existing spec changed status, `src/main.rs`, `current` -> `stale` (the false "current" this fixes).
- **Still not covered, found validating on `ripgrep`; not built.** (a) An integration-test crate whose root is not `lib.rs`/`main.rs` (`tests/tests.rs` declaring `mod util;`): `crate::util` from `tests/feature.rs` stays unresolved, about 20 imports in `ripgrep`. A cheap extension is treating a package's `tests/` directory as one crate root. (b) A re-export written with nested braces (`pub use crate::{ searcher::{Searcher, ..}, sink::{..} }`, `grep_searcher`'s `lib.rs`) is not followed, so `use grep_searcher::Searcher` still misses; and a re-export more than one hop deep, a limit that predates this change. (c) Dependency renames (`package = "..."`), `[[bin]] path` entries, `#[path]` attributes and `extern crate`. A `Cargo.toml` edit is only picked up at the next full open, since the file watcher reacts to `.rs` changes. (d) From the code review of the fix, deliberately left as is, with the reasoning: `CrateMap::crate_root` treats any directory holding a file named `lib.rs` or `main.rs` as a crate root, so a *module* that happens to be called `main.rs` (`src/cli/main.rs`, declared with `mod main;`) would capture its siblings' `crate::` paths. **Why it stays:** it is a file-name guess that was right for every real root in the Rust repos on hand (CodeOwl 2 of 2, `ripgrep` 11 of 11, `bat` 3 of 3), including two unusual ones, `ripgrep`'s `crates/core/main.rs` (declared by a `[[bin]] path`) and `bat`'s `build/main.rs` (a build script). A module named `main.rs` or `lib.rs` was found in none of them; the reviewer found the shape by reading the code. When it does fail it mostly loses an edge (the siblings' `crate::x` looks in the wrong directory and finds nothing) and only affects the files in that one directory; a wrong edge needs a coincidentally named file there. **Options weighed.** (1) A positional guard, counting a nested `main.rs`/`lib.rs` as a root only when it sits under `bin/`, `examples/`, `tests/` or `benches/`: about ten lines and no parsing, but it would reject a real `[[bin]] path` that points inside a library's directory under another name. (2) Reading the bin roots (`src/main.rs`, `src/bin/*`, `[[bin]] path`, `build =`) from the manifest: the principled fix, but real work, and it must reproduce `ripgrep`'s and `bat`'s unusual roots above or it regresses them. Neither is worth building against a shape no repo has shown. **Revisit when** a real repo has a module named `main.rs` or `lib.rs` whose siblings' imports go unresolved; option (1) is the cheap first move. And `CrateMap::load` re-reads every `Cargo.toml` on each rebuild; harmless at these sizes (one `read_to_string` per directory, against a rebuild that already re-resolves every import), but cacheable in `RepoIndex` if a very large workspace ever makes it show up.

**21.** **Other stacks' import resolution has gaps of its own: TypeScript never creates symbols for `interface`, `type` and `enum` declarations or destructured exports, so imports of them produce no edge; Java picks one file when several match, without checking which is right.** Surfaced 2026-10-01, asking whether question 20's gap was Rust-only. Measured the same way on each stack: of the imports that did not resolve, how many name something a file in the repo actually matches.
- **Measurement (a path-suffix check against the walked files; a first look, not an audit).**

  | Stack (repo) | Unresolved imports | Matched by an in-repo file | Verdict |
  |---|---|---|---|
  | Java (`quarkus-super-heroes`) | 1,269 | 0 | path resolution sound |
  | Java (`commons-lang`) | 3,542 | 0 | path resolution sound |
  | Python (`full-stack-fastapi-template/backend`) | 144 | 1, not a real miss (`models.py` re-exports an external name) | sound |
  | **TypeScript (`talentTrail`)** | 858 | **141 (16%)** | real gap, below |

- **TypeScript: module paths resolve (the `@/` alias included); the *symbol* is missing.** `extract.rs` matches only `function_declaration`, `class_declaration` and `lexical_declaration` (`const`/`let`). There is no case for `interface_declaration`, `type_alias_declaration` or `enum_declaration`, so `export type Database = {…}` (19 imports), `export interface JudgeProgress`, `export type RegistrationFormData` and `export type CompetitionStage` are never graph nodes. A destructured export, `export const { handlers, auth, signIn, signOut } = NextAuth(…)`, yields no `auth` symbol either (45 imports, the single largest group), and an `export { X }` of a name the file imported (`VIEW_AS_JUDGE_COOKIE`) does not resolve. In all 141 cases the matched file exists and the symbol is not extracted; none was a path failure.

**22.** **A file's summary is written from the first 8,000 bytes of the file, so most file summaries describe a fragment, and the file-level fingerprint hashes bytes the summary never saw.** Surfaced 2026-10-03, while planning a finer file fingerprint (so a comment-only edit stops staling hub file summaries). **13.** ~~**Should a method's signature belong in a container's `interface_hash`, the way an exported field's now does?**~~ — Decided, 2026-09-29 (`ROADMAP.md` M21.i): **yes.** Surfaced 2026-09-26, verifying M21.c item 4's own premise (`ROADMAP.md`): every pack's fold is gated on `kind == SymbolKind::Value`, so a `Callable` (method) is never folded in at all — a method signature change stays local, identical in mechanism to a body-only edit, confirmed with a dedicated `tests/lifecycle_matrix.rs` scenario across all 4 stacks. Deliberately undecided here, not because it's unimportant but because it's the same shape open question 12 was before M21.a measured it: a real tradeoff, not yet worth guessing at.

The case for leaving it alone: CodeOwl resolves *imports* (file → class), not *calls* (function → specific method on that class) — `get_callers`'s own doc comment in §7 says this plainly: "Not a call graph, and scoped to declared imports only." Without call-level resolution, folding a method's signature can't be targeted at only the consumers that actually call it; every importer of the class would cascade on *any* method's signature changing, whether or not that importer calls it. Classes typically have more methods than public fields, so this could plausibly produce a much noisier cascade than the field fold did — unmeasured, unlike question 12, which had a real cost table before it was decided.

The case against: a method's signature is arguably a *stronger* part of the public contract than a field's type (a signature mismatch is often a hard compile error for real callers, where a field type change might still coerce), and the current gap is a genuine false negative — CodeOwl reports "still current" after a real breaking signature change, which is a worse failure mode for a tool whose whole value is trustworthy staleness signals than the field fold's occasional over-cascade would have been.

Revisit if/when method-call resolution (not just import resolution) exists, the same way question 12 waited for M21.a's measurement rather than being decided from the framing alone.

**Decided, 2026-09-29: fold a public method's signature into its container's `interface_hash`, the same way a public field's now does — all 4 packs, one hop, signature text only, never the body.** The owner's call, from the real numbers above: a bounded cost (worst case 13, same order of magnitude as M21.a's field-fold worst case of 11) against a correctness rationale that's *stronger* for methods than it was for fields on two dimensions real hits actually evidenced (parameter-type and return-type claims, a category fields never had at all). The known downside — CodeOwl resolves imports, not calls, so invalidation can't be targeted at only the importers that actually call the changed method — is accepted as a real, structural limitation rather than something this decision tries to work around; it's the same shape the field fold already accepted, just against a real cost table this time instead of an estimate.

**Built, 2026-09-29 (`FORMAT_VERSION` 15 → 16, one bump covering all 4 packs).** No signature normalization, per this entry's own lean — every method's stored signature is hashed exactly as captured.

Two real correctness cases the naive "just widen the existing `kind == Value` check" version would have missed, caught in plan review before any code was written, not found by a test after the fact:
- **Rust trait methods and Java interface methods carry no explicit visibility keyword at all** — a trait/interface method is public *because the trait/interface itself is*, the JLS/Rust-analogous implicit-visibility shape neither pack's existing field-visibility check (`is_pub_field_signature`, `has_public_or_protected`) was built to recognize, since a *field* never has this shape. Fixed by gating on the *container's* own kind (`raw == "trait"`/`"interface"`) rather than the member's own text. Java's one explicit exception — a Java 9+ `private` interface method — is checked for and excluded.
- **A Rust inherent-impl method doesn't exist as the type's own member at the point `visit_container` first computes `interface_hash`** — it's still a separate `impl` block's member; `merge_inherent_impls` reparents it onto the type afterward. The fold for these methods lives there instead, chaining onto the already-computed `interface_hash` the same self-chaining way that function's own `source_hash` fold already works — a plain field-fold port that only touched `visit_container` would have silently missed every ordinary `impl Type { pub fn ... }` method, which is most of them.

**18.** **Should CodeOwl build a call graph — `Callable → Callable` edges, not just the file-level `import`/`use` edges it resolves today?** Surfaced 2026-09-29, discussing M21.i's own accepted downside (folding a method's signature into `interface_hash` can't be *targeted* at only the importers that actually call the changed method, for exactly the reason `get_callers`'s own §7 doc comment already states: "Not a call graph, and scoped to declared imports only"). Two separate questions, worth keeping apart:

- **For spec correctness, the win is real but marginal, not foundational.** A call graph would sharpen three already-working things — targeted invalidation instead of blanket-per-importer (M21.i's own measured worst case is already bounded: 13 importers, average 3–4), a per-symbol `### Depends on` that doesn't rely on `scoped_symbol_deps`'s whole-word text scan (which M21.i's own measurement caught mis-attributing `Graph` to a symbol that only mentions it in a comment), and a feature spec's flow narrative reaching past one import hop (`FightResource → FightService → HeroClient → HeroRestClient`). None of these are things specs *can't* do today — M21's own BA review already judged feature-spec quality sufficient without call-level precision, and the M18 generated-interface fix deliberately declined general call/type resolution in favor of a narrow one-hop rule for exactly this reason.
- **For human navigation, the win is more plausible but depends on infrastructure that doesn't exist yet.** "Who calls this, and what does it call" is a real, common question — but an IDE's language server already answers it well today. CodeOwl's differentiated value would be a call path where every hop already carries its own generated spec prose (navigable documentation, not just navigable code) — genuinely new, but only realizable once a viewer/UI exists to walk it, which isn't built (see `REQUIREMENTS.md`'s Phase 2 web-viewer item).
- **The real obstacle is correctness, not maintenance cost.** Tree-sitter sees text, not resolved types — it can't reliably attribute `x.foo()` without knowing `x`'s type, can't disambiguate a trait/interface with several implementors, and (confirmed concretely by M21.i's own measurement, not projected) can't even give two Java-overloaded methods of the same name distinct ids today, let alone resolve which overload a given call site means. A confidently wrong call graph is a worse failure mode than no call graph at all, for a project whose entire pitch is trustworthy signals — the same tree-sitter-vs-LSP tradeoff open question 1 already names, just landing on the LSP side of the line this time. A realistic middle path, if this is ever built: read a precomputed SCIP index (an existing code-index format with real indexers for Java/TypeScript/Python/Rust) when a repo has one, the same "read what's already there, don't build a resolver" move this project already made for build-generated sources (open question 3/11's M19 resolution) — not a from-scratch call resolver.
- **Same graph, new edge kind, if built — not a separate graph.** A separate call graph would need to keep its own copy of symbol identity in sync with the real one, which is exactly where bugs come from; `Callable → Callable` edges belong alongside `imports`/`flow_edges` on the existing arena. Two invariants any future build must hold, not yet needing enforcement since nothing is built: call edges must never drive generation recursion (containment-only, per "Recursive spec generation" above), and must not feed staleness invalidation until they're precise enough to trust — an imprecise call edge silently flagging (or silently failing to flag) a spec as stale would be a worse regression than today's coarser-but-honest import-level signal.
- **Not yet decided; deliberately not built now.** Matches this project's "wait for a real repo to demand it" policy (the same reasoning behind open questions 8, 10, and 11's docstring-inheritance item) rather than building ahead of evidence. **The trigger to revisit, per the owner's own call:** measure it after M21.i's build lands — on a real dogfooded repo, how many real feature specs are missing a participant that's two or more call hops from the entry point (the same shape M21.a/M21.h/M21.i's own cost-table measurements already use), the same way M21.a wouldn't guess at the field-fold cost.

Confirmed Rust-specific among the four packs: TypeScript/Java/Python's grammars all keep a class's methods inside its own body node, so none of the three can produce this split at all.
- **Degenerate case (zero fields, zero inherent methods, exactly one trait impl) — M21.e:** `rust.rs::merge_inherent_impls`'s existing inherent-impl fold, extended with one more eligibility condition (`FORMAT_VERSION` 13 → 14). One known limitation, logged rather than built: the "only trait impl targeting it" check is per-file, so a type with a second trait impl living in a different file is invisible to it (confirmed real in `ripgrep`'s `crates/globset/src/serde_impl.rs`, but never observed landing on an actual zero-field marker) — closing it needs a whole-graph second pass, deliberately not built ahead of a real repo hitting the exact conjunction.
- **General case (real fields and/or more than one trait impl, where documents legitimately stay separate) — M21.g:** dogfooding `ripgrep`/`bat` found this shape is not rare — 76/133 and 29/44 surviving top-level trait impls target a type with real fields; `ripgrep`'s `crates/printer/src/stats.rs::Stats` (7 fields, 5 trait impls) is the grounding fixture. Design settled by re-deriving which direction actually has a gap, rather than assuming both symmetric: each document describes only its own symbol's source (the same generation rule M21.e's degenerate case rests on), so a type's own document never says anything about a trait impl's method bodies — nothing there can go wrong when the impl changes, no edge needed in that direction. The impl's document, by contrast, genuinely depends on the type's public shape (`self.field` inside its methods) — that's the real, one-way gap. Built as one synthetic dependency edge per trait impl, `impl -> type` (`rust.rs::same_file_trait_impl_edges`, called from `resolve_imports`) — no new edge kind, just an ordinary `ResolvedImport` flowing through the existing `dependency_hash`/`deps_hash` cascade, with the existing `stale` signal, not a new `smells` concept. No sibling-impl-to-sibling edge: `Stats`'s five trait impls don't depend on each other, only each depends on `Stats` itself. Confirmed Rust-only. Covers both a same-file trait impl (no `use` needed, so `graph.imports()` had no edge for it at all until this fix) and a cross-file one with an explicit `use` (already covered by the pre-existing `use`-resolution + `contains_identifier` scoping — confirmed by a passing test, not assumed). No `FORMAT_VERSION` bump: `RepoIndex::open` calls `rebuild()` unconditionally on every open, always re-deriving `imports` fresh from already-cached data — unlike `extract_symbols`'s output, `resolve_imports`'s result is never what a stale `.codeowl/` cache could silently keep serving. **A real self-dependency bug, caught by `/code-review high` on the shipped PR before merge, needed one more fix beyond the above:** the scoping mechanism `dependency_hash`/`scoped_symbol_deps` share matches a resolved import to a symbol purely by same-file + whole-word text containment, with no record of which symbol created the edge — safe for an ordinary `use` import (Rust rejects `use`-ing a name a file also locally declares), but this synthetic edge's `imported_name` is deliberately a locally-declared type's own name, which that type's own declaration always contains too. Without an exclusion, `PersonalGreeter` matched its own synthetic edge and appeared to depend on itself — exactly the type→impl direction the design concluded had no gap. Fixed with an explicit `self_id` exclusion in both functions (never legitimate for any resolved import, in any pack, to target the very symbol being scoped) — not scoped narrowly to this one edge kind. A second, related fix in the same pass: the synthetic edge's `specifier` was an empty string, unlike every other resolved import, rendering a malformed `` `target` — `` line with nothing after the dash in both the rendered spec and `get_callees`'s response — now `"same file"`.

<a id="q4"></a>
**4.** **Feature boundaries and naming** — M5 derives one feature spec per framework-enumerated entry point, slugged from its route path. Real features don't always map 1:1 to routes: some span several (a wizard across three pages), some routes are too trivial to warrant a feature narrative, and route slugs make poor human-facing titles. A manifest for merging/renaming/excluding is the obvious answer, but its format is deliberately not designed yet — guessing it before real generated feature specs exist to judge against would be premature. Revisit once M5 has produced a repo's worth of them. *Update (M13-pre spike, `experiments/exp-02-feature-layer.md`):* the feature layer is now an **optional** pack capability — a library stack (commons-lang, and CodeOwl's own Rust by choice) returns no feature model at all and composes the system spec over module rollups. When a stack *does* have one, an `EntryPoint` carries a pack-owned `kind` (a Quarkus service has HTTP-resource, Kafka-consumer, scheduled-job and gRPC entry points coexisting), and titling is per-kind and pack-internal — a route slug is a Next.js-ism, not universal. The merge/rename manifest is still deferred: design it when a framework stack with real routing (M17/FastAPI, then M18/Quarkus) can shape it.

<a id="q10"></a>
**10.** **One `feature_model()` per `StackPack`, fixed at compile time — no answer yet for two real frameworks in one language.** Surfaced 2026-09-15, at the start of M18 (Quarkus). `feature_model(&self) -> Option<&'static dyn FeatureModel>` (`stack.rs`) takes no repo context: whatever a `StackPack` impl hardcodes is what runs against *every* repo that pack matches. This has worked so far because each language has had exactly one real framework worth modeling (`TypeScriptNextStack` → `TypeScriptNextFeatureModel`, `PythonStack` → `FastApiFeatureModel`) — a non-matching repo (a Vite frontend under the Next model) just recognizes zero entry points, which is *correct* there because Q2 of `experiments/exp-03-polyglot.md` already established that repo genuinely has no comparable feature layer to model.
- **Why Spring Boot (hypothetical, not yet scheduled) is a different case, not the same one.** If `JavaStack::feature_model()` is hardcoded to a Quarkus-shaped recognizer (JAX-RS `@Path`, `@Incoming`/`@Scheduled`/`@GrpcService`) and pointed at a Spring Boot service instead, it finds nothing — completely different annotation vocabulary (`@RestController`, `@GetMapping`, `@KafkaListener`). Unlike the Vite case, a Spring service *does* have a real product surface just as legitimate as a Quarkus one's; silently producing zero feature specs for it would be an actual regression (indistinguishable from a library with no runtime entry surface), not a benign non-fire.
- **Two shapes a real fix could take, neither built or chosen:** (A) one recognizer per language that tolerates several frameworks' conventions internally — several annotation vocabularies mapping onto the same `EntryPoint.kind` taxonomy, the same looseness `fastapi.rs::parse_route_decorator` already has ("any `.<verb>(` call is a route, receiver unchecked") extended to "any of these annotation shapes is a route"; no trait change needed. Or (B) several `FeatureModel` impls per language, composed and merged — `enumerate_entry_points` results unioned from whichever recognizer(s) actually fire on this repo — real new plumbing, since the trait doesn't support composition today. (A) fits the existing precedent (one model per stack, tolerant of not firing) with no trait-shape change; (B) is more explicit but requires it.
- **Not yet decided, deliberately.** Matches this project's stated "wait for a real repo" policy for exactly this class of question (see open question 8, `is_schema_symbol`'s own doc comment) — Spring Boot isn't a scheduled milestone, so guessing the shape now would risk the same kind of premature guess M13's `FeatureModel` trait was deliberately kept minimal to avoid (design decision 8: "an interface with one real impl for three milestones will accrete assumptions nobody can see"). Revisit when a second real Java (or any language's second) framework is actually on the schedule.
